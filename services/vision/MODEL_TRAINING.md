## 1. 왜 딥러닝이 아니라 SVM인가

후보는 두 갈래였다 (`document/02_설계문서_v2.md` §2).

- **후보 A — 랜드마크 + 경량 분류기**: MediaPipe가 뽑아준 21개 좌표를 입력으로 쓰는 방식
- **후보 B — 이미지 분류(CNN fine-tuning)**: 손 영역을 잘라 CNN에 넣는 방식

**A를 골랐다.** 결정적인 이유는 네 가지다.

1. **데이터가 적다.** 클래스당 ~300장, 총 8클래스 2,400장이 목표다(04_데이터셋명세서_v2 §2).
   CNN fine-tuning에는 턱없이 부족하지만, 63차원 저차원 벡터를 쓰는 고전 분류기에는 충분한 규모다.
2. **조명·배경 강인성을 MediaPipe가 이미 해결해준다.** 우리가 픽셀을 직접 다루지 않으므로
   배경이 바뀌어도 좌표는 비슷하게 나온다. 계획서가 악조건 인식을 범위에서 제외한 것과도 맞는다.
3. **일치율(match_score)을 자연스럽게 얻는다.** 같은 63차원 공간에서 코사인 유사도만 재면 되므로,
   "얼마나 비슷한가"를 위한 별도 설계가 필요 없다(§5 참고).
4. **비전공자 팀원이 설명할 수 있어야 한다.** 팀 4명 중 2명이 비전공자이고, 5주 안에 각자 자기
   파트를 발표에서 설명해야 한다(01_프로젝트계획서_v4 정성 목표). `C`, `gamma` 두 개짜리 모델이
   "어떤 층을 얼마나 얼렸는지" 설명해야 하는 CNN보다 훨씬 유리하다.

그중에서도 **RBF 커널 SVM**을 고른 이유 (05_모델카드_v3 §5-2):

- **MLP 대비**: 소규모 데이터에서 초기화·학습률에 덜 민감하고 재현이 쉽다. 5주 일정에서 "어제는
  잘 됐는데 오늘은 안 되는" 상황을 피하는 게 중요했다.
- **랜덤포레스트 대비**: 랜덤포레스트는 축에 수직인 분할을 쌓는 방식이라, 회전 정렬까지 마친
  연속형 좌표 공간에서는 매끄러운 커널 경계를 만드는 SVM이 더 적합하다고 판단했다.
- **수신호 7종이 "손가락 조합"으로만 구분된다**(02_설계문서_v2 §4)는 점도 근거다. 미세한 질감이
  아니라 관절 위치의 기하학적 차이라서, 좌표 기반 분류기로 충분히 갈린다.

> ⚠️ 정직하게 남겨둘 것: "좌회전 유도(엄지+검지)"와 "우회전 유도(엄지+약지)"는 손가락 하나 차이다.
> 실측 혼동행렬에서 이 쌍이 가장 먼저 무너질 가능성이 높다(05_모델카드_v3 §9). 만약 실제로 무너지면
> 분류기를 바꾸기 전에 **손 모양 재설계**부터 검토하는 게 맞다 — 모델 문제가 아니라 클래스 설계 문제이기 때문.

## 2. 특징 추출: 왜 이런 정규화를 거치는가

코드: [`src/cognition/normalize.py`](src/cognition/normalize.py) (05_모델카드_v3 §3-5 구현체)

MediaPipe가 주는 원본 좌표를 그대로 쓰면, 분류기가 "손 모양"이 아니라 **"손이 어디에 있었는지,
얼마나 컸는지, 어느 쪽으로 기울었는지"** 를 외워버린다. 그래서 네 가지 변인을 차례로 제거한다.

| 단계 | 하는 일 | 제거되는 변인 |
| --- | --- | --- |
| 1. 좌우 손 통일 | Handedness가 `Left`면 x좌표 반전 | 왼손/오른손 차이 — 어느 손으로 해도 같은 신호로 인정 |
| 2. 원점 이동 | 손목(landmark 0)을 원점으로 | 화면 속 손의 위치 |
| 3. 스케일 정규화 | 손목→중지 MCP 거리로 나눔 | 손 크기, 카메라와의 거리 |
| 4. 회전 정렬 | 손 고유 좌표계로 변환 | 손 기울임(촬영 변인 ±15°) |

4번은 문서가 "손목→중지 MCP 벡터를 기준 축에 정렬"이라고만 정해두었는데, 축 하나만 맞추면 **그 축을
중심으로 도는 회전(roll)이 남는다.** 그래서 구현에서는 손바닥 가로 방향(검지 MCP → 새끼 MCP)을 두 번째
기준으로 삼아 x·y·z 세 축을 모두 고정했다. 남는 자유도 없이 완전한 canonical 자세가 된다.

결과는 21 × 3 = **63차원**. 정규화 특성상 손목(0,0,0)과 중지 MCP(0,1,0)는 항상 상수라 실질 정보는
57차원이지만, 문서가 정의한 63차원을 그대로 유지했다(스키마·문서와 숫자를 어긋나게 만들지 않기 위함).

> **학습과 추론이 같은 코드를 쓴다.** 노트북은 저장소를 `git clone` 해서 이 `normalize.py`를 그대로
> import한다. 전처리가 학습 때와 추론 때 달라지는 것(train-serve skew)은 조용히 정확도를 갉아먹는
> 대표적인 사고 유형이라, 아예 복붙 대신 같은 파일을 쓰도록 구조를 잡았다.

## 3. 데이터 분할: 왜 인물 단위인가

04_데이터셋명세서_v2 §4가 **subject-wise split 강제**를 못 박았다. 이유는 단순하다 — 사람마다 손
모양·관절 비율·습관이 다른데, 같은 사람의 손이 train과 test에 섞이면 모델이 "이 사람의 손"을 외워서
실제보다 높은 점수가 나온다. 팀원 4명이 데이터 대부분을 찍는 구조라 위험이 특히 크다.

그래서 코드에서는 두 겹으로 지킨다.

1. **최종 test 분리**: 외부인 1~2명의 `subject_id`를 `TEST_SUBJECT_IDS`로 지정해 학습에서 완전히 제외.
2. **교차검증도 인물 단위**: 하이퍼파라미터 탐색의 CV를 `GroupKFold(groups=subject_id)`로 돌린다.
   일반 `KFold`를 쓰면 검증 점수 자체가 부풀려져 잘못된 하이퍼파라미터를 고르게 된다.

## 4. 학습 설정과 τ(미판정 임계값)

### 4-1. 하이퍼파라미터 탐색

```python
Pipeline([
    ("scaler", StandardScaler()),
    ("clf", CalibratedClassifierCV(SVC(kernel="rbf"), method="sigmoid", cv=3, ensemble=False)),
])

param_grid = {
    "clf__estimator__C":            [0.1, 1, 10, 100],      # 오분류 허용 정도(작을수록 부드러운 경계)
    "clf__estimator__gamma":        ["scale", 0.01, 0.1, 1],  # 한 샘플의 영향 반경(클수록 국소적=과적합 위험)
    "clf__estimator__class_weight": [None, "balanced"],     # 클래스별 수집량이 어긋났을 때 대비
}
```

- **StandardScaler를 붙인 이유**: RBF 커널은 거리 기반이라 차원별 스케일이 다르면 특정 좌표축이
  거리 계산을 지배한다. 정규화를 이미 했더라도 z축(깊이)은 MediaPipe 추정값이라 분산이 다르게 나올
  수 있어 표준화를 한 번 더 건다.
- **탐색 점수는 Macro F1(신호 7종)**: 05_모델카드_v3 §7-1에서 "Macro F1은 negative를 빼고 계산"으로
  확정했으므로, 하이퍼파라미터를 고르는 기준도 같은 지표로 맞췄다. 최적화 지표와 보고 지표가 다르면
  엉뚱한 모델이 뽑힌다.

### 4-2. 확률 보정과 τ 결정

`is_reject`(미판정)를 가르려면 "이 예측을 얼마나 믿을 수 있는가"라는 확률이 필요하다. SVM은 원래
확률을 내지 않으므로 **Platt scaling**(내부 교차검증으로 시그모이드를 적합)을 씌운다. 학습이 조금
느려지지만, τ 없이는 미판정률 KPI(≤5%) 자체를 만들 수 없다.

> 구현 메모: 흔히 쓰는 `SVC(probability=True)`는 **scikit-learn 1.9에서 deprecated(1.11 제거 예정)** 라
> 권장 API인 `CalibratedClassifierCV(SVC(), ensemble=False)`를 쓴다. 동작(시그모이드 보정)은 같다.
> 보정의 내부 `cv=3`은 인물 단위가 아니지만, 이는 보정 곡선에만 영향을 주고 결정 경계는 건드리지
> 않는다. **τ를 고르는 확률은 아래 절차에서 GroupKFold로 따로 뽑으므로** 인물 단위 원칙은 지켜진다.

τ는 05_모델카드_v3 §8-1 절차를 그대로 코드로 옮겼다.

1. train/val에서 **교차검증 확률**(`cross_val_predict`, GroupKFold)을 모은다 — test는 최종 보고용으로 남긴다
2. τ를 0.50 ~ 0.95까지 0.05 간격으로 훑으며 정답률 / 오분류율 / 미판정률을 재계산
3. **치명 오분류("정지"→다른 클래스)가 1건이라도 있는 τ는 먼저 탈락** (KPI 0건이 최우선 제약)
4. 정답률 ≥ 92%, 오분류율 ≤ 3%, 미판정률 ≤ 5%를 **동시에** 만족하는 후보만 남김
5. 그중 **미판정률이 가장 낮은 값**을 채택 — 학습자가 불필요하게 재시도하는 횟수를 줄이기 위함

모두 만족하는 τ가 없으면 노트북이 경고를 띄우고 차선책을 고른다. 그때는 **모델을 더 만지기 전에
데이터 추가 수집이나 클래스 재설계를 검토**하고, 그 사실을 06_테스트기록_v2 / 08_리스크레지스터에
남기는 것이 맞다.

> 학습 전 기본값은 τ=0.75, N=3프레임이다(05_모델카드_v3 §8-0). 실측 데이터가 없는 상태에서 고른
> 잠정치이고, 위 절차로 확정한 값이 번들에 실려 서비스가 자동으로 그 값을 쓴다.

## 5. match_score는 분류와 따로 계산한다

`predicted_class`(무엇으로 판정했는가)와 `match_score`(얼마나 비슷한가)는 **다른 질문**이다.
학습자 입장에서 "정답이지만 70점", "정답이고 95점" 같은 피드백이 나와야 교육 도구로 쓸모가 있다.

- 클래스별 **centroid**(같은 클래스 학습 벡터의 평균)를 템플릿으로 삼는다.
- 추론 시 현재 63차원 벡터와 예측 클래스 템플릿의 **코사인 유사도**를 잰다.
- 0~100 매핑은 05_모델카드_v3 §2가 "percentile 매핑"을 요구한다. 분포를 알아야 하므로, 노트북이
  검증셋에서 **같은 클래스 유사도의 5·95 퍼센타일**을 구해 번들에 싣고, 서비스는 그 구간을 0~100으로
  선형 매핑한다([`src/cognition/templates.py`](src/cognition/templates.py)).

템플릿은 `sign_templates.json`으로도 내보낸다. 이 파일을 데이터 담당에게 넘기면
`services/data/src/seed_templates.py`가 DB(`sign_templates` 테이블)에 넣고, 그제서야 서비스의
match_score가 0이 아닌 값을 낸다. **DB가 비어 있으면 match_score는 0으로 안전하게 동작**한다.

## 6. 산출물과 로컬 적용

노트북 마지막 셀이 만드는 것:

| 파일 | 어디로 | 용도 |
| --- | --- | --- |
| `svm_classifier.joblib` | `services/vision/models/` | 모델 + classes + τ + match_score 보정 + 메타데이터 번들 |
| `sign_templates.json` | 데이터 담당 → `seed_templates.py` | 클래스별 centroid (match_score용 DB 시드) |

번들에 τ와 보정값까지 함께 담는 이유는, **모델과 임계값이 따로 놀지 않게** 하기 위해서다. 모델을
새로 학습하면 확률 분포도 바뀌므로 τ도 같이 바뀌어야 한다. 파일 하나만 교체하면 둘 다 갱신된다.

```bash
# ① 서비스가 모델을 물었는지 확인
docker compose up --build vision
curl http://localhost:8001/health     # model.loaded == true, tau, classes 확인

# ② 실제로 잘 맞히는지 눈으로 확인 (노트북 웹캠)
cd services/vision
pip install -r requirements-dev.txt
python scripts/webcam_check.py        # 손을 비추면 예측 클래스·confidence·match_score가 뜬다
```

②는 **숫자(정답률)만으로는 안 보이는 문제**를 잡는 단계다. 예를 들어 좌회전/우회전이 실제로는 잘
갈리는지, 손을 천천히 바꿀 때 N프레임 안정화가 답답하지 않은지, 특정 각도에서만 무너지는지 같은 것들.
webcam_check는 운영과 **같은 `cognition/` 코드**를 쓰므로, 여기서 본 판정이 곧 RPi5에서의 판정이다
(카메라 기종 차이는 남는다 — 최종 확인은 Pi Camera Module 3로).

환경변수 `CONFIDENCE_THRESHOLD`를 주면 번들의 τ를 **덮어쓴다**(운영 중 급히 조일 때용).
평소에는 설정하지 않고 번들 값을 쓰는 것을 권장한다.
