# 인터페이스 계약서 (v1)

> 관련: 02_설계문서_v1 · 05_모델카드_v1
목적: 인식 ↔︎ 제어 ↔︎ DB 간 메시지 스키마를 명문화하여, 팀원이 각자 파트를 독립적으로 개발해도 통합 시 문제가 없도록 함.
> 

> **이 문서 작성법**
이 문서의 목적은 “담당자가 바뀌어도, 파트가 나뉘어 있어도 서로 연동이 되는 것”입니다. 작성 원칙:
> 
> 1. 필드마다 **이름, 타입, 예시값, 단위**를 반드시 명시하세요. (“각도”라고만 쓰지 말고 “0~180, 정수, 도(degree)”처럼)
> 2. 스키마를 바꿀 때는 버전을 올리고(v1→v2), 무엇이 왜 바뀌었는지 이 문서 맨 아래 “변경 이력”에 남기세요.
> 3. 파트를 나눠 개발하는 팀원끼리는 **이 문서에 있는 필드명 그대로**로 코드 변수명을 맞추면 통합 시 혼선이 줄어듭니다.
> 4. `⚠️` 표시는 실물 테스트 전에는 확정할 수 없는 값입니다 — 하드웨어(AiHand, micro:bit)를 손에 쥐고 직접 측정한 뒤 채워 넣으세요.

---

## 1. 시스템 구성 요소

```
[카메라] → [Perception: MediaPipe] → [Cognition: 분류기] → [교육 상태머신] → [Actuation: AI Hand / micro:bit]
                                                ↕
                                          [수신호 DB]
```

## 2. 카메라 → Perception

> ⚠️ 계획서 전제조건: “카메라는 랜드마크 좌표를 호스트로 넘길 수 있는 장치여야 함”. 온보드 자체 분류만 하는 AI 카메라(예: WonderCam류)는 부적합할 수 있음 — 기본안은 **일반 USB 웹캠 + RPi5에서 MediaPipe 실행**.
> 

| 항목 | 스펙 (초안) |
| --- | --- |
| 입력 | RGB 프레임 (해상도/FPS: *확정 필요*) |
| 출력 | 21 keypoints × (x, y, z) |

> **해상도/FPS는 어떻게 정하나요?** 카메라 스펙(최대 해상도) 확인 → MediaPipe가 실시간(1초에 여러 프레임)으로 처리 가능한 해상도로 낮춰가며 테스트(보통 640×480 부근에서 시작) → 판정 지연(P95 ≤ 1.0초) 목표를 만족하는 최소 해상도로 확정. 확정 후 이 표를 바로 채우세요.
> 

## 3. Perception → Cognition (랜드마크 스키마)

```json
{
  "timestamp": "ISO8601",
  "hand_detected": true,
  "landmarks": [
    {"id": 0, "x": 0.0, "y": 0.0, "z": 0.0},
    "... (21개)"
  ]
}
```

## 4. Cognition → 교육 상태머신 (판정 결과 스키마)

```json
{
  "predicted_class": "string (수신호 이름 또는 'negative')",
  "confidence": 0.0,
  "match_score": 0,
  "is_reject": false,
  "latency_ms": 0
}
```

- `match_score`: 일치율(유사도) 0~100 점수 (계획서 KPI 항목)
- `is_reject`: 신뢰도 임계값 미달 시 true (미판정률 계산에 사용)
- 판정 지연(P95 ≤ 1.0초) 측정 기준점: 손 정지 시점 → 이 스키마 확정 시점

## 5. 교육 상태머신 → Actuation

### 5-1. AI Hand 제어 명령 (초안)

```json
{
  "command": "demo | correct_pose",
  "target_signal": "string (수신호 이름)",
  "servo_angles": {
    "thumb": 0, "index": 0, "middle": 0, "ring": 0, "pinky": 0,
    "wrist_rotation": 0
  }
}
```

> 서보 각도값은 설계 문서의 “분야별 수신호 후보안”에서 실물 테스트로 확정 필요 (특히 수중 OK 사인). **작성법:** 최종 채택 5종마다 한 행씩 실측 각도값 표를 이 아래에 추가하세요 (예: `| 정지 | thumb:0, index:0, ... | wrist:0 |`).
> 

### 5-2. micro:bit 시리얼 프로토콜

> 통신 방식: **USB 시리얼** (BLE는 페어링 이슈로 미사용). 한 줄 텍스트 수준으로 충분.
> 

**RPi → micro:bit** (LED 매트릭스 표시 지시)

```
RESULT:OK:87\n
```

- 필드: `RESULT` (고정) : `OK|NG` (정오답) : `87` (match_score, 0~100)

**micro:bit → RPi** (버튼 입력)

```
BTN:A\n
BTN:B\n
BTN:AB\n
```

> ⚠️ 위 프로토콜은 초안 예시입니다. 실제 필드 구분자, 종료 문자, 에러 처리(파싱 실패 시 재전송 여부) 등은 구현 착수 전 확정 필요.
> 
> 
> **확정하는 방법:** micro:bit 담당자와 RPi 담당자가 함께 실제 시리얼 통신 코드를 5~10줄만 짜서 문자열을 주고받아 본 뒤, 실제로 동작한 형식을 그대로 이 문서에 옮겨 적으세요(“설계만 하고 나중에 코드로 바꾸기”가 아니라 “코드로 확인된 것만 문서화”하는 순서를 권장합니다).
> 

### 5-3. 물리 피드백 지연 측정 기준

- 시작점: 손 정지 시점 (Perception 입력 기준)
- 종료점: AI Hand 동작 완료 + micro:bit 표시 완료 (둘 중 늦은 시점)
- 목표: P95 ≤ 2.0초

## 6. 수신호 등록 기능 인터페이스

| 단계 | 입출력 |
| --- | --- |
| 촬영 | 카메라 → 랜드마크 시퀀스 (여러 프레임) |
| 등록 | 랜드마크 템플릿 → DB 저장 (수신호 이름, 분야 태그 포함) |
| 즉시 인식 | 재학습 없이 신규 템플릿과의 유사도 비교로 인식 |
- 목표: 등록 소요 시간 ≤ 60초/수신호
