## 1. 무엇을 만드나

학습자가 수신호를 **보여주는 동안만** picar가 움직이고, 명령이 끊기면 picar가 **스스로 멈춘다**(dead-man 방식).

```
[RPi5]                                                   [RPi4B]
vision GET /latest  ─┐                                   
vision GET /health  ─┴─▶ drive_bridge.py ── 10Hz ──▶ POST /drive ──▶ 모터 + LED
                         (판정 → 주행 명령 변환)          └ 0.5초 안에 다음 명령이 없으면 워치독이 정지
```

| 구분 | 교육 모드 (현행, 변경 없음) | 조종 모드 (신규, 선택) |
|---|---|---|
| 호출 주체 | web 상태머신 | `drive_bridge.py` |
| 엔드포인트 | `POST /picar` | `POST /drive` (본문은 같은 `picar_command`) |
| 전송 시점 | 정답일 때 1회 | 수신호 확정 중 매 100ms |
| 주행 종료 | 2초 뒤 자동 정지 (`PICAR_MOTION_DURATION_S`) | 마지막 명령 0.5초 뒤 정지 (`PICAR_WATCHDOG_S`) |
| 속도 상한 | 50 (`PICAR_MAX_SPEED`) | 30 (`PICAR_DRIVE_MAX_SPEED`) |

> 범위 확인: 01 §범위 제외 항목 "연속 제스처·동작 추적(하드웨어 제약)"과 겹쳐 보일 수 있습니다. 조종 모드는 정적 수신호 판정을 반복할 뿐 동작 추적은 아니지만, 해석은 요구사항·범위 A(이동혁) 확인이 필요합니다 — 회의 안건 1.

**두 모드를 동시에 돌리지 않습니다.** 조종 모드를 켤 때는 web을 내리거나 교육을 진행하지 않는 상태여야 합니다(§6 운영 규칙).

### 왜 `/picar`에 옵션을 넣지 않고 엔드포인트를 따로 두나

- `/picar`는 09-23~25 실물 검증을 통과한 경로입니다. 창 길이·LED 동작을 바꾸면 그 검증이 무효가 됩니다.
- 스키마에 필드를 추가하면 전원 리뷰가 필요합니다(README §4). 같은 본문을 받는 엔드포인트를 추가하는 것은 스키마 변경이 아닙니다.
- picar를 재시작하지 않고 두 모드를 오갈 수 있습니다(환경변수로 창 길이를 바꾸는 방식은 재시작이 필요합니다).

## 2. picar 변경 (`services/picar/src/`) — 0.5일

기존 `_schedule_auto_stop()`([controller.py:189](../../services/picar/src/controller.py))은 이미 주행 명령마다
타이머를 취소하고 새로 겁니다. 워치독의 핵심은 **이 타이머의 창 길이를 호출 경로별로 다르게** 하는 것입니다.

| # | 변경 | 내용 |
|---|---|---|
| P1 | 창 길이 인자화 | `_schedule_auto_stop(duration_s)`, `_apply_motor(..., duration_s)`. `/picar`는 `MOTION_DURATION_S`(2.0), `/drive`는 `WATCHDOG_S`(기본 0.5). 기본 인자로 현행 동작 유지 |
| P2 | `POST /drive` | `controller.execute(cmd, mock, mode="drive")`. 속도는 `min(MAX_SPEED_PCT, DRIVE_MAX_SPEED_PCT)`로 자름 |
| P3 | **LED 중복 적용 방지** (drive만) | 채널 상태가 직전과 같으면 `_apply_led`를 **다시 호출하지 않는다**. 지금은 명령마다 `led.blink()`를 새로 걸어, 100ms 간격으로 보내면 0.3초 점멸이 계속 처음부터 시작돼 **계속 켜진 것처럼** 보인다. 세대 갱신·소등 타이머 재예약은 그대로 한다(명령이 이어지는 동안 LED 유지) |
| P4 | 적용 상태 캐시 초기화 | 소등 타이머가 LED를 끄거나 `/picar`가 들어오면 캐시를 비운다 — 안 비우면 다음 `/drive`가 "같은 상태"로 보고 LED를 켜지 않는다 |
| P5 | LED 창 | drive에서는 LED 소등도 `WATCHDOG_S`로. 차는 섰는데 LED만 2초 남는 불일치를 없앤다 |
| P6 | `/health` 필드 | `watchdog_s`, `drive_max_speed_pct`, `last_drive_age_ms`(마지막 `/drive` 이후 경과), `drive_active` |

환경변수 (신규): `PICAR_WATCHDOG_S`(기본 0.5), `PICAR_DRIVE_MAX_SPEED`(기본 30). 둘 다 **0 이하면 `/drive`를 거부**
(`status: error`, `reason: drive_disabled`) — 창이 없는 연속 주행은 허용하지 않습니다.

**바꾸지 않는 것**: `/picar` 동작·응답, 정지 쓰기 순서(쓰기 성공 후 타이머 취소), 정지 3회 재시도, `shared/schemas/`.

## 3. 브리지 (`services/actuation/scripts/drive_bridge.py`, RPi5에서 실행) — 0.5일

vision `/latest`를 100ms마다 읽어 판정을 주행 명령으로 바꿔 `/drive`로 보냅니다. **재시도하지 않습니다** —
다음 주기가 곧 재시도입니다. 모든 HTTP 타임아웃은 주기보다 짧게(`/latest` 80ms, `/drive` 150ms) 둡니다.

**선례가 이미 있다.** `aihand_picar_demo.py`·`aihand_vision_picar_demo.py`의 `PicarDriver`는 주행 상태를
`HEARTBEAT_S`(1초)마다 다시 보내 2초 자동 정지와 맞물려 연속 주행을 만든다 — 창이 긴 워치독이다.
`load_test.py`도 같은 방식이며 13 §4.1에서 648회(#1~#9) 요청 실패 0건으로 검증됐다. 조종 모드는 이 구조를
**주기 1초 → 0.1초, 창 2초 → 0.5초로 줄이고, 보낼 상태를 진행자 대신 vision 판정이 정하게** 바꾼 것이다.
그래서 RPi5용 데모 스크립트가 모인 `services/actuation/scripts/`에 두고 다음을 재사용한다:

- `aihand_picar_demo.PICAR_COMMANDS`(수신호 → 명령 표, web 표와 같은 값)·`_LED_OFF` — 속도만 조종 모드 값으로 덮어쓴다
- `aihand_vision_picar_demo`의 `/latest` 폴링 방식(`POLL_S = 0.1`)

`_send_picar()`는 **재사용하지 않는다** — 500ms 타임아웃 + 1회 재시도라 100ms 주기에 맞지 않는다.

### 3.1 판정 → 동작 (순수 함수 `decide()`로 분리해 표 기반 테스트)

| 입력 | 동작 | 이유 |
|---|---|---|
| vision 연결 실패 · 카메라 멈춤(`/health` `camera.state != running` 또는 `last_frame_age_ms > 300`) | **즉시 stop 전송** | `/latest`에는 시각 필드가 없어 카메라가 멈춰도 마지막 판정이 그대로 남는다. 이걸 못 잡으면 "서행"이 계속 전송된다 |
| 확정된 정지 · 확인_완료 · 주의 | **즉시 stop 전송** (LED는 해당 신호) | 정지 계열은 기다리지 않는다 |
| 확정된 서행 · 좌회전 · 우회전 · 후진 | 주행 명령 전송 | 매 주기 |
| 미판정(`is_reject`: `no_hand`, `below_tau`, `awaiting_consecutive_frames` 등) | **아무것도 보내지 않음** → 0.5초 뒤 워치독 정지 | MediaPipe가 한두 프레임 손을 놓치는 일이 흔하다. 매번 stop을 보내면 차가 덜컹거린다. 워치독 창이 곧 디바운스 |

- `/health`는 500ms마다 읽고 결과를 캐시합니다(`/latest`와 같은 주기로 읽으면 vision 부하만 늘어남).
- 속도는 조종 모드 값으로 덮어씁니다(서행 20, 좌·우·후진 30). web `PICAR_COMMANDS`([state_machine.py:101](../../services/web/backend/state_machine.py))를
  import하지 않는 것은 web 쪽 변경이 브리지에 번지지 않게 하기 위해서입니다. 표가 갈라지지 않도록
  **데모 표와 web 표의 키·LED가 같은지 테스트로 고정**합니다.
- 방향 전환(예: 좌회전 → 우회전)은 vision이 반드시 `awaiting_consecutive_frames`(N=3, 약 75ms)를 거치므로 **정지를 거쳐서** 바뀝니다.
- 종료(Ctrl+C·SIGTERM) 시 stop 1회 전송. `kill -9`로 죽어도 워치독이 0.5초 안에 세웁니다.
- 로그: 주기마다 `시각, predicted_class, is_reject, reason, 보낸 동작, /drive 응답 status, 왕복 ms`를 CSV로 남깁니다(§5 정지 지연 측정용).

### 3.2 정지까지 걸리는 시간 (예상)

| 상황 | 경로 | 예상 |
|---|---|---|
| 정지 계열 신호 | 확정(약 75ms) + 폴링(≤100ms) + `/drive`(20~50ms) | 약 0.2초 |
| 손을 내림 | 전송 중단 → 워치독 | 약 0.5~0.6초 |
| 브리지 사망 · Wi-Fi 두절 | 워치독 | ≤ 0.5초 |
| 카메라 멈춤 | `/health` 캐시(≤500ms) + stop | ≤ 0.6초 |
| **picar 프로세스 `kill -9`·멈춤** | **정지 안 됨** — MCU가 마지막 명령 유지 | **배터리 스위치** |

마지막 행은 08 "picar 비정상 종료" 행과 같은 위험이며 이 계획으로 해결되지 않습니다(소프트웨어 워치독의 한계).

## 4. vision 쪽 의존 (이동혁 확인 요청, 코드 변경 없음)

- 브리지는 `/health`의 `camera.state`·`camera.last_frame_age_ms`를 씁니다. 이 필드 이름이 바뀌면 브리지가 **stop으로 떨어집니다**(안전한 쪽 실패).
- **남는 구멍**: vision `_cognition_loop` 스레드만 죽고 카메라는 살아 있으면 `/latest`가 굳은 채 `/health`는 정상으로 보입니다. [회의안건_KPI측정방법](회의안건_KPI측정방법.md) 안건 1(판정 결과에 캡처 시각 선택 필드 추가)이 채택되면 브리지가 그 필드로 이것까지 잡을 수 있습니다. 채택되지 않으면 이 한계를 운영 규칙(§6)에 적고 갑니다.

| 7. 교육 모드 회귀 | 단위 테스트 전부 통과 + H9 | **필수** |

하나라도 실패하면 10-02에 **no-go** — 조종 모드를 시연에서 빼고 "향후 과제"로 보고한다. 이때 교육 모드는
H9와 단위 테스트로 영향이 없음을 확인한 상태여야 한다. 판정은 송승호, 기준 승인은 이동혁(안건 2).

## 6. 운영 규칙 (시연 시)

1. 두 모드 동시 실행 금지 — 조종 모드 중에는 web 교육을 진행하지 않는다.
2. 배터리 스위치 담당자 1명이 차 옆에 선다. picar 프로세스가 멈추면 워치독도 멈춘다.
3. 주행 구역을 테이프로 표시하고 관람객은 그 밖에 선다.
4. 조종 모드는 교육 흐름 뒤 보너스 시연으로만 쓴다. KPI(01·10 §2.1) 측정 대상이 아니다.
