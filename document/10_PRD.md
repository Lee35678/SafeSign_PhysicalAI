## 1. 제품 개요

**SafeSign**은 산업 현장 안전 수신호를 교육하는 **피지컬 AI 제품**이다. 학습자가 카메라 앞에서 수신호를
따라 하면, 시스템이 이를 인식·채점하고 **AI Hand(로봇 손)**가 수신호를 시범하고, 판정 결과는 **picar(주행 로봇)**와
**micro:bit(LED)** 물리 장치로 피드백한다(AI Hand는 시범 전용 — 판정 뒤에는 움직이지 않는다, 10-02 결정). 인식 결과가 화면 텍스트가 아니라
실제 로봇의 움직임으로 나타난다는 점이 이 제품을 "웹캠 앱"과 구분 짓는 핵심이다.

**폐루프 구조**:

```
AI Hand가 수신호 시범 → 학습자 손동작 → Pi Camera Module 3(Perception) → MediaPipe 랜드마크
  → 정규화 → SVM 분류 + 일치율 산출(Cognition) → 교육 상태머신
  → picar 주행+LED · micro:bit LED 매트릭스(Actuation) → 학습자가 보고 교정
```

> (→ 2026-10-04 정정) 옛 그림의 "AI Hand 재시범/교정"을 뺐다. **AI Hand는 시범 전용**이다 — 판정 뒤 보내는 정답 자세·재시범이 시범과 같은
> 제스처 `G{n}`이라 시범을 마친 손은 판정 뒤 움직이지 않고, 정답·오답은 micro:bit O/X와 picar가 알린다(10-02 결정, [06 §2-3](06_테스트·평가리포트.md), 15 상태 요약).

### 1.1 추진 배경

- ~~산업 현장 작업자마다 안전 수신호 표현이 달라 소통 오류 → 안전사고 위험~~ (→ 2026-10-04 근거 보강)
  **신호는 법정 안전 수단이고, 어긋나면 사고로 이어진다.** 양중기 작업은 사업주가 신호방법을 정하고 운전자·근로자가 따라야 한다(안전보건규칙 제40조).
  타워크레인 양중작업 재해 343건 중 45건(13.0%)이 신호체계 미준수(신호방법 미숙지·신호내용 착각 등)였고(임현무·김승호, 안전문화연구 18호, 2022, 투고본 p.7 표4),
  이동식 크레인 사망재해 연구는 "운전자와 주변 작업자 간의 신호소통상에 의한 사고"를 주요 요인으로 꼽았다(신운철 외, 산업안전보건연구원, 2014, 요약문 iii쪽).
  2023년 크레인류 사망은 23명(사망재해 564명 중 4.1%, 고용노동부 「2023 산업재해 현황분석」 344~345쪽 — 신호 원인은 따로 세지 않음)이고,
  2020년 아산 이동식 크레인 사망 사고에서는 신호체계 미수립이 원인 중 하나로 지적됐다(안전보건공단 중대재해 사례 OPS).
- ~~기존 교육(영상 시청, 인쇄물)은 학습자의 이해도를 객관적으로 측정하기 어려움~~ (→ 2026-10-04 근거 보강)
  **지금 신호수 교육은 이론 위주이고 실기 평가가 없다.** 타워크레인 신호업무는 특별교육 대상(산업안전보건법 시행규칙 별표 5, 39번 — "신호방법 및 요령" 포함)이지만,
  국내 신호수는 자격증 없이 8시간 특별교육만 받으면 되고 교육은 이론 위주라는 지적이 있다(임현무·김승호, 2022, 투고본 p.7·p.9 — 미국·영국·일본은 실기시험).
  그래서 영상 시청·인쇄물만으로는 학습자가 실제로 신호를 할 수 있는지 객관적으로 확인할 수단이 없다고 보았다(팀 문제 정의).
- 로봇 손 시범 + 장치 피드백(micro:bit·picar)으로 **몸으로 반복 연습하는 체험·실습형 교육**과 정량 지표(정답률 등)로 평가하는 체계 구축 필요.
  체험형 방식의 참고 근거: VR 체험교육 이수자 설문에서 이해도 평균이 기존 온라인 교육 4.09 → 4.58(5점 척도) 등 12% 안팎 높았다
  (배필균, 서울과학기술대 석사논문, 2024, 표4.9 p.46~48 — 시기·문항이 다른 설문 평균 비교라 효과 입증은 아님, 이차전지 제조업 1개사).
- **기대 효과(가설, 미검증)**: 수신호 습득 속도·정확도 향상, 소통 오류·사고 감소는 이번에 **측정하지 않았다**. 잰 것은 시스템 성능 KPI(§2.1)뿐이다.
  검증은 향후 과제 — 현장 시범 운영에서 교육 전·후(사전·사후) 시험 비교, 또는 기존 교육 집단과 비교.

> 인용 범위 — 타워크레인 논문은 결론이 "타워크레인 수신호를 무선 신호로 표준화"라서 **신호수 교육 체계의 문제** 근거로만 쓴다. VR 논문은 수신호 교육 효과가 아니라

### 1.2 왜 지금 이 설계인가 (아키텍처 변경 이력)

기존 초안(v1)은 산업/건설/농업/수중 4개 분야, 분야별 5개 후보(총 20개)에서 학습자가 micro:bit 버튼으로
분야를 고른 뒤 그 분야의 5종을 학습하는 구조였다. 이번 개발 착수 시점에 다음과 같이 **단순화·확장**되었다:

- **분야 선택 폐지 → 통합 7종 단일 커리큘럼**: 산업/건설 현장에서 공통으로 쓰이는 크레인 작업표준신호지침
  기반 신호 5종 + 자체 지정 2종(후진, 주의) = 7종으로 통합. 더 이상 분야를 고르지 않는다.
  (→ 2026-10-04 보충: 5종은 표준 동작을 그대로 옮긴 것이 아니라 AI Hand가 표현할 수 있는 **손 모양으로 재해석한 시안**이다 — [02 §4-1](02_설계문서.md).
  학습 데이터는 ASL 지문자 공개 데이터에서 **손 모양만 빌렸다**(ODbL·MIT, 27,735건 — [04 §3-1·§5](04_데이터셋명세서.md)))

  결과를 물리적으로 보여주는 두 번째 Actuation 채널이 추가되었다.

### 1.3 하드웨어 배치 확정 (보유 장비 기준, 2026-09-18 2보드 분리로 정정)

> **왜 보드를 2개로 나눴나**: 처음에는 RPi5 한 대가 카메라와 picar 구동을 모두 겸했다. 그런데 picar가
> 실제로 주행하면 그 위의 카메라도 함께 움직여, **학습자가 판정을 받을 때마다 카메라를 따라 이동해서
> 다시 손을 보여줘야 하는 모순**이 생긴다. 그래서 카메라·AI Hand·micro:bit(학습자 앞 고정)는 **RPi5**,
> picar 구동은 새로 추가한 **Raspberry Pi 4B 8GB**로 분리하고 **Wi-Fi**로 연결했다.

| 장비 | 연결/배치 | 역할 |
| --- | --- | --- |
| Raspberry Pi 5 | 학습자 앞 **고정** 스테이션 | Perception(카메라 추론) + Cognition(분류) + AI Hand/micro:bit 구동 |
| Raspberry Pi Camera Module 3 | CSI (15핀 → 22핀 변환 케이블 → RPi5 CAM/DISP 포트) | 학습자 손 촬영 (범용 USB 웹캠 아님) |
| AI Hand | micro:bit v2 + StartbitV2 확장보드가 서보 구동 (RPi5 GPIO 직결 아님) | 수신호 시범(먼저 보여줌) — ~~오답 시 교정 자세 재시범~~ (→ 2026-10-04 정정: **시범 전용**, 판정 뒤에는 움직이지 않음 — §1 폐루프 주석) |
| micro:bit v2 | **BLE**(Nordic UART)로 RPi5 연결 (2026-09-21 USB 시리얼에서 전환) | AI Hand 제스처 실행, LED 매트릭스 O/X 표시 |
| **Raspberry Pi 4B 8GB (신규)** | **picar 차체에 탑재, 이동** | picar 모터는 I2C 코프로세서(0x16), LED 4개는 GPIO로 구동. RPi5와 **Wi-Fi(HTTP)** 로 통신 |
| picar | RPi4B가 직접 구동 | RPi5의 명령을 Wi-Fi로 받아 물리 동작(§3.2 표) 수행 |

**제품 동작 순서**: ① AI Hand가 수신호를 시범 → ② 학습자가 따라 함 → ③ Pi Camera Module 3로 인식 →
④ 동일 수신호로 판정되면 RPi5가 Wi-Fi로 명령을 보내 **picar가 §3.2 표의 정해진 동작으로 물리적으로
반응**(+micro:bit LED 표시). picar는 학습자 앞에서 벗어나 움직여도 카메라 위치는 그대로 고정된다.

### 3.3 Perception (인식)

- 카메라: **Raspberry Pi Camera Module 3** (CSI, 15핀→22핀 변환 케이블로 RPi5 직결 — 범용 USB 웹캠 아님)
- 입력: 계약값 **1920×1080 @ 60fps (Binned Mode)** (03_인터페이스계약서 §2). 운영 기본값은 **1280×720 @ 30fps**
  (`CAPTURE_SIZE`/`CAPTURE_FPS`, `services/vision/src/perception/capture.py`) — MediaPipe가 내부에서 축소하므로
  1080p 이득이 적고 변환 비용만 늘기 때문. 계약값으로 돌리려면 환경변수로 지정
- MediaPipe **Tasks API `HandLandmarker`**, **`LIVE_STREAM` 모드**(비동기 콜백), `num_hands=1`
  - **왜 `LIVE_STREAM`인가**: 이 제품은 개발 편의보다 실시간 처리 성능이 우선인 피지컬 AI 제품이다.
    `VIDEO`(동기 루프)는 추론이 끝날 때까지 다음 프레임 캡처가 막히지만, `LIVE_STREAM`은 캡처와 추론을
    분리해 카메라 FPS를 더 살릴 수 있다. 대신 프레임 타임스탬프를 단조 증가로 직접 관리하고, 콜백↔상태머신
    간 스레드-세이프 큐/락이 필요하다 (05_모델카드 §3-2).
- `hand_world_landmarks`(실세계 3D, 카메라 거리 변화에 강함) 채택
- 출력: 21 keypoints × (x,y,z) → `landmark_frame` 스키마

*(근거: 05_모델카드 §3, 03_인터페이스계약서 §2~3)*

### 3.4 Cognition (판정)

- **정규화**: 원점이동(손목 기준) → 스케일 정규화(손목-중지MCP 거리) → 회전정렬(손목→중지MCP 축 정렬) →
  좌우손 반전(Left면 x좌표 미러링) → **특징벡터** — `feature_mode` 기본·권장 **joint23**(관절 각도·거리 23차원),
  선택 landmark63(63차원) / landmark63+orient6(69차원). 실제 모드는 모델 번들 metadata가 정함 (05_모델카드)
- **분류기**: MediaPipe Hand Landmarker(동결, 재학습 안 함) + **SVM(RBF 커널)** — **7클래스** 분류 +
  1단계 소속 게이트(7종 어디에도 속하지 않으면 `out_of_distribution` 미판정)
  - 채택 근거: 저차원 특징+소량데이터 조건에서 MLP/랜덤포레스트 대비 과적합 위험 낮고 튜닝 용이
    (→ 2026-10-04 정정, [05 §0·§5-2](05_모델카드.md)) 설계 당시 전제였던 "클래스당 ~300장"과 "좌표 거리 기반 일치율"은 이후 바뀌었다 — 실제 학습 데이터는
    공개 데이터 **27,735건**이고, 일치율은 **목표 수신호 확률 × 100**이다(05 §10-8). 지금 근거는 특징이 23개뿐이라 학습이 수십 초 안에 끝나고,
    RPi5 CPU에서 실시간으로 돌며(판정 26~30fps), 판정 근거(관절 각도·거리)를 설명할 수 있다는 것이다. ~~다른 분류기와의 정량 비교는 하지 않았다(향후 과제, 05 §5-2)~~
    (→ 2026-10-06 정정: 딥러닝(MLP·HandFormer EDL)과는 공개 데이터 학습·검증·시험 분할로 비교했다 — 분류는 같았고 처음 보는 손 거르기는 SVM 방식이 앞서 SVM 유지.
    랜덤포레스트·kNN과는 비교하지 않았다. 분할이 세션 5겹과 다르다 — [05 §5-2](05_모델카드.md))
- **일치율(match_score)**: ~~특징벡터 vs 클래스 템플릿(DB, 없으면 번들 centroid) cosine similarity → 0~100 매핑 (분류 결과와 분리 설계)~~
  (→ 2026-09-30 정정: 학습자 화면의 일치율 = **분류기가 본 목표 수신호 확률 × 100** — vision이 판정 결과에 7종별 확률(`class_probabilities`)을 싣고 web이 고른다.
  템플릿 cosine 값은 7종을 가르지 못해 참고 `match_score`로만 남김 — [05 §10-8](05_모델카드.md))
- **판정 안정화**: 프레임 단위 판정이 아닌 **N프레임 연속 동일 클래스**일 때 확정. 초기 기본값 **N=3**
  (RPi5 CPU 추론 성능 가정 근거, 05_모델카드 §8-0 — ~~실물 도착 후 재검증~~).
  (→ 2026-10-04 정정: **실측으로 확인** — RPi5 판정 속도 평균 29.9fps(06 §1-1)로 가정(10~15fps)보다 빨라 3프레임을 채우는 데 약 0.1초, 판정 지연 P95 0.046초 — [05 §8-0](05_모델카드.md). N=3 유지)
  `LIVE_STREAM` 콜백에서 스레드-세이프 큐(deque)로 최근 클래스를 누적해 판단
- **판정 임계값 τ**: confidence < τ → `is_reject=true`. 초기 기본값 **τ=0.75** (하드웨어 제약 근거,
  05_모델카드 §8-0). 최종 확정 절차 — 검증셋 확률 수집 → τ 그리드 탐색 →
  "정지" 치명오분류 0건 최우선 필터 → 나머지 KPI 동시 만족 → 미판정률 최소값 채택 (05_모델카드 §8-1)
  (→ 2026-10-04 정정: 이 절차는 원안대로 실행하지 못했다 — 팀원 촬영분을 평가 전용으로 써서 검증셋이 없었다(05 §8-1). 대신 최종 210시도로 **τ 민감도**를 확인했다:
  τ 0.50~0.80에서 결과가 같고(정답 95.2%·미판정 4.8%·오분류 0), 0.85부터 제대로 한 손을 막기 시작한다. **τ 0.75 유지** — [05 §8-2](05_모델카드.md). 미판정 10건은 전부 소속 게이트가 냈다)

*(근거: 05_모델카드 §3~§8, 02_설계문서 §2)*

  예측 가능해 재학습 없는 실시간 등록이 성립하지 않음 (2026-09-18 결정)
- 연속 제스처·동적 동작 추적, 음성 안내, 다중 객체/사용자 동시 인식

- 모델 신규 학습(from scratch) — 사전학습 가중치+경량 분류기 재학습까지만
