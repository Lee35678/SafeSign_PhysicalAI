## 1. 설계 단계에서 잡은 것들 (9/17 ~ 9/18)

코드를 쓰기 전에 설계 문서를 읽으면서 **분류기가 성립하지 않는 문제 두 개**를 발견했다.

### 1-1. "서행"과 "후진"이 같은 손모양이었다

| | 당시 정의 | 문제 |
| --- | --- | --- |
| 서행 | 검지 + 중지 펴기 | **두 클래스의 AI Hand 표현이 완전히 동일** |
| 후진 | 검지 + 중지 펴기 | 분류기가 원리적으로 가를 수 없음 |

AI Hand는 손가락을 펴짐(170°)/굽힘(10°) 2단계로만 제어한다. 두 수신호가 같은 손모양이면
**모델을 아무리 잘 만들어도 50%가 한계**다. 데이터를 모으기 전에 잡아서 재작업을 피했다.

→ **대응**: 후진을 "검지만 펴기"로 재설계. (`02_설계문서` §4 참고사항 2)

### 1-2. picar가 움직이면 카메라도 같이 움직인다

초기 구성은 RPi5 한 대가 카메라·AI Hand·picar를 전부 맡는 것이었다. 그런데 picar 위에 카메라가
있으면 **picar가 주행할 때 학습자가 카메라를 따라다녀야 한다.** 교육 제품으로 성립하지 않는다.

→ **대응**: 컴퓨트 보드를 2대로 분리. RPi5(고정 — 카메라·AI Hand·micro:bit) ↔ Wi-Fi ↔
RPi4B(picar 탑재, 이동). 부수적으로 CPU/GPIO 자원 경합도 해소됐다.

### 1-3. 그 외 설계 결정

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| MediaPipe 실행 모드 | `VIDEO` → **`LIVE_STREAM`** | 피지컬 AI는 개발 편의보다 성능이 우선 |
| 수신호 등록 기능 | **범위 제외** | SVM은 고정 클래스만 예측 가능. 재학습 없는 실시간 등록이 원리적으로 불가 |
| 좌표계 | `hand_world_landmarks` | 픽셀이 아닌 실세계 좌표라 카메라 거리에 강함 |

## 2. 라이브러리와 배선에서 터진 것들 (9/19 ~ 9/20)

### 2-1. MediaPipe 1.x가 레거시 API를 삭제했다

모델 카드에 "판정이 느리면 `mediapipe.solutions.hands`로 교체"라는 **폴백 계획**을 적어뒀는데,
실제로 설치해 보니 `ModuleNotFoundError: No module named 'mediapipe.solutions'` 였다.
1.x에서 모듈이 통째로 제거된 것이다.

→ **대응**: 폴백 계획을 폐기하고 유효한 대안 4개로 교체 — 추론 입력 축소 / 프레임 서브샘플링 /
N프레임 축소 / GPU delegate. **문서에 적힌 대책이 실제로 존재하는지 확인해야 한다**는 교훈.

### 2-2. scikit-learn이 `SVC(probability=True)`를 폐기 예고했다

τ(신뢰도 임계값) 판정에는 확률 출력이 필요한데, 쓰려던 방식이 sklearn 1.9에서 deprecated
(1.11 제거 예정)였다.

→ **대응**: `CalibratedClassifierCV(SVC(), method="sigmoid", ensemble=False)`로 교체.
Platt scaling을 별도 단계로 분리하는 표준 방식이다.

### 2-3. Docker에서 모듈을 못 찾았다

`uvicorn src.app:app`으로 띄우면 `ModuleNotFoundError: No module named 'cognition'`.
`src`를 패키지 경로로 쓰면 그 안의 상대 import가 깨진다.

→ **대응**: `uvicorn app:app --app-dir src`로 수정. vision·actuation 양쪽 Dockerfile에 적용.

### 2-4. 환경변수가 모델 설정을 조용히 덮어쓰고 있었다

`docker-compose.yml`이 `CONFIDENCE_THRESHOLD=0.75`를 **항상** 설정하고 있었다. τ는 모델 번들에
함께 저장해서 "모델과 임계값이 따로 놀지 않게" 설계했는데, 이 한 줄이 그 설계를 무력화했다.
재학습으로 τ를 바꿔도 반영되지 않는다.

→ **대응**: `${CONFIDENCE_THRESHOLD:-}` (기본 빈값)로 바꿔 번들 값이 이기게 했다.
**조용히 잘못 동작하는 종류의 버그**라 실행 로그만 봐서는 못 찾는다.

## 3. 데이터를 받고 나서 (9/20 ~ 9/21)

데이터 담당(김지훈)이 공개 데이터셋 3종에서 **수신호 7종 27,735건**을 확보했다. ASL 지문자에서
"의미"가 아니라 **손모양만** 차용한 것이다. 전량이 정규화를 통과했다.

### 3-1. 데이터가 손모양을 바꾸게 만들었다

원하는 손모양의 데이터가 없어서 설계를 데이터에 맞춰야 했다.

| 수신호 | 변경 | 이유 |
| --- | --- | --- |
| 우회전 유도 | 엄지+약지 → **엄지+소지** | 약지 단독 신전은 힘줄 구조상 사람이 어렵고, 데이터도 없음 |
| 확인/완료 | 따봉 → **주먹** | 데이터 확보 불가 |

→ 이 변경이 나중에 **가장 큰 혼동 쌍**을 만들었다(§3-3). 당시에는 최선의 선택이었고,
대가를 문서에 명시해 두었다.

### 3-2. 🔴 정답률 98.81%가 허수였다

첫 학습 결과가 **98.81%** 였다. 너무 좋아서 의심했고, 파일명을 조사했다.

- `color_18_0002 (2).png` 같은 **복사본**이 섞여 있었다
- 같은 사람이 연달아 찍은 컷들이 **805개 세션**에 묶여 있었고, 전체의 97.7%가 여기 속했다
- 표본의 69.8%는 **유사도 0.999 이상인 쌍둥이**를 갖고 있었다

무작위로 나누면 **사실상 같은 사진을 학습하고 그 사진으로 시험**하는 셈이었다.

무작위 5겹 98.81% → **같은 세션은 한쪽에만 77.57%**, **−21.2%p.** 실제 실력은 77.57%였다
(분할 방식별 표는 [05 §4](05_모델카드.md)).

→ **대응**: 학습 스크립트의 기본 분할을 **세션 단위 GroupKFold**로 고정했다. 파일명에서
복사본 표시·연속 촬영 번호를 떼어 세션 키를 만든다. 무작위 분할 점수는 보고에 쓰지 않기로 했다.

> **교훈**: 좋은 숫자가 나오면 먼저 의심한다. 평가 설계가 틀리면 그 위의 모든 판단이 틀린다.

### 3-3. 혼동이 한 쌍에 몰려 있었다

| 혼동 | 건수 |
| --- | --- |
| 주의(소지만) ↔ 우회전 유도(엄지+소지) | **2,530건** |
| 확인 완료(주먹) → 주의 | 913건 |
| 후진(검지만) → 서행(검지+중지) | 853건 |

**전체 오분류의 41%가 한 쌍**이었다. 엄지 하나 차이이고, 클래스 중심 코사인 유사도 0.979로
7종 중 가장 가까웠다. §3-1의 손모양 변경이 만든 결과다.

### 3-4. 손모양을 바꿔서 풀 수 있는가 — 전수 계산

"우회전 유도를 다른 손모양으로 바꾸면 되지 않나"가 자연스러운 발상이었다. 그런데 **후보를 감이
아니라 계산으로** 고르기로 하고, 손가락 5개 이진 조합 **32가지를 전부** 계산했다.

결과는 **바꿀 자리가 없다**였다.

- 손가락 **1개 차이는 74%가 합격선 미달**. 2개 이상 달라야 안전하다
- 기존 6종이 32자리 중 **24자리를 막아**(6개 사용 + 이웃 18개) 남는 자리가 8개뿐
- 그 8자리는 전부 약지를 쓰거나 검지를 접는 부자연스러운 모양
- **7종 전체를 재설계해도** 최선이 0.9650인데, 클래스 내부 퍼짐(후진 하위 5% 0.9681)이 그보다 크다

| 방안 | 최악 쌍 | 개선 |
| --- | --- | --- |
| 현재 7종 | 0.9732 | — |
| 1개만 교체 | 0.9739 | **없음** |
| 7종 전체 재설계 | 0.9650 | +0.014 (데이터 전부 재수집 필요) |

1개 교체가 **후보를 뭘로 골라도 같은 값**이었다. 6종을 고정하면 그 6종끼리의 최악 쌍이 바닥이
되어, 병목만 옮겨간다.

→ **대응**: 손모양 재설계를 포기했다. 대신 회의에서 **손 방향(회전) 축 도입**을 채택했다.
([archive/회의자료_안건3_손모양거리계산표](archive/회의자료_안건3_손모양거리계산표.md) — 팀 회의용으로 전수 계산표를 따로 만들었다)

### 3-5. Colab이 필요 없었다

처음에는 "로컬 GPU 한계"를 이유로 Colab 학습을 전제했다. 실제로 재보니 **SVM은 GPU를 쓰지
않고**, 전체 27,735건 학습이 **16초**였다.

→ **대응**: 로컬 학습(`training/train_svm.py`)을 기본 경로로 바꿨다. 학습·추론이 같은 머신이라
scikit-learn 버전 불일치 위험도 크게 줄었다. Colab 노트북은 대체 경로로 남겼다.

> **교훈**: 근거 없이 정한 전제는 실측 한 번으로 뒤집힌다. "GPU 한계"는 확인하지 않은 가정이었다.

## 4. 회의에서 결정한 것 (9/21)

혼자 정할 수 없는 사안이 쌓여 회의 자료를 만들었다. 안건마다 **선택지 · 근거 수치 · 권고 ·
결론이 안 날 때의 잠정치**를 붙였다.

| 안건 | 결정 |
| --- | --- |
| negative 클래스 | **7클래스만 학습**. "7종 아닌 자세"는 종류가 무한해 학습 불가. τ 미달을 미판정으로 처리 |
| 수신호 손모양 | **손 방향 축 도입** (재설계는 §3-4대로 불가) |
| 자체 촬영 | 팀원 촬영 — KPI 측정의 유일한 경로 |
| 치명 오분류 KPI | 정지 전용 τ 상향 검토, 자체 촬영 후 재측정 |

**negative 0건 문제**: 공개 데이터의 `nothing`은 손이 아예 없는 배경이라 랜드마크가 나오지
않았다. "손은 있는데 7종이 아닌 자세"는 한 건도 없었다.

## 5. 실사용에서 터진 것 — 모르는 손모양 (9/22)

웹캠으로 직접 써 보니 **"엄지만 폈는데 우회전 유도로 인식"** 되는 현상이 보고됐다.

### 5-1. τ는 원리적으로 이걸 막을 수 없다

한 클래스를 학습에서 통째로 빼고 그 클래스를 "모르는 자세"로 넣어 측정했다(open-set 표준 프로토콜).

결과: τ가 거른 비율은 **평균 16.7%**(주의는 0.1%)뿐이고, **77.3%가 confidence ≥ 0.90으로 오판**됐다
(클래스별 표는 [05 §3-7](05_모델카드.md)).

**원인은 구조다.** 분류기의 확률은 7종 안에서 정규화된다(합 = 1). 아무리 낯선 입력이 와도
"그나마 가장 비슷한" 클래스가 높은 값을 받는다. **τ는 "얼마나 확신하나"를 잴 뿐 "애초에 7종에
속하나"를 재지 못한다.** τ 값을 조정해서 풀 문제가 아니었다.

점수 함수별 분리 능력(AUC)을 비교하니 **클래스 중심까지의 거리 0.932**가 가장 좋았고, τ가 쓰는
**confidence는 0.594**(거의 무작위)였다 (전체 비교표 [05 §3-7](05_모델카드.md)).

### 5-2. 대응 — 소속 게이트

분류 결과가 나온 뒤 **"이 손모양이 그 클래스에 속하기는 하는가"** 를 따로 확인하는 단계를 넣었다.
예측 클래스의 중심과의 코사인 유사도가 **클래스별 임계값**보다 낮으면 미판정으로 보낸다
(`reason="out_of_distribution"`).

임계값을 클래스마다 다르게 잡은 이유: 절대값 범위가 클래스별로 달라서(주의의 이상치 중앙값
0.9746 > 정지의 정상 하위 5% 0.9513) **전역 임계값 하나로는 쓸 수 없었다.**

**전부 우리 데이터로 직접 측정**했다.

| 전략 | 정답률 | Macro F1 | 최대 혼동 쌍 | 채택 |
| --- | --- | --- | --- | --- |
| (기준) 좌표 63차원 | 77.57% | 0.784 | 68.0% | — |
| ① 계층 분류(병합+전문가) | 79.11% | 0.797 | 72.6% | ✗ |

¹ 이 표는 정지 가중 없음(×1) 조건. 현재 기본(`--critical-weight 10`)으로는 88.68% / 0.879 — [05 §3-5](05_모델카드.md).

### 6-1. 좌표 대신 관절 관계량

canonical 좌표 63차원에는 **"엄지가 펴졌나"가 암묵적으로만** 들어 있다. 손가락 하나 차이가 21개
점 중 12개 성분에 조금씩 흩어져서, RBF 커널이 그 방향을 잘 잡지 못한다.

관절 각도·거리로 바꾸면 그것이 **한 축**이 된다. 23차원 = 굽힘 5 + 폄 방향 5 + 손끝~손목 거리 5 +
인접 손끝 간격 4 + **엄지끝~나머지 손끝 거리 4**("엄지 하나 차이"를 직접 겨냥) — 구성표는 [05 §3-5](05_모델카드.md).

**+11.1%p, 최대 혼동 쌍은 +22%p.** 차원을 63 → 23으로 **줄이면서** 성능이 올랐다.

특히 중요한 것: **둘을 합친 86차원(82.99%)이 관절 특징만 쓴 23차원(88.71%)보다 낮았다.**
원좌표가 잡음으로 작용한다. 더하는 게 아니라 **대체**해야 했다.

### 6-2. 적용할 수 없었던 전략

**② 마진 손실(ArcFace·contrastive·MV-Softmax)** — 자료에는 "기존 파이프라인에 얹기 쉬움"이라고
되어 있었으나, 이는 **CNN 기준** 서술이다. ArcFace는 *softmax 층을 바꾸는* 기법이라 임베딩
신경망과 역전파가 전제인데, 우리는 SVM이라 둘 다 없다. 채택하려면 SVM을 MLP로 교체해야 하고,
그건 설계 결정을 되돌리는 일이다. 같은 목적의 SVM 대응물인 NCA 거리 학습으로 대신 측정했다(82.37%).

**⑤ 자기지도 학습** — 같은 이유로 제외.

### 6-3. ① 계층 구조가 무력화됐다

좌표 63차원에서는 계층 구조가 **+3.48%p**였는데, 관절 특징 위에서는 **−1.04%p**였다.
쌍 정답률이 이미 90%라 병합으로 잃는 것이 전문가로 얻는 것보다 컸다.

> **교훈**: 대책은 서로 독립이 아니다. 근본 원인(특징)을 고치면 증상 대책(계층 구조)은
> 필요 없어지고, 오히려 해가 된다. **원인부터 고친다.**

## 7. 🔴 측정 방법이 결과를 뒤집은 사건 (9/22)

특징을 바꾼 뒤 웹캠으로 다시 시험했더니 **"오판정이 오히려 더 심해진 것 같다"** 는 보고가 왔다.

### 7-1. 로그를 남겨 원인을 찾기로 했다

감이 아니라 데이터로 판단하기 위해, `webcam_check.py`에 진단 로그 기능을 넣었다. 숫자키로
"지금 하려는 동작"(정답 라벨)을 찍고, **원본 랜드마크 21개를 함께 기록**하도록 했다 —
나중에 다른 특징 모드로 다시 계산해 비교할 수 있게.

4,800프레임을 받았고, 정답률은 **28.2%** 였다. 공개 데이터 88.68%와 60%p 차이다.

### 7-2. 그런데 28.2%가 틀린 숫자였다

먼저 **"바꾼 게 원인인가"** 부터 확인했다. 같은 프레임을 이전 모델로 재판정하니 **26.0%** 였다.
둘 다 나빴으므로 특징 교체는 범인이 아니었다.

다음으로 **"측정이 맞나"** 를 봤다. 로그에서 손가락 상태를 복원했더니:

| 구간 | 누른 라벨 | 실제 손모양 |
| --- | --- | --- |
| 15 | 정지 | 엄지+검지 폄 → **좌회전 유도** |
| 17 | 좌회전 유도 | 전부 접힘 → **주먹** |
| 11 | 후진 | 엄지+검지 폄 |

결정적 증거: **"정지"로 라벨링된 두 구간의 특징 중심 유사도가 0.54**였다. 같은 동작이라면
나올 수 없는 값이다.

**원인은 라벨링 방식이었다.** 숫자키를 누르면 다음 키를 누를 때까지 **수백 프레임**이 그 라벨로
기록된다. 그 사이 손을 만들기까지의 전환, 자세가 풀리는 순간, 다음 동작으로 넘어가는 프레임이
전부 섞였다. **내가 만든 도구의 설계 결함이었다.**

### 7-3. 같은 손을 제대로 찍으니 100%였다

`record_dataset.py`(2초 카운트다운 후 3프레임만 촬영)로 같은 사람이 다시 찍었다.

**105프레임 전부 정답. 최저 confidence 0.866.**

### 7-4. 이 과정에서 내가 틀린 진단을 했다

로그 분석 중 **"소지가 안 펴진다"** 고 진단했다. 학습 데이터의 소지 폄 지표가 0.87~0.89인데
로그에서는 0.03~0.06이었기 때문이다. 손모양 설계까지 다시 봐야 한다고 보고했다.

깨끗한 데이터로 재보니 **0.92~0.96으로 오히려 학습 데이터보다 잘 펴졌다.** 23개 특징 전부
0.5σ 이내로 학습 데이터와 일치했다. **전환 프레임을 보고 내린 오진이었다.**

> **교훈**: 측정 도구를 먼저 검증한다. 하마터면 멀쩡한 모델을 되돌리고, 있지도 않은 문제를
> 해결하려고 손모양 설계를 다시 열 뻔했다. **이상한 숫자가 나오면 모델보다 측정을 먼저 의심한다.**

## 8. KPI 실측 (9/22)

### 8-1. 게이트 동작점 재조정

애매한 자세 24건과 정상 7종 105건을 **같은 사람·같은 카메라**로 확보하고 나서야 게이트를
제대로 조정할 수 있었다. 그전까지는 "학습에서 뺀 클래스"를 대용품으로 썼다.

p1(이전 기본)은 미지 자세 차단 37.5%에 그쳤고, **p10에서 차단 75.0% / 정상 오거부 2.9%**, p12부터
오거부가 10.5%로 급격히 오른다. **p10이 명확한 최적점**이었다 (동작점 표는 [05 §3-7](05_모델카드.md)).

### 8-2. 최종 KPI

촬영자 2명(JH·me01), 7종 × 10·5테이크 = **105시도 315프레임**. 집계 단위는 **테이크**다 —
KPI의 "전체 시도 수"는 프레임이 아니라 한 번의 시도이고, 운영에서도 N=3 연속 프레임이 같아야
확정하기 때문이다.

결과는 §0 요약표와 같다(5개 지표 전부 달성, 🟡 잠정). 촬영자별(JH 95.7% · me01 100%)·손 방향별
(정면 97.6% / 좌 97.1% / 우 96.4%) 상세는 [05 §7-3](05_모델카드.md).

미판정 3건은 전부 소속 게이트가 막은 것이고, **오분류는 0건**이다. 교육 제품에서
"틀린 답을 자신 있게 주는" 사고가 없었다는 점이 가장 중요하다.

> → 2026-09-30: 이 절은 9/22 잠정치다. **최종 KPI(팀원 3명 210시도, 공식 3연속)는 §13-8**.

### 8-3. 안 본 데이터가 왜 더 높게 나왔나

공개 데이터에서는 88.7%인데 자체 촬영에서는 97.1%가 나왔다. **보통은 반대여야 한다** —
학습에 쓰지 않은 데이터가 더 어려워야 정상이다. 그래서 세 가지를 확인했다.

**① 자체 촬영분이 학습에 섞였나 — 아니다.** 학습 스크립트는 `datasets/processed`(공개 데이터)만
읽는다. 자체 촬영분은 `self_recorded`로 폴더가 분리돼 있다. 번들 메타데이터의 학습 건수
**27,735건**이 공개 데이터 수와 정확히 일치한다 — 섞였다면 늘었을 것이다.

**② 집계 단위가 유리했나 — 일부만.** 자체 촬영은 테이크(3프레임) 다수결로 집계한다.
프레임 단위로도 재봤다.

| 조건 | 정답률 |
| --- | --- |
| 자체 촬영 — 테이크 단위 | 97.1% |
| 자체 촬영 — **프레임 단위** | **95.6%** |
| 공개 데이터 — 프레임 단위 | 88.7% |

다수결 덕은 **1.5%p**뿐이고, 같은 기준으로 놓아도 여전히 **+6.9%p** 높다.

**③ 데이터 난이도가 다르다 — 이게 진짜 이유.** 같은 클래스 안에서 샘플이 얼마나 뭉쳐 있는지
쟀다. **하위 5%**(가장 어정쩡한 샘플)를 보면 차이가 확연하다.

| 클래스 | 공개 하위5% | 자체 하위5% | 차이 |

공개 데이터의 후진은 하위 5%가 0.8462다 — "이게 정말 후진이 맞나" 싶은 샘플이 5% 넘게 섞여

| | 공개 데이터 | 자체 촬영 |
| --- | --- | --- |
| 촬영자 | 수천 명, 제각각 | 2명, 일관된 수행 |

**세 번째 줄이 결정적이다.** 공개 데이터는 미국 수화 알파벳 사진에서 **손모양만 빌려온 것**이다.
'Z'를 만들던 사람의 손을 "후진"이라고 라벨한 셈이고, 그 사람은 후진 수신호를 하려던 게 아니라
글자를 쓰던 중이었다.

> **두 숫자 모두 맞고, 용도가 다르다.** 88.7%는 **어떤 방법이 나은지 비교**하는 데 쓴다
> (27,735건이라 비교가 안정적이다). 97.1%는 **실제 쓸 때 얼마나 맞나**를 재는 데 쓴다 —
> 우리 제품은 카메라 1대 고정에 학습자가 안내를 보고 수행하는 환경이라 이쪽이 실사용에 가깝다.
> 다만 **97.1%를 과신하면 안 된다**(§9-1, §9-4).

### 8-4. τ는 실제로 한 번도 작동하지 않았다

자체 촬영 데이터로 거름망별 차단 수를 세어봤다.

| | 정상 7종 315프레임 | 애매한 자세 48프레임 |
| --- | --- | --- |
| ① 게이트가 차단 | 14 | **39** |
| ② τ<0.75 가 차단 | **0** | **0** |
| 통과 | 301 (95.6%) | 9 (18.8%) |

**τ가 걸러낸 것이 0개다.** τ를 0.50에서 0.85까지 움직여도 결과가 완전히 동일하다 —
또렷하게 수행한 손은 분류기가 0.85 이상으로 확신하기 때문이다. 0.90부터 작동하기 시작하는데,
그때 걸러내는 것은 애매한 자세가 아니라 **제대로 한 손**이다(미판정률 4.4% → 16.2%,
애매한 자세 차단률은 81.2% 그대로).

> 이것이 §5-1에서 확인한 "τ는 7종 밖을 판정할 수 없다"의 실사용 증거다. τ가 쓸모없다는 뜻은
> 아니다 — 학습자가 **두 수신호 중간쯤 되는 어정쩡한 자세**를 할 때를 위한 장치이고, 지금
> 데이터에는 그런 입력이 없었을 뿐이다. 초보 학습자 데이터가 들어오면 그때 작동할 것이다.

| **joint23 (현재)** | **97.1%** | **0.0%** | **2.9%** |
| landmark63 (이전) | 92.4% | 1.9% | **5.7%** |

이전 특징이었다면 **미판정률 5.7%로 KPI 미달**이었다.

### 9-1. 통계적으로는 "확정"이 아니다

내려간다. 한 사람이 15시도만 더 찍으면 된다.
(→ 2026-09-27 정정: Wilson 기준으로는 120시도 상한이 3.1%라 부족하고 **125시도(2.98%)**, 즉 20시도가 더
필요하다. 외부인 ext03 70테이크가 2026-09-23에 촬영돼 있어 재계산만 하면 된다 — [05 §7-3](05_모델카드.md))
(→ 2026-09-30 **해소**: 최종 210시도에서 오분류 0건 → 상한 **1.8%**로 목표 3%를 통계적으로 확정했다. 대신 미판정률 상한 8.5%가
새 한계로 남는다 — §13-8)

### 9-2. 7종이 아닌 자세의 19%가 여전히 샌다

16테이크 중 3건이 정지로 판정됐다. 새어나간 자세들은 **중심 유사도가 0.99 수준** — 손가락
4개를 편 자세처럼 기하학적으로 정지와 거의 같은 입력이다. **거리 기반 게이트로는 원리적으로
가를 수 없다.** 임계를 올리면 정상 자세도 함께 튕긴다.

→ 넘으려면 "무엇이 7종이 아닌가"를 학습해야 한다. negative 데이터를 모아 8클래스로 가는
방안(회의 안건 2 B안)을 검토 대상으로 남겨뒀다.

### 9-3. τ는 여전히 잠정값이다

공개 데이터에서는 KPI를 모두 만족하는 τ가 없어 기본값 0.75를 쓰고 있다. 자체 촬영 표본이
커지면 §8-1 같은 방식으로 재결정할 수 있다.

### 9-4. 촬영자가 팀 내부다

JH·me01 모두 수신호를 아는 사람이다. 실제 초보 학습자보다 정확하게 수행했을 가능성이 있다.
외부인 데이터가 있으면 더 보수적인 수치가 나올 것이다.

## 10. 최종 구조

```
Pi Camera Module 3 (1080p@60fps, CSI)
   │
   ├─ MediaPipe HandLandmarker (LIVE_STREAM)      21개 관절 좌표
   │
   ├─ 정규화                                        좌우손 통일 → 원점 이동 → 스케일 → 회전 정렬

   ├─ 특징 추출                                     관절 각도·거리 23차원 (joint23)

   ├─ [2] τ = 0.75      "확신하는가"                 미달 → negative
   ├─ [3] N = 3프레임    "흔들리지 않는가"            연속 동일 판정일 때만 확정
```

### 13-4. 판정 규칙 결정 — 3연속 (9/29 회의, KPI 안건 7)

오프라인 KPI는 한 테이크 3프레임을 최빈값으로 판정하고 있었는데, 운영은 **3연속 같은 판정**이다. 같은 175테이크로 비교하니
**갈린 테이크 7개**, 전부 "최빈값 정답 → 3연속 미판정"(게이트가 1~2장 막음)이었고 오분류·치명은 같았다. 그런데 이것만으로
**팀원 미판정률이 2.9% → 6.7%로 목표(≤5%)를 넘었다.**

- **결정: 공식 = 3연속, 최빈값 = 참고치.** 둘 다 운영과 딱 같지는 않다(촬영 도구는 0.15초 간격 3장, 운영은 26fps로 확정될 때까지 본다).
  3연속은 하한, 최빈값은 상한으로 읽는다.
- `evaluate_kpi.py` — 두 규칙을 나란히 출력, 결과 JSON(`--out`), 치명 오분류 Wilson 상한, 비교 모델은 `--compare`일 때만
  (**KPI 데이터로 여러 모델을 재보고 고르면 그것도 오염**).

### 13-7. 🔴 일치율 재정의 (9/30) — 두 번 고쳤다

**증상** (localhost에서 실제 손으로 시험): 확인_완료·후진·주의가 **정답인데 일치율 55~69%**. 판정 확신도는 0.92~0.99였다.

**1차 원인과 수정 — 환산 구간.** 일치율은 "예측 클래스 대표 손과의 코사인 유사도"를 0~100으로 옮긴 값인데, 구간이 7종 공통
(0.922~0.998) 하나였다. 접힌 손가락이 많은 손모양은 사람마다 굽힘이 달라 원래 더 퍼져 있어서, 공개 데이터의 **정상 손조차**
확인_완료 중앙값 78·하위 10% 52점이었다. 클래스별 구간으로 바꿨다(5~95 퍼센타일은 좁은 클래스를 깎아서 1~95).

> **내 실수.** 모델 파일(환산표)만 자동으로 다시 읽히고 **코드는 재시작해야 바뀌는데**, 재시작 없이 "반영됐다"고 말했다.
> 다음 시험의 55점은 옛 계산이었다(새 방식으로 역산하면 게이트를 못 넘는 값이라 모순으로 확인).

**2차 — 사용자 지적: "일부러 다른 수신호를 보여 줬는데 85%가 뜬다."** 원인은 두 가지였다.

1. **비교 대상** — 목표가 아니라 **예측된(틀린) 수신호**와 비교하고 있었다. 틀린 동작도 "그 틀린 동작과는 잘 맞는다"로 높게 나왔다.
2. **유사도 자체가 7종을 가르지 못한다** — 대표 손끼리도 주의↔우회전 0.958, 후진↔좌회전 0.946. 모델은 이 값으로 판별하지 않는다
   (게이트 보조용일 뿐이고, 판별은 SVM 확률이 한다).

"유사도 × 100"도 검토했으나 목표 기준으로 바꿔도 틀린 동작이 평균 64~74점, 헷갈리는 짝은 93~95점이었다. 공개 데이터로 비교:

| 목표 기준 방식 | 제대로 한 손 (중앙값) | 다른 수신호를 한 손 (중앙값 · 최악) |
| --- | --- | --- |
| A. 유사도 × 100 | 98~100 | 64~74 · 최악 95 |
| B. 구분 환산 (0점 = 다른 수신호의 p95) | 65~99 | 0 · 0 |
| **C. 목표 수신호 확률 × 100 (채택)** | **85~97** | **0~1 · 최악 14** |

**결정: 일치율 = 분류기가 본 목표 수신호 확률 × 100** (판정에 쓰는 바로 그 값, [05 §10-8](05_모델카드.md)). vision이 7종 확률
(`class_probabilities`)을 싣고 web이 목표 값을 고른다. 확인: 주의 손 → 목표 주의 92점 / 목표 우회전 **8점**(예전 99점).
정답 기준(τ 0.75)과 같은 척도라 **75점 이상이어야 정답**이다. 스키마 선택 필드 추가라 팀 확인이 남았다.

### 13-9. 화면 정리와 회사 사이트 (9/30)

- **교육장 화면을 산업 제어실(HMI) 기준으로** — 평상시 무채색, 색은 상태에만. 일치율 막대에 **판정 기준 75% 눈금**을 넣어
  "몇 %면 되는가"를 학습자가 볼 수 있게 했다(τ 0.75와 같은 값). 수료증은 성명·사원 코드·수료 일시·번호를 넣어 정식 디자인으로.
- **회사 사이트(`services/portal`)** — 회원가입이 교육장 RPi5에서만 돼서, RPi5 없이 가입하고 수료증을 다시 받는 사이트를 따로 만들었다.
  같은 회원 DB, 스키마 변경 없음. 교육장 화면은 "화면 1대 = 학습자 1명"이라 로그인 상태를 전역으로 두지만, 회사 사이트는 여러 명이 동시에 쓰므로
  사람마다 서명된 쿠키로 바꿨다 — 같은 저장소 코드를 쓰되 **세션 모델은 쓰는 환경에 맞춰 다르게** 했다. 상세는 [19_회사웹사이트](19_회사웹사이트.md).
- **SQL을 처음으로 실제 Postgres에서 돌렸다** — 그전까지 가짜 Supabase(MockTransport)로만 확인했다. 내장형 PostgreSQL 16에서 업그레이드·재실행·
  저장·권한까지 통과한 뒤 팀 Supabase에 연결했다.

## 14. 향후 과제 — 제품화 구조 (엣지·클라우드 분리)

> 지금 구조는 **교육장 스테이션 한 대**(RPi5가 판정·장치 제어·웹 화면까지 맡음)다. 실제 제품으로 판다면 웹 서버를 기기에서
> 떼어 내는 것이 일반적이다. 제출(10/08)까지는 지금 구조를 유지하고, 결과보고서에 확장 방향으로 적는다.

### 14-1. 구조 — 무엇을 어디에 두나

```
[교육장 RPi5 — 엣지]                              [클라우드 — 항상 켜져 있음]
카메라 → MediaPipe·SVM 판정                        웹페이지 (정적 호스팅)
상태머신 + AI Hand(BLE)·picar(Wi-Fi) 제어   ──▶    실시간 채널 (Supabase Realtime 또는 MQTT)
영상 인코딩 → 송신                          ──▶    미디어 서버 (WebRTC — mediamtx·LiveKit 등)
결과 저장                                   ──▶    DB (Supabase — 이미 구현, §13-6)
                                                  ↑ 브라우저는 클라우드에만 접속
```

- **판정과 장치 제어는 반드시 엣지에 남긴다.** 판정 지연 ≤1초·물리 피드백 ≤2초 KPI가 클라우드 왕복에 흔들리고, picar 정지 같은
  안전 동작이 인터넷 상태에 좌우되면 안 된다. **KPI가 구조를 정한다** — 이 요구가 "엣지에서 판정·제어"라는 구조를 만든다.
- 클라우드로 옮기는 것은 **화면·기록·모니터링**이다.
- 참고: 산업용 엣지 기기에서 컨테이너를 돌리는 것 자체는 흔하다(AWS Greengrass·Azure IoT Edge 등). 피하는 것은 기기가 사용자용
  웹 서버까지 떠안는 구조다. (현재 실물 실행도 Docker가 아니라 네이티브다 — 16 §2.4.)

### 14-2. 방법

1. **판정·상태 이벤트** — RPi5가 판정 결과·상태를 Supabase Realtime(또는 MQTT) 채널로 발행하고 웹이 구독한다. 화면의 확인 버튼은
   반대로 채널을 거쳐 RPi5로 온다(micro:bit 버튼 A는 지금처럼 로컬).
2. **영상** — WebRTC로 미디어 서버에 올리고 브라우저가 받는다(지연 약 0.2~0.5초). HLS는 지연이 수 초라 따라 하기 교육에 맞지 않는다.
3. **웹** — 정적 사이트로 올리고, 로그인은 브라우저가 Supabase Auth를 직접 쓴다(그때는 RLS 정책으로 권한을 막는다).
4. **기기 인증·보안** — 교육장마다 기기 토큰, 모든 통신 TLS, 기기는 바깥으로 **보내기만** 한다(들어오는 접속을 받지 않음).

### 14-3. 좋은 점과 나쁜 점

| 좋은 점 | 나쁜 점 |
| --- | --- |
| 여러 교육장을 한곳에서 관리 — 상태·회원 기록·통계를 중앙에서 보고, 화면 업데이트는 기기를 안 건드리고 한 번에 | **인터넷이 필수** — 교육장 인터넷은 보장되지 않는다(07 네트워크설정법). 끊기면 화면이 멈추므로 로컬 대체 화면이 필요 |
| 기기 부담 감소 — 쿨러 없이 스로틀링이 난 RPi5에서 웹 서버 부담이 빠진다 | **지연 증가** — 영상·이벤트가 클라우드를 한 번 돌아온다 |
| 보안 경계가 분명 — 기기가 외부 접속을 받지 않는다 | **RPi5에는 H.264 하드웨어 인코더가 없다**(RPi4에는 있었다) — WebRTC용 인코딩이 CPU를 MediaPipe와 나눠 쓴다. 해상도를 낮추고 실측 필요 |
| 원격 모니터링 — 교육 담당자가 여러 스테이션을 동시에 본다 | **개인정보** — 학습자 얼굴이 나오는 영상이 교육장 밖으로 나간다. 동의·보관 금지·암호화 등 법적 검토 필요(지금은 영상이 기기 밖으로 안 나간다) |
| | **비용·복잡도** — 미디어 서버, 방화벽 우회(TURN), 스테이션당 약 1~2Mbps 대역폭, 재연결 처리 |

### 14-4. 제품화 시 추가로 재야 할 KPI

지금 KPI(판정 성능 5개·지연 2개)는 **내놓는 구조에서** 잰다. 구조가 바뀌면 이것이 더해진다.

| 지표 | 예 |
| --- | --- |
| 네트워크를 포함한 지연 | 손 정지 → 원격 화면 반영, 영상 glass-to-glass 지연 |
| 가용성 | 인터넷 단절 중 동작 범위, 복구 시간, 대기열 전송 완료 시간 |
| 장시간 안정성 | 연속 가동 중 오류·재연결·열 스로틀링·판정 속도 저하 |

산업식 측정에서 지금도 할 수 있는 것: 측정 프로토콜을 시험 전에 동결, 처음 보는 사람으로 최종 측정, 휴대폰 슬로모션(240fps)으로
"손이 멈춘 순간 → 반응"을 20건쯤 직접 세어 로그 값과 비교, 쿨러 장착 후 연속 가동 시험.

### 14-5. 단계적 로드맵 (제안)

1. **지금(제출까지)** — 현 구조 유지. 결과만 Supabase로 나간다(이미 구현).
2. **다음** — 판정·상태 이벤트를 실시간 채널로 발행해 원격 모니터링 화면을 붙인다(영상 없이 — 개인정보·대역폭 부담이 없다).
3. **그다음** — 필요할 때만 저해상도 영상을 원격으로 보낸다(동의·보관 정책을 먼저 정한다).
4. **현장 설치 자동화** — IP 대신 이름(mDNS `safesign-rpi5.local`)으로 접속하고, 안 되는 망에서는 RPi5가 서브넷을 훑어 picar를 찾는다
   (현장마다 IP를 찾던 설치 시간을 줄인다).
