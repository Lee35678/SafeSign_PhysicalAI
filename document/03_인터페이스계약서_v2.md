## 1. 시스템 구성 요소

```
[Pi Camera Module 3] → [Perception: MediaPipe (LIVE_STREAM)] → [Cognition: 분류기] → [교육 상태머신] → [Actuation: AI Hand / picar / micro:bit]
                                                ↕
                                          [수신호 DB]
```

## 2. 카메라 → Perception

> **확정**: **Raspberry Pi Camera Module 3**를 CSI로 RPi5에 직결한다 (15핀 카메라 케이블 →
> 22핀 변환 케이블 → RPi5 CAM/DISP 포트). 온보드 자체 분류 AI 카메라(WonderCam류)나 범용 USB 웹캠은
> 채택하지 않는다 — 리스크 레지스터의 "카메라가 랜드마크 좌표를 못 내줌" 항목은 이 결정으로 해결됨.
> 

| 항목 | 스펙 |
| --- | --- |
| 장치 | Raspberry Pi Camera Module 3 (CSI, 15핀→22핀 변환 케이블) |
| 입력 | RGB 프레임 (해상도/FPS: *확정 필요*) |
| 출력 | 21 keypoints × (x, y, z) |
| MediaPipe 실행 모드 | `LIVE_STREAM` (05_모델카드_v3 §3-2 — 실시간 성능 우선, `VIDEO` 동기 루프 대비 캡처-추론 분리) |

> **해상도/FPS는 어떻게 정하나요?** Camera Module 3 지원 모드 확인 → MediaPipe가 실시간(1초에 여러 프레임)으로 처리 가능한 해상도로 낮춰가며 테스트(보통 640×480 부근에서 시작) → 판정 지연(P95 ≤ 1.0초) 목표를 만족하는 최소 해상도로 확정. 확정 후 이 표를 바로 채우세요.
> 

## 3. Perception → Cognition (랜드마크 스키마)

```json
{
  "timestamp": "ISO8601",
  "hand_detected": true,
  "landmarks": [
    {"id": 0, "x": 0.0, "y": 0.0, "z": 0.0},
    "... (21개)"
  ]
}
```

## 4. Cognition → 교육 상태머신 (판정 결과 스키마)

```json
{
  "predicted_class": "string (수신호 이름 또는 'negative')",
  "confidence": 0.0,
  "match_score": 0,
  "is_reject": false,
  "latency_ms": 0
}
```

- `match_score`: 일치율(유사도) 0~100 점수 (계획서 KPI 항목)
- `is_reject`: 신뢰도 임계값 미달 시 true (미판정률 계산에 사용)
- 판정 지연(P95 ≤ 1.0초) 측정 기준점: 손 정지 시점 → 이 스키마 확정 시점

## 5. 교육 상태머신 → Actuation

### 5-1. AI Hand 제어 명령 (초안)

```json
{
  "command": "demo | correct_pose",
  "target_signal": "string (수신호 이름)",
  "servo_angles": {
    "thumb": 0, "index": 0, "middle": 0, "ring": 0, "pinky": 0,
    "wrist_rotation": 0
  }
}
```

> 서보 각도값은 설계 문서의 “수신호 확정안(통합 7종)”에서 실물 테스트로 확정 필요. **작성법:** 최종 채택 7종마다 한 행씩 실측 각도값 표를 이 아래에 추가하세요 (예: `| 정지 | thumb:0, index:0, ... | wrist:0 |`).
> 

### 5-2. picar 제어 명령 (초안)

> 02_설계문서_v2 §4 "수신호 확정안(통합 7종 + picar 동작)" 표를 그대로 구현에 반영. `command`는 표의 picar 동작 열과 1:1 대응.

```json
{
  "command": "stop | slow | turn_left | turn_right | reverse | caution | complete",
  "target_signal": "string (수신호 이름)",
  "motor": {
    "action": "stop | forward | backward | left | right",
    "speed": 0
  },
  "led": {
    "red": "off | on | blink",
    "yellow_left": "off | on | blink",
    "yellow_right": "off | on | blink"
  }
}
```

- `speed`: 0~100 (%), 서행(`slow`)은 정상 속도보다 낮은 고정값 사용 — ⚠️ 실측 후 확정
- `command`와 `motor`/`led` 조합 예시는 02_설계문서_v2 §4 표 참고 (예: `stop` → `motor.action=stop`, `led.red=on` 양쪽)
- **제어 인터페이스: 확정 — RPi5 GPIO 직결.** RPi5가 picar를 직접 구동하므로(02_설계문서_v2 §1-1) 이
  JSON 스키마는 프로세스 간 통신용이 아니라 **같은 RPi5 프로세스 내부에서 이 필드들을 그대로 GPIO 핀
  제어 함수 인자로 매핑**하는 용도로 쓰인다(REST 호출이나 별도 시리얼 전송 불필요).

### 5-3. micro:bit 시리얼 프로토콜

> 통신 방식: **USB 시리얼** (BLE는 페어링 이슈로 미사용). 한 줄 텍스트 수준으로 충분.
> 

**RPi → micro:bit** (LED 매트릭스 표시 지시)

```
RESULT:OK:87\n
```

- 필드: `RESULT` (고정) : `OK|NG` (정오답) : `87` (match_score, 0~100)

**micro:bit → RPi** (버튼 입력)

```
BTN:A\n
BTN:B\n
BTN:AB\n
```

> ⚠️ 위 프로토콜은 초안 예시입니다. 실제 필드 구분자, 종료 문자, 에러 처리(파싱 실패 시 재전송 여부) 등은 구현 착수 전 확정 필요.
> 
> 
> **확정하는 방법:** micro:bit 담당자와 RPi 담당자가 함께 실제 시리얼 통신 코드를 5~10줄만 짜서 문자열을 주고받아 본 뒤, 실제로 동작한 형식을 그대로 이 문서에 옮겨 적으세요(“설계만 하고 나중에 코드로 바꾸기”가 아니라 “코드로 확인된 것만 문서화”하는 순서를 권장합니다).
> 

### 5-4. 물리 피드백 지연 측정 기준

- 시작점: 손 정지 시점 (Perception 입력 기준)
- 종료점: AI Hand 동작 완료 + picar 동작 완료 + micro:bit 표시 완료 (셋 중 가장 늦은 시점)
- 목표: P95 ≤ 2.0초

## 6. (범위 제외) 수신호 등록 기능 인터페이스

> ⚠️ **이 기능은 범위에서 제외되었습니다 (2026-09-18 팀 결정).** 랜드마크 기반 **SVM 분류기**는 학습
> 시점에 고정된 클래스만 예측할 수 있어, 신규 수신호를 추가하려면 분류기 재학습이 필요합니다. 규칙
> 기반/순수 유사도 비교 시스템이었다면 재학습 없이 템플릿만 추가해 "즉시 인식"이 가능했겠지만, 경량
> 분류기(SVM) 채택으로 그 전제가 성립하지 않습니다. `match_score`(일치율)만 유사도로 즉시 계산될 뿐
> `predicted_class`(분류 결과)는 갱신되지 않으므로, 이 기능은 구현하지 않기로 했습니다.
> 아래는 폐기 전 스키마였습니다(참고용, 구현하지 않음).
>
> | 단계 | 입출력 |
> | --- | --- |
> | 촬영 | 카메라 → 랜드마크 시퀀스 (여러 프레임) |
> | 등록 | 랜드마크 템플릿 → DB 저장 (수신호 이름 포함) |
> | 즉시 인식 | ~~재학습 없이 신규 템플릿과의 유사도 비교로 인식~~ (분류기 구조상 성립 불가로 폐기) |
>
> 관련: 01_프로젝트계획서_v4 §범위, 05_모델카드_v3 §5-2, 09_화면목록_v2
