## 1. 시스템 구성 요소

```
[Raspberry Pi 5 — 학습자 앞 고정 스테이션]
[Pi Camera Module 3] → [Perception: MediaPipe (LIVE_STREAM)] → [Cognition: 분류기] → [교육 상태머신] → [Actuation: AI Hand / micro:bit]
                                                ↕                                              │
                                          [수신호 DB]                                    Wi-Fi(HTTP)
                                                                                                │
                                                                                                ▼
                                                                          [Raspberry Pi 4B 8GB — picar 탑재]
                                                                                       [Actuation: picar]
```

RPi5(카메라·AI Hand·micro:bit, 고정)와 RPi4B 8GB(picar 탑재, 이동)는 물리적으로 분리된 두 보드이며
**Wi-Fi**로 통신한다 — picar가 움직이면 카메라도 함께 이동해버리는 문제를 피하기 위한 배치
(02_설계문서_v2 §1-1, 2026-09-18).

## 2. 카메라 → Perception

> **확정**: **Raspberry Pi Camera Module 3**를 CSI로 RPi5에 직결한다 (15핀 카메라 케이블 →
> 22핀 변환 케이블 → RPi5 CAM/DISP 포트). 온보드 자체 분류 AI 카메라(WonderCam류)나 범용 USB 웹캠은
> 채택하지 않는다 — 리스크 레지스터의 "카메라가 랜드마크 좌표를 못 내줌" 항목은 이 결정으로 해결됨.
> 

| 항목 | 스펙 |
| --- | --- |
| 장치 | Raspberry Pi Camera Module 3 (CSI, 15핀→22핀 변환 케이블) |
| 입력 (확정) | **1920×1080 @ 60fps (Binned Mode)** — 2026-09-18 확정 |
| 출력 | 21 keypoints × (x, y, z) |
| MediaPipe 실행 모드 | `LIVE_STREAM` (05_모델카드_v3 §3-2 — 실시간 성능 우선, `VIDEO` 동기 루프 대비 캡처-추론 분리) |

> **실무 참고**: 카메라 캡처 자체는 1080p@60fps로 동작하지만, RPi5에서 MediaPipe 추론을 매 프레임(60fps)
> 그대로 돌릴 필요는 없다 — `LIVE_STREAM` 콜백이 처리 가능한 속도로 프레임을 서브샘플링하거나, 추론
> 직전에 축소본을 만들어 넘기는 방식을 권장한다. 실제 추론 처리율은 실측 후 05_모델카드_v3 §3-3에
> 반영하고, 판정 지연(P95 ≤ 1.0초) 미달 시 이 지점을 우선 점검한다.
> 

## 3. Perception → Cognition (랜드마크 스키마)

```json
{
  "timestamp": 12345,
  "captured_at_ms": 1789000000000,
  "hand_detected": true,
  "handedness": "Right",
  "landmarks": [
    {"id": 0, "x": 0.0, "y": 0.0, "z": 0.0},
    "... (21개)"
  ]
}
```

- `timestamp`: ms 단위 **단조 증가** 카운터 — MediaPipe `LIVE_STREAM`이 요구하는 프레임 타임스탬프 (05_모델카드_v3 §3-2)
- `captured_at_ms`: 벽시계 기준 캡처 시각(ms). **판정 지연 측정용** — `timestamp`는 단조 증가 카운터라 지연 계산에 쓸 수 없다
- `handedness`: `"Right" | "Left"`. 정규화 단계에서 **왼손을 오른손 기준으로 미러링**하는 데 필요 (05_모델카드_v3 §3-5 4번)
- `landmarks`: `hand_world_landmarks`(실세계 미터 단위 3D). `hand_detected=false`면 빈 배열

> ⚠️ `captured_at_ms`·`handedness`는 2026-09-18에 추가됐다. 문서상 정규화 절차(§3-5 4번)가 좌우 손
> 판별을 요구하는데 기존 스키마에 그 정보가 없었고, 지연 KPI도 벽시계 기준 시각이 없으면 측정할 수
> 없어서 보완한 것이다.

## 4. Cognition → 교육 상태머신 (판정 결과 스키마)

```json
{
  "predicted_class": "string (수신호 이름 또는 'negative')",
  "confidence": 0.0,
  "match_score": 0,
  "is_reject": false,
  "latency_ms": 0,
  "reason": "below_tau",
  "consecutive": 2
}
```

- `match_score`: 일치율(유사도) 0~100 점수 (계획서 KPI 항목). 예측 클래스의 템플릿과의 cosine similarity를 매핑
- `is_reject`: 미판정 여부 (미판정률 계산에 사용). τ 미달뿐 아니라 손 미검출·N프레임 미충족도 포함
- `reason`(선택, is_reject=true일 때): `no_hand` · `normalize_failed` · `model_not_loaded` ·
  `inference_error` · `below_tau` · `awaiting_consecutive_frames`
  → 웹 상태머신이 **SC-04(카메라 인식 실패: `no_hand`/`normalize_failed`)** 와
  **SC-03b(재시도 유도: `below_tau` 등)** 를 구분하는 근거. 2026-09-18 추가.
- `consecutive`(선택): 현재 연속 동일 판정 프레임 수 — N프레임 안정화(05_모델카드_v3 §3-6) 진행도
- 판정 지연(P95 ≤ 1.0초) 측정 기준점: `captured_at_ms` → 이 스키마 확정 시점

## 5. 교육 상태머신 → Actuation

### 5-1. AI Hand 제어 명령 (초안)

```json
{
  "command": "demo | correct_pose",
  "target_signal": "string (수신호 이름)",
  "servo_angles": {
    "thumb": 0, "index": 0, "middle": 0, "ring": 0, "pinky": 0,
    "wrist_rotation": 0
  }
}
```

> **초기 기본값 (2026-09-18, 실물 캘리브레이션 전 잠정)**: 서보는 0~180° 범위지만, 양 끝단(0°/180°)에
> 반복적으로 붙이면 기어/서보혼에 기계적 스트레스가 누적되므로 여유를 두고 **펴짐(EXTENDED)=170°,
> 굽힘(CURLED)=10°**의 이진값만 사용한다. 손목은 이번 7종 판별에 사용하지 않으므로(02_설계문서_v2 §4
> 참고사항 4) 항상 **중립 90°**로 고정한다. AiHand 실물 수령 후 이 값들은 실제로 각 손가락이 눈으로 봐도
> "펴짐/굽힘"으로 보이는지 확인해 조정하세요(구조는 유지, 각도 수치만 보정).

| 수신호 | thumb | index | middle | ring | pinky | wrist_rotation |
| --- | --- | --- | --- | --- | --- | --- |
| 정지 | 170 | 170 | 170 | 170 | 170 | 90 |
| 서행 | 10 | 170 | 170 | 10 | 10 | 90 |
| 좌회전 유도 | 170 | 170 | 10 | 10 | 10 | 90 |
| 우회전 유도 | 170 | 10 | 10 | 170 | 10 | 90 |
| 확인/완료 | 170 | 10 | 10 | 10 | 10 | 90 |
| 후진 | 10 | 170 | 10 | 10 | 10 | 90 |
| 주의 | 10 | 10 | 10 | 10 | 170 | 90 |

> 위 표는 02_설계문서_v2 §4의 "AiHand 표현"(예: "엄지+검지 펴기")을 그대로 이진 각도로 옮긴 것입니다.
> 서보 방향(펴짐이 170°인지 10°인지)은 실제로 서보를 돌려보고 반대면 두 값을 맞바꾸세요.

### 5-2. picar 제어 명령 — RPi5 ↔ RPi4B Wi-Fi 통신 (확정, 2026-09-18)

> 02_설계문서_v2 §4 "수신호 확정안(통합 7종 + picar 동작)" 표를 그대로 구현에 반영. `command`는 표의 picar 동작 열과 1:1 대응.
>
> ⚠️ **정정**: 이전 버전은 "RPi5가 picar를 GPIO로 직접 구동"이라고 기술했으나, picar가 움직이면 카메라도
> 함께 이동해버리는 문제 때문에 picar 컴퓨트 보드를 **Raspberry Pi 4B 8GB로 분리**했다(02_설계문서_v2
> §1-1). 아래 스키마는 이제 **네트워크 메시지**이며, RPi5의 교육 상태머신이 RPi4B의 HTTP 엔드포인트로
> 전송한다.

**검토한 대안**: MQTT(pub/sub, 재연결 로직 내장) vs HTTP REST(기존 FastAPI 마이크로서비스 구조 재사용).
**기준**: 1:1 통신(브로커가 중개할 다수 구독자가 없음)이라 pub/sub 이점이 작고, 브로커(mosquitto 등)를
새로 설치/운영하는 부담을 피하고 싶었다. **선택**: **HTTP REST(POST)**, 이미 만들어둔 FastAPI 서비스
구조를 그대로 재사용.

```json
{
  "command": "stop | slow | turn_left | turn_right | reverse | caution | complete",
  "target_signal": "string (수신호 이름)",
  "motor": {
    "action": "stop | forward | backward | left | right",
    "speed": 0
  },
  "led": {
    "red": "off | on | blink",
    "yellow_left": "off | on | blink",
    "yellow_right": "off | on | blink"
  }
}
```

| 항목 | 값 |
| --- | --- |
| 전송 방식 | HTTP POST, 같은 로컬 Wi-Fi 네트워크 |
| 엔드포인트 | `POST http://<RPi4B_IP>:8003/picar` (포트는 예시, services/picar에서 확정) |
| Body | 위 JSON (picar_command.schema.json) |
| 요청 타임아웃 | **500ms** — 물리 피드백 지연 예산(P95 ≤ 2.0초) 안에서 Wi-Fi 왕복 실패를 빠르게 감지하기 위함 |
| 재시도 | 1회만 재시도 후 포기 (ACK 왕복을 여러 번 반복하지 않음 — micro:bit와 동일하게 "실패하면 다음
  이벤트에서 다시 시도"하는 self-healing 방침, §5-3 참고) |
| 실패 시 | picar 없이 AI Hand + micro:bit로 진행 (§7 폴백) |

- `speed`: 0~100 (%), 서행(`slow`)은 정상 속도보다 낮은 고정값 사용 — ⚠️ 실측 후 확정
- `command`와 `motor`/`led` 조합 예시는 02_설계문서_v2 §4 표 참고 (예: `stop` → `motor.action=stop`, `led.red=on` 양쪽)
- RPi5와 RPi4B의 IP는 고정 IP 또는 mDNS 호스트명(예: `picar.local`) 사용을 권장 — ⚠️ 실물 네트워크 구성 후 확정

### 5-3. micro:bit 시리얼 프로토콜 (확정, 2026-09-18)

> 통신 방식: **USB 시리얼**, **115200 baud, 8N1** (BLE는 페어링 이슈로 미사용). 텍스트 라인 기반,
> 필드 구분자 `:`, 각 메시지는 `\n`(LF)로 종료(CR 없음), ASCII 인코딩.

**연결 확인 (핸드셰이크)** — RPi 프로세스 시작 시 micro:bit가 붙어 있는지 확인

```
RPi → micro:bit : HELLO\n
micro:bit → RPi : READY\n
```

**RPi → micro:bit** (LED 매트릭스 표시 지시)

```
RESULT:<OK|NG>:<match_score>\n     예) RESULT:OK:87\n
PROGRESS:<current>:<total>\n       예) PROGRESS:3:7\n  (현재 몇 번째 수신호/전체 7종)
```

- `RESULT` 필드: `RESULT`(고정) : `OK|NG`(정오답) : `match_score`(0~100 정수)
- `PROGRESS` 필드: 09_화면목록_v2 SC-03 전환마다 전송 — 02_설계문서_v2 §5의 "진행 표시" 요구사항에 대응

**micro:bit → RPi** (버튼 입력)

```
BTN:A\n
BTN:B\n
BTN:AB\n
```

**에러 처리 정책 (물리 피드백 지연 P95 ≤ 2.0초 KPI를 고려한 설계)**

- **ACK/재전송 프로토콜을 두지 않는다.** RESULT/PROGRESS는 판정이 바뀌거나 화면이 전환될 때마다
  다시 전송되므로, 한 줄이 유실되거나 손상돼도 다음 이벤트에서 자연히 복구된다(self-healing). 왕복
  확인(ACK) 절차를 넣으면 그만큼 지연이 늘어나 KPI에 불리하므로 의도적으로 생략한다.
- **micro:bit 쪽에서 파싱 실패(알 수 없는 라인/구분자 개수 불일치) 시**: 그 줄은 조용히 버리고 이전
  표시 상태를 유지한다. 에러를 되돌려 보내지 않는다 — 학습자 앞 화면(LED)이 불필요하게 깜빡이는 것을
  방지하기 위함.
- **포트 연결 자체가 끊긴 경우**: RPi가 1초 간격으로 포트 재오픈을 시도하고, 지속 실패 시 §7의 화면
  폴백 UI로 전환한다.

이 설계는 별도 회의 없이 "피지컬 AI 제품에서 중요한 것은 왕복 확인이 아니라 다음 이벤트에서 항상
최신 상태가 다시 도착하는 것"이라는 원칙으로 정했다. micro:bit 담당자는 실제 시리얼 코드를 짜본 뒤
동작이 이 문서와 다르면(예: 실제로는 CRLF가 필요하다는 등) 이 절을 갱신하세요.

### 5-4. 물리 피드백 지연 측정 기준

- 시작점: 손 정지 시점 (Perception 입력 기준)
- 종료점: AI Hand 동작 완료 + picar 동작 완료 + micro:bit 표시 완료 (셋 중 가장 늦은 시점)
- 목표: P95 ≤ 2.0초

## 6. (범위 제외) 수신호 등록 기능 인터페이스

> ⚠️ **이 기능은 범위에서 제외되었습니다 (2026-09-18 팀 결정).** 랜드마크 기반 **SVM 분류기**는 학습
> 시점에 고정된 클래스만 예측할 수 있어, 신규 수신호를 추가하려면 분류기 재학습이 필요합니다. 규칙
> 기반/순수 유사도 비교 시스템이었다면 재학습 없이 템플릿만 추가해 "즉시 인식"이 가능했겠지만, 경량
> 분류기(SVM) 채택으로 그 전제가 성립하지 않습니다. `match_score`(일치율)만 유사도로 즉시 계산될 뿐
> `predicted_class`(분류 결과)는 갱신되지 않으므로, 이 기능은 구현하지 않기로 했습니다.
> 아래는 폐기 전 스키마였습니다(참고용, 구현하지 않음).
>
> | 단계 | 입출력 |
> | --- | --- |
> | 촬영 | 카메라 → 랜드마크 시퀀스 (여러 프레임) |
> | 등록 | 랜드마크 템플릿 → DB 저장 (수신호 이름 포함) |
> | 즉시 인식 | ~~재학습 없이 신규 템플릿과의 유사도 비교로 인식~~ (분류기 구조상 성립 불가로 폐기) |
