## 3. 분석 · 선택 · 구현 · 시험 · 협업 행동

### 3-1. 분석

- **기존 web의 빈틈 확인(09-22)** — 상태머신은 판정 거부를 사유와 관계없이 무시했다. 정답 때 vision `/reset`을 부르지 않아 이전 수신호의 N프레임 누적이 넘어갈 수 있었다([15 09-22](../15_개발로그.md), [14 D6](../14_web_구현보고서.md)).
- **문서와 코드의 불일치 발견(09-22)** — `확인_완료` AI Hand 자세가 PRD·인터페이스계약서(주먹)와 actuation 코드에서 달랐다. 임의로 통일하지 않고 개발로그·README에 기록해 actuation 담당 확인을 요청했다(`fcbf091`).
- **SC-04 임계값 근거(09-29)** — 09-25 실물 데모에서 판정 시작부터 정답까지 1.2~8.0초(중앙값 2.3초) 걸렸다. 잠정치 15회(약 3초)로는 정상 동작도 SC-04(카메라 인식 실패)로 넘어갈 수 있다고 판단했다(`554a10c`, [14 D5](../14_web_구현보고서.md)).
- **"성공률" 지표 점검(09-29)** — 화면의 "성공률"(100 / 시도 횟수)은 시도 횟수를 다른 모양으로 쓴 값이었다. "50% 성공률"처럼 보여 KPI 정답률(시스템 판정 정확도)과 헷갈렸다(`554a10c`).
- **테스트가 실제 기록을 더럽히는 경로 발견(09-29)** — `tests/test_state_machine.py`를 `python`으로 직접 실행하면 `conftest.py`를 거치지 않아 실제 `logs/` 시행 로그에 가짜 행이 쓰였다(`d766e6b`).

## 5. 문제 해결 과정과 다음에 개선할 점

### 5-1. 문제 해결 사례

**① 장치가 조용히 실패해도 화면은 정상(09-21~22)**
- 문제: picar 모터가 돌지 않아도 web은 정상으로 보였다(송승호 개선안 09-21 지적).
- 원인: `_post_with_retry`가 반환값을 버렸다. 게다가 `httpx`는 4xx/5xx에 예외를 던지지 않아, 서버 오류까지 성공으로 셌다.
- 조치: 결과를 반환하고 4xx/5xx를 실패로 판정했다. 결과는 `last_dispatch`로, 장치 3종 상태는 `devices`로 `/api/state`에 노출했다(`fcbf091`).
- 결과: D3로 남았다. HTTP 200 안의 본문 실패(`timeout`·`partial`) 판정은 09-25에 남은 문제로 드러나 이동혁이 보완했다(`c8f1fd3`, [06 §1-3](../06_테스트·평가리포트.md)). 21 발표자료 7장 "화면은 정상인데 모터는 멈춤"이 이 사례다.

**② 실측 전 값을 실측값으로 교체(09-22 → 09-25)**
- 문제: 09-22 구현의 장치 값 두 개가 실측 전 값이었다. actuation 타임아웃은 C안(0.6초 일괄), picar 속도는 스키마 TBD 상태의 잠정치(서행 40·회전 60·후진 50)였다.
- 원인: 09-23 송승호 실측에서 `/command`는 손 동작이 끝난 뒤 회신해 0.79~0.83초가 걸렸다. 0.6초면 모든 제스처 명령이 timeout된다. 속도 60은 바닥 주행에서 "너무 빠름"으로 기각된 값이었다([15 09-24](../15_개발로그.md)).
- 조치: 타임아웃을 엔드포인트별로 나눴다(C′안, `/command` 1.5초, `/result`·`/progress` 0.5초). 속도는 20/40/40/40으로 바꿨다(`6f82886`). picar 서비스의 상한 50(09-24)은 송승호가 따로 넣은 안전망이다.
- 결과: 09-25 첫 전 구간 통합 빌드에 들어갔다. 현재 코드도 같은 값이다([14 §3.3·§3.4](../14_web_구현보고서.md)). 【본인 확인: 배운 점】

**③ 테스트가 실제 시행 로그에 가짜 행을 씀(09-29)**
- 문제: 테스트 파일을 직접 실행하면 실제 `logs/` 시행 로그(KPI 집계 입력)에 가짜 행이 들어갔다.
- 원인: 직접 실행은 `conftest.py`를 거치지 않아 로그 경로가 임시 폴더로 바뀌지 않았다.
- 조치: 직접 실행하면 안내 후 종료하게 했고, README 테스트 안내를 `pytest` 전용으로 바꿨다(`d766e6b`).
- 결과: 14 §6.1에 "반드시 `pytest`로 실행" 규칙으로 남았다.

**④ 같은 화면을 두 사람이 따로 구현(09-29)**
- 문제: ①-b 판정 타이밍 화면이 `feature/web`(`d03a2dc`, 조은수)과 대행본(`edb5da9`, 송승호)으로 두 번 만들어졌다.
- 원인: 같은 날 담당 공백으로 대행이 시작됐다([01 RACI 주석](../01_프로젝트계획서.md)). 【본인 확인: 당시 상황】
- 조치: `dev` 병합 때 프론트엔드와 충돌 문서(09·14·15·README)는 `dev` 쪽을 채택했다. `dev`에 없는 결정 2건·집계 스크립트 옵션·캡처를 다시 얹었다(`b119241`).
- 결과: web 테스트 71개·브라우저 검증 24개 통과. 14 §10 v1.15에 경위를 남겼다.

**⑤ 화면 교체 뒤 보고서·캡처가 현재 화면과 어긋남(10-05)**
- 문제: 09-29 캡처 11장과 14 본문이 옛 화면(예시 사진·CSV 저장) 기준이었다. 09-29~10-02 새 화면·회원·라이브 영상이 들어온 뒤 본문 곳곳이 취소선·정정 메모로 쌓였다.

- 결과: 20 결과보고서가 19장을 인용한다([20](../20_결과보고서_v1.4.md)). 실물 화면 캡처는 남았다.
