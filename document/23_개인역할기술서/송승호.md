## 1. 책임 요약

카메라 판정 결과를 실물 장치(AI Hand·micro:bit·picar)로 옮기는 **하드웨어 경로 전체**를 설계·구현·시험했다.
그 경로가 목표(물리 피드백 P95 ≤ 2.0초, 판정 지연 P95 ≤ 1.0초)를 지키는지 **실물에서 측정**하는 일까지 맡았다.

- **하드웨어·로봇 동작 (R)** — `services/actuation`(micro:bit BLE + AI Hand 서보)과 `services/picar`(RPi4B 모터 I²C·LED)의 코드, 펌웨어, 배선·전원 설계, 실물 검증을 맡았다.
- **통합·운영** — RPi5·RPi4B 두 보드의 네트워크(AP)를 구성하고 실물 기동 스크립트(`scripts/rpi/`)를 만들었다. 전 구간 통합 시험과 운영 방식(네이티브 실행)도 결정했다.
- **성능측정 (A → 09-30부터 집계 R)** — 지연 KPI 2개의 측정 정의를 확정하고 온라인 91시도를 측정·집계했다. 결과는 [06 §2](../06_테스트·평가리포트.md)에 반영했다.
- **팀장** — 회의 안건과 결정을 기록했다., 제출 산출물의 정합성을 맞췄다. 프로젝트 일정 관리와 주간회의를 주관 했으며 회의록 작성도 같이 했다. 멘토링 일정과 멘토링에게 진행사항 보고 및 질문사항을 취합하여 멘토링때 활용 했다.

## 3. 분석 · 선택 · 구현 · 시험 · 협업 행동

### 3-1. 분석 — 추정을 실물과 원본으로 확인

- **전원 구조 근거 정정(09-21)** — 문서 6곳이 "micro:bit 공급 300mA < 서보 700mA"를 서보 동시 구동 금지의 근거로 들고 있었다. 실제 배선을 확인하니 서보 전원은 확장보드가 어댑터에서 직접 분배하고 있어 이 근거는 틀렸다. 근거를 바로잡았다.
- **picar 모터 I²C 프로토콜 확보(09-21)** — 문서가 없어 "구현 불가"로 막혀 있던 항목이다. Yahboom 드라이버 소스(`YB_Pcb_Car.py`)에서 레지스터와 바이트 형식을 찾아냈다(주소 `0x16`, `0x01` 구동·`0x02` 정지).
- **micro:bit 패닉 070 원인 확정(09-22)** — 전용 검증 코드로 재현해 BLE SoftDevice와 `music`이 타이머·PWM을 공유하는 하드웨어 제약임을 확인했다. "나중에 되살릴 수 있다"던 문구 4곳을 철회하고, 플래그 뒤에 남아 있던 `music` 호출도 삭제했다.
- **Docker 운영 재검토(09-28)** — vision 이미지에는 `picamera2`를 설치할 수 없어 CSI 카메라를 쓸 수 없었다. 이때 `/health`가 계속 `ok`를 돌려줘 카메라 고장과 손 미검출이 구분되지 않는다는 점도 재현으로 찾았다.

## 5. 문제 해결 과정과 다음에 개선할 점

### 5-1. 문제 해결 사례

**① picar 정지 실패 — 시연 사고 직전에 잡음(09-23)**
- 문제: 부하 테스트 #10(`speed 50`)이 끝났는데 차가 멈추지 않았다.
- 원인: 코드가 자동 정지 타이머를 먼저 취소하고 정지를 썼다. 그래서 정지 쓰기(I²C)가 실패하면 멈출 수단이 남지 않았다. 측정 스크립트도 HTTP 200만 보고 응답 본문(`i2c_failed`)을 읽지 않아 이 실패를 "0건"으로 기록했다.
- 조치: 순서를 바꿔 정지가 성공한 뒤에 타이머를 걷고, 정지 재시도 3회와 `/health`의 `last_stop_error`를 추가했다. 스크립트는 응답 본문까지 검사하게 고쳤다. 회귀 테스트 4건은 순서를 되돌리면 실패하는 것까지 확인했다.
- 결과: 09-25 같은 조건으로 재시행해 정상 정지했다. 10-03에는 같은 원리로 타이머 경쟁 결함도 찾아 고쳤다.

**② micro:bit 핸들러 블로킹 — 1424ms(09-23)**
- 문제: 정답 표시 직후의 명령만 매번 정확히 1424ms 걸렸다.
- 원인: 수신 핸들러 안에서 LED를 표시하느라 다음 명령이 기다렸다. 게다가 `showLeds()`가 기본으로 400ms를 더 쉬어서, LED가 문서상 1초가 아니라 1.4초 켜져 있었다.
- 조치: 결과 표시를 백그라운드로 옮기고 대기 0ms를 지정했다. 표시 순번을 넣어 새 결과를 앞 표시가 지우지 않게 했다.
- 결과: 1424 → 37ms. `aihand_test.py`에 "응답은 `ok`여도 지연이 기준을 넘으면 실패" 판정을 추가했다.

**③ 펌웨어 반영 착오 — "반영됐다"와 실제가 달랐다(09-25)**
- 문제: 확인_완료(주먹) 제스처가 반영됐다고 보고됐지만, MakeCode를 열어 보니 옛 코드였다.
- 조치: 저장소 파일을 MakeCode에 통째로 붙여 넣어 플래시하는 것을 원칙으로 정했다. 23:23 재플래시 후 33건을 재검증해 통과했다.
- 배운 점: 반영 여부는 소스를 직접 봐야 확인된다.

**④ web 재시험 결함 — 단위 테스트·mock이 놓친 것(09-29)**
- 문제: 실사용 흐름에서 SC-04 재시도 버튼이 동작하지 않았고, 시도 횟수에 상한이 없었다.
- 1차 수정이 실물에서 실패한 이유는 셋이었다. 커밋 전이라 RPi5가 받지 못했고, 브라우저가 옛 JS를 썼고, 재시도 직후 손이 카메라 밖이라 SC-04로 다시 튕겼다.
- 조치: 재시도하면 시범 단계로 돌아가게 하고, 판정 제한시간 10초를 두었다. JS 버전 표식도 붙였다. 수정 전 코드에서 10건이 실패하는 회귀 테스트 11건을 추가했다.
- 결과: 같은 날 실물 재검증을 통과했다.

**⑤ RPi5 과열 — 86.2°C, 스로틀링(09-25)**
- 조치: PLA 케이스를 씌우고 선풍기를 켠 상태로 `monitor.py`를 신설해 장시간 측정했다.
- 결과: KPI 시행 구간 최대 68.6°C, 스로틀링 없음. 쿨러 없이 운용하기로 결정했고, 시연·측정 때 선풍기는 필수로 둔다.
