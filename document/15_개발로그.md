## 📌 프로젝트 개요

- **목적**: AI Hand(로봇손)가 수신호를 시범 → 학습자가 따라 함 → 카메라+MediaPipe+SVM으로 인식/판정 →
  AI Hand 재시범·picar 주행+LED·micro:bit LED 3개 물리 장치로 피드백을 주는 폐루프 안전교육 제품.
  화면 텍스트가 아니라 실제 로봇 동작으로 피드백을 준다는 점이 핵심 차별점.
- **기술 스택**: Python(FastAPI), TypeScript(MakeCode/micro:bit), MediaPipe HandLandmarker, SVM,
  BLE(`bleak`), Docker Compose. 4인 팀(vision/actuation/picar/web/data 서비스 분담).
- **관련 링크**: `document/10_PRD.md`(종합 기획서), `shared/schemas/`(서비스 간 인터페이스 계약),
  `document/11_하드웨어설계서.md`(하드웨어 단일 출처), `services/actuation/doc/`(micro:bit 디버깅 이력)

### 2026-09-21 (추가) · `actuation` — A-1 실물 BLE 검증

**작업 내용**
- A-1(실물 micro:bit `MOCK_HARDWARE=false` 검증) 수행. RPi5 대신 Windows PC에서 진행했다 — `bleak`이
  크로스플랫폼이라 BLE 구간 검증은 동일하게 성립하고, 컨테이너/BlueZ 관련 항목만 RPi5로 미뤘다.
  - BLE 스캔: `BBC micro:bit [zezuz]`(`E5:4C:EF:73:24:A9`) 탐지 확인
  - `tests/ble_debug_services.py`로 UUID 실측 대조 — `6e400003`=write(RX), `6e400002`=indicate(TX)로
    `ble_bridge.py`의 상수와 일치함을 확인(표준 NUS와 반대인 것도 재확인)
  - `MOCK_HARDWARE=false`로 서비스 기동 → `/health`가 `microbit_connected: true` 반환
  - `/command` 7종(G1~G7) 전송 + AI Hand 손모양 육안 대조 완료
  - `/result` correct/incorrect → LED O/X 표시 정상 확인 (아래 부저 수정 후)
  - `/progress` → `P37`/`P17` 전송에 `OKP37`/`OKP17` 회신 확인(`status: ok`). LED 표시가 없는
    명령이라 회신값이 유일한 성공 근거인데, 왕복까지 정상으로 확인됨
- 검증 중 발견한 환경 이슈 2건(문서화 목적):
  - PowerShell에서는 bash식 `MOCK_HARDWARE=false uvicorn ...`이 안 된다 → `$env:MOCK_HARDWARE = "false"` 후 실행
  - PowerShell의 `curl`은 `Invoke-WebRequest` 별칭이라 `-d '{"..."}'`의 큰따옴표가 벗겨져 JSON이 깨진다
    → `curl.exe`를 쓰거나 `Invoke-RestMethod ... -Body (@{...} | ConvertTo-Json)` 사용.
    한글 `target_signal`은 파일(`cmd.json`, UTF-8)로 만들어 `--data-binary @cmd.json`으로 보낼 것

**이슈/블로커**
- 🐛 **패닉 070 재발** — `/result` 테스트 중 **부저가 울리는 순간** micro:bit에 슬픈 얼굴 + `070`이
  표시되며 BLE가 끊겼다. 원인은 `aihand_control.ts`의 `playResultTone()`이 쓰는 `music.playTone()`이
  micro:bit v2 BLE SoftDevice와 충돌하는 것(SD_ASSERT).
- 이것은 **이미 알려진 문제의 회귀**였다 — `StartbitV2_patched.ts:324`에 "원래는 music.playTone() -
  BLE SoftDevice 충돌(070 panic) 방지를 위해 소리 대신 LED로 대체"라는 주석이 남아 있는데, 나중에
  RESULT 기능을 추가하면서 같은 호출을 다시 넣었던 것이다.

**결정 사항**
- **부저는 사용하지 않는다(확정).** `aihand_control.ts`에 `const BUZZER_ENABLED = false;`를 추가하고
  `playResultTone()` 최상단에서 가드한다. 부저가 꺼져 있을 때는 `showResult()`가 `basic.pause(2000)`으로
  **LED 표시 시간 2초를 그대로 유지**한다(기존엔 부저 1초 블로킹 + 1초 대기로 2초였음).
  코드를 삭제하지 않고 플래그로 남긴 것은, 패닉 없이 소리 내는 방법을 찾으면 한 줄로 되살리기 위함이다.
- 판정 피드백은 **LED O/X만** 사용 — `02_설계문서`, `03_인터페이스계약서`,
  `shared/schemas/microbit_protocol.md`, `services/actuation/README.md`를 모두 이 기준으로 갱신했다.
- 재플래시 후 정상 동작(소리 없이 O/X 표시, 패닉·BLE 끊김 없음) 확인 완료.

### 2026-09-21 (추가) · `picar` — B-1 picar 모터 I2C 프로토콜 확보 및 구현

**작업 내용**
- **Raspbot 모터 I2C 명령 프로토콜 확보** — Yahboom 공식 드라이버 라이브러리 `YB_Pcb_Car.py`에서
  레지스터/바이트 포맷을 확인했다. 그동안 "벤더 문서가 없어 구현 불가"로 막혀 있던 항목이다.

  | 레지스터 | 용도 | 바이트 포맷 |
  | --- | --- | --- |
  | `0x01` | 모터 구동 | `[좌_방향, 좌_속도, 우_방향, 우_속도]` (방향 0=후진/1=전진, 속도 0~255) |
  | `0x02` | 정지 | 단일 바이트 `0x00` |
  | `0x03` | 서보 | `[서보ID, 각도(0~180)]` — 카메라 팬/틸트용, 주행 미사용 |

  슬레이브 주소는 **`0x16`**(Raspbot 오리지널). ⚠️ Raspbot **V2는 `0x2B`** 라 보드가 다르면 값이
  달라진다 — 실물에서 `i2cdetect -y 1`로 확인하고 `RASPBOT_I2C_ADDR`로 덮어쓸 수 있게 해뒀다.
  우리 보드를 오리지널로 추정한 근거: `hardware_pinmap.md`에서 초음파·부저·LED·트래킹이 전부 Pi
  GPIO 직결인데, V2는 이 주변장치들까지 MCU가 I2C로 관장한다.
- `services/picar/src/controller.py` 실물 구동 구현 — 기존 `NotImplementedError` 제거
  - 모터: `stop`/`forward`/`backward`/`left`/`right` → I2C 레지스터 쓰기. 스키마의 speed(0~100%)를
    코프로세서용 0~255로 변환
  - 좌/우 회전은 **제자리 회전**(한쪽 전진 + 반대쪽 후진)으로 구현 — 교육 시범이라 회전이 눈에
    확실히 보이는 편이 낫다는 판단(완만한 선회로 바꾸려면 한쪽 속도를 0으로)
  - LED: `gpiozero`로 적색(BCM21) on/off/blink 구현. 황색 2개는 미배선이라 `unsupported` 응답
  - I2C 실패해도 예외를 삼키고 응답에 담아 돌려준다 — web이 picar 실패로 학습 흐름을 막지 않는

### 2026-09-21 (추가) · `actuation` — ⚠️ 전원 구조 근거 정정 (기존 문서 6곳 오류)

**무엇이 틀렸나**

그동안 "손가락 서보 동시 구동 금지"의 근거로 여러 문서가 이렇게 적고 있었다:

> micro:bit v2 보드 최대 공급 전류 약 300mA < 손가락 서보(LFD-01) 구속 전류 700mA
> → 서보 하나만 걸려도 보드 공급 한계를 넘는다

**이 설명은 틀렸다.** 실제 전원 구조를 확인한 결과(2026-09-21):

```
[7.5V 3A 어댑터] ──▶ [Hiwonder micro:bit 확장보드] ──┬──▶ micro:bit v2
                            (전원 분배)              ├──▶ 서보 핀 6개 (각 핀 7.5V)
                                                    ├──▶ 각종 입출력 인터페이스
                                                    └──▶ DC 모터 전용 핀
```

**서보는 micro:bit를 거치지 않는다.** 확장보드가 어댑터에서 직접 분배한다. micro:bit의 300mA는
micro:bit가 *외부로* 공급할 수 있는 한계치라서 서보 전류와는 애초에 상관이 없는 수치였다.

**실제 메커니즘**: 어댑터 1개가 확장보드를 거쳐 **micro:bit와 서보를 같은 레일에서** 먹인다.
손가락 서보 5개를 동시 기동하면 3.5A(구속 기준)로 어댑터 용량 3A를 넘겨 7.5V 레일이 주저앉고,
**같은 레일의 micro:bit가 브라운아웃되어** BLE SoftDevice가 죽는다(패닉 070). 순차 구동은 이
돌입 전류를 시간축으로 흩어 놓는 방식이다.

**결론은 안 바뀌지만 함의가 바뀐다**: 순차 구동이 필요한 건 동일하다. 다만 기존(잘못된) 모델에서는
어떤 수를 써도 동시 구동이 불가능했는데, 실제 제약이 어댑터 용량이라면 **전원 보강(고용량 어댑터 +
서보 레일 벌크 커패시터)으로 동시 구동이 가능해질 여지가 있다.** 일정상 후순위로 두고 기록만 남긴다.

**🔴 정정 과정에서 새로 발견한 위험 — 서보 정격 전압 초과 가능성**

확장보드의 서보 핀은 **7.5V를 그대로 내보내는데**, LFD-01과 LD-1501MG의 정격 작동 전압은 둘 다
**DC 4.8~6.0V**다(`hardware_spec.md`). 사실이라면 정격을 25% 초과해 구동 중이다.

- 그렇다면 **손가락 서보 5개가 모두 같은 위험**에 노출돼 있다 — 시연 전에 고장이 날 수 있다.
- 다만 Hiwonder가 이 서보들과 7.5V 어댑터를 한 제품으로 함께 출하하므로, 의도된 오버볼트이거나

### 2026-09-21 (추가) · `picar` `web` — RPi5↔picar 통신 신뢰성 + IP 구성 확정

**IP 구성 확정 — 공유기 없이 1:1 무선 직결**
- RPi5의 Wi-Fi를 **AP 모드**로 띄우고 picar(RPi4B)가 접속하는 구조, **양쪽 고정 IP**로 확정.
  RPi5 `192.168.50.1/24`, picar `192.168.50.10/24`. PC 직결(UTP)은 `192.168.10.x`로 서브넷이 달라
  두 링크가 섞이지 않는다.
- **공유기를 안 쓰는 이유**: 발표장 공용 Wi-Fi 품질은 통제 밖 변수다. 다른 팀 기기 간섭으로
  picar의 500ms 예산이 잠식되면 그 자리에서 할 수 있는 게 없다. `네트워크_구성_결정.md`에서
  RPi5↔PC를 UTP 직결로 정한 것과 같은 원칙 — **시연 경로에서 외부 인프라 의존을 전부 제거**.
- **mDNS 대신 고정 IP**: 이름 해석이 한 단계 더 끼어들고 Avahi 상태에 따라 간헐 실패한다.
  장치가 2대뿐이라 이름을 쓸 이득이 없다.
- ⚠️ **트레이드오프**: RPi5는 무선 IF가 1개뿐이라 AP 모드에서 스스로 인터넷에 못 나간다(이더넷은
  PC 직결에 사용). → 개발 중엔 공유기에 붙여 쓰고 **시연 직전에 AP로 전환**한다.
- `11_하드웨어설계서.md` §6.1에 IP 표·근거·`nmcli` 구축 절차 기재. `02_설계문서.md` §5의
  미확정 체크 해소, `네트워크_구성_결정.md`에 상호 참조 추가.

**picar `/health` 실질화**
- 기존에는 프로세스만 살아 있으면 무조건 `ok`였다 — **"I2C가 죽었는데 HTTP 200"** 을 구분할 수 없었다.
- `controller.diagnose()` 추가: I2C 코프로세서 ACK 여부, LED 핀 배정, 주행 중 여부를 보고한다.
  I2C 프로브는 `write_quick`(주소만 전송)이라 **모터를 돌리지 않는 비파괴 검사**다.
- `/health`가 `status: "ok" | "degraded"`를 돌려주도록 변경 — 호출부가 한 필드만 봐도 된다.
- 단위 테스트 5개 추가 (picar 21 → **26개**)

**web 쪽 개선은 변경안으로 전달**
- `services/web/backend/state_machine.py`는 **조은수 담당**이라 직접 수정하지 않고
  `document/archive/web_picar_통신_신뢰성_개선안.md`로 정리했다.
- 핵심 발견: `_post_with_retry`가 반환값을 버리는 데다, **`httpx.post()`는 4xx/5xx에 예외를 던지지
  않는다.** 즉 지금 구조는 **서버 오류(HTTP 500)까지 성공으로 세고 있다.** picar가
  `{"status":"partial","motor":{"reason":"i2c_failed"}}`를 반환해도 web은 정상으로 인식한다 —
  시연 중 모터가 안 돌아도 화면은 멀쩡해 보인다.
- 제안: ①`_post_with_retry` 결과 반환(+4xx/5xx 처리) ②전송 결과를 `/api/state`에 노출
  ③`/health` 주기 확인 ④폴링 블로킹 완화(A/B/C 택1, 나는 C 선호)
- `.env.example` 정리: 실물 고정 IP 예시 추가, 옛 `MICROBIT_PORT=/dev/ttyACM0`(USB 시리얼 시절
  유물)을 `MICROBIT_BLE_NAME`으로 교체

**① 제작사 제공 SD 이미지 분석** (`11_하드웨어설계서.md` §5.5)

Yahboom이 제공한 RPi4B 전용 이미지 `Raspbot_rpi4B.img`(15.6GB)의 파티션을 추출해 내부를 확인했다.

- **§5.2 I2C 프로토콜 확증**: 이미지 안의 `YB_Pcb_Car.py` **17개 사본이 전부 md5 동일**하고,

- 🔴 **핀 번호 체계 함정 발견**: 제작사 코드는 전부 `GPIO.setmode(GPIO.BOARD)`(물리 핀 번호)를
  쓴다. 우리는 BCM 기준이므로 **제작사 예제 상수를 그대로 옮기면 전혀 다른 핀을 잡는다.**
  13핀 대조표를 §5.5.3에 남겼다 — 기존 §5.4 점유 핀표와는 일치했다.
- **제작사 코드 결함 4건** 기록(§5.5.5): 서보 각도 클램프가 리스트 생성 *뒤*에 있어 무효, 펄스 변수
  windup, GPIO9/10 ↔ SPI 충돌, IR 핀 이중 점유. **참고는 하되 이식하면 안 되는 지점**이다.
- **재사용 판단**: 가져올 것은 **I2C 프로토콜 사양뿐**. 이미지 전체는 Buster(EOL) + TF 1.14 +
  `force_turbo=1` + SSH/VNC 기본 활성이라 그대로 쓸 수 없고, Flask·WebSocket 스택은 우리 아키텍처와
  역할이 겹친다. **자체 OS에 `services/picar`만 올리는 기존 방침이 타당함을 확인**했다.
  단, 자체 OS 설치 시 `dtparam=i2c_arm=on`을 직접 켜야 한다(기본 비활성) — 체크리스트에 추가.
- 부수 확인: 제작사 기본 속도 `car_speed=100`(0~255), 완만한 선회는 한쪽 절반 속도, 제자리 회전은

- **현재 어댑터는 5V/3A뿐이고 5V/5A는 배송 중.** 3A로 1차 테스트를 진행해도 되는지 검토한 결과
  **충분하다**고 판단했다:
  - 이번 구성에서 RPi5가 하는 일은 `services/picar`(FastAPI + I2C + LED 3핀)뿐이고 **USB 주변기기가
    하나도 붙지 않는다**(웹캠은 PC 쪽, 카메라 미사용).
  - RPi5 보드 단독 소비는 공식 자료 기준 유휴 약 3W / 고부하 약 9~12W(2.4A). 3A=15W면 여유가 있다.
    공식 27W PSU 요구는 **USB 주변기기 1.6A분 확보**가 목적인데 우리는 그것을 쓰지 않는다.
  - 예상 현상 2가지(동작 지장 없음): 부팅 시 *"5A를 공급할 수 없습니다"* 경고, USB 총 전류 600mA 제한.
  - ⚠️ 어댑터·케이블 품질은 확인할 것. 표기만 3A이고 CC 저항 구성이 부실하면 실제 1.5A로 떨어져
    언더볼티지(4.63V 미만)와 스로틀링이 발생한다. 의심되면 `vcgencmd get_throttled`.
- 🔴 **전류보다 배선이 위험하다 — 확인 2건** (블럭 위 테스트에서도 동일하게 적용):
  1. **확장보드의 헤더 5V 공급을 끊어야 한다.** Raspbot 확장보드는 통상 배터리 전원을 GPIO 헤더로
     Pi에 공급한다. 여기에 USB-C 어댑터를 동시에 꽂으면 두 전원이 같은 5V 레일에서 맞물리는데,
     **RPi5의 USB-C 입력에는 역류 방지가 있지만 헤더 5V 핀에는 없다.** 조립 전 확장보드의 5V 공급
     구조를 확인하고, 공급 구조라면 해당 라인을 차단한다.
  2. **GND는 반드시 공통 유지.** I2C(SDA/SCL)는 GND를 기준 전위로 삼는다. 5V만 끊고 GND는 연결
     상태를 유지해야 한다 — 분리하면 I2C가 아예 안 되거나 간헐적으로 깨진다.
- 🟡 **어댑터 방식은 주행 시연에 쓸 수 없다.** 벽 어댑터는 차를 케이블에 묶는다. 1차 벤치
  테스트(⑦)까지는 무관하지만, 실제 주행에는 배터리/PD 보조배터리가 필요하다. 다만 위 부하 계산대로면
  **PD 보조배터리 5V/3A로도 감당된다** — 5V에서 5A를 내는 보조배터리는 드물어 오히려 실용적이다.

**⑦ 1차 벤치 테스트 범위 확정 — 블럭 위, 바퀴와 LED만**

차체를 블럭 위에 올려 바퀴를 띄운 상태로 **구동 확인만** 진행한다. 주행·조향 튜닝은 이후로 미룬다.

- 이 범위에서는 어댑터 테더링이 문제되지 않으므로 **5V/3A로 그대로 진행 가능**하다.
- 기존 §9.2 체크리스트의 *"차를 들어 올린 상태에서 저속(speed=30) 전진"* 항목과 같은 방식이다.

**⑧ 테스트 절차 — 진단 경로를 활용한 3단계 분리**

`controller.py`에 이미 비파괴 진단이 들어 있어, 단계를 나누면 어디서 막혔는지 바로 드러난다.

| 단계 | 명령 | 확인 대상 | 바퀴 |
| --- | --- | --- | --- |
| 1 | `i2cdetect -y 1` → `GET /health` | I2C 코프로세서 ACK | **안 돎** |
| 2 | `POST /picar` (led만, `motor.action=stop`) | LED 3채널 배선 | 안 돎 |
| 3 | `POST /picar` (`forward`, `speed:30`) | 바퀴 회전 방향·자동 정지 | 돎 |

- 1단계가 **바퀴를 돌리지 않는 이유**: `_probe_i2c()`가 `write_quick`(주소만 전송, 데이터 없음)을
  쓴다. `/health`가 `degraded`면 주소가 V2(`0x2B`)일 수 있으므로 `RASPBOT_I2C_ADDR=0x2b`로 재시도.
- `speed`는 **퍼센트**다 — `_speed_pct_to_byte()`가 0~100을 0~255로 변환한다(30% ≈ 76).
  명령 1회마다 **2초 후 자동 정지**하므로 계속 돌지 않는다.
- 3단계에서 볼 것: `forward`인데 좌우 회전 방향이 다르면 배선 반전, `left`/`right`가 의도와 반대면
  좌우 교체(제자리 회전이라 눈에 띄지 않을 수 있음).
- 🔴 **2단계는 응답으로 판정할 수 없다 — 반드시 육안으로 확인할 것.** `PIN_MAP`의 3핀이 2026-09-21에
  전부 배정돼(`13`/`5`/`6`) `_apply_led`의 `unsupported` 경로는 **이제 발생하지 않는다**
  (`test_controller.py`가 `leds_unassigned == []`를 단언한다). 즉 **LED를 한 개도 결선하지 않아도
  `status: "ok"`가 돌아온다** — gpiozero는 핀을 잡는 데 성공했을 뿐, 그 끝에 LED가 달렸는지 알 방법이
  없다. 응답만 보고 "LED 배선 검증됨"으로 판단하면 **거짓 양성**이다.
- ⚠️ **정정(2026-09-22)**: 앞서 "`motor`를 빼면 422로 거부된다"고 적었으나 **틀렸다.**
  `POST /picar`는 FastAPI에서 `dict`로 받아 **스키마 검증을 하지 않고**, `execute()`가 `.get()`
  기본값으로 채운다 — `motor`가 없으면 `stop`으로 동작한다. 스키마상 필수인 것과 **서비스가
  강제하는 것이 다르다.** 벤치 테스트는 web이 실제로 보낼 형태(4개 필드)로 보내되, 이 차이는

### 2026-09-22 (추가) · `actuation` — micro:bit BLE ↔ `music` 병용 불가 확정, 규칙화

  돈다는 점, `bleak`이 크로스플랫폼이라 PC에서 BLE만 따로 검증할 수 있다는 점(A-1에서 실제로 활용),
  Windows Docker가 웹캠·BLE를 전달하지 못한다는 점.

**§7.1 전원 계산을 RPi4B 기준으로 교체**

RPi4B의 공식 요구가 **USB-C 5V 3A**라 보유 어댑터가 곧 정격이다. RPi5용으로 따지던 "27W 요구의
정체는 USB 주변기기 1.6A" 같은 논의가 통째로 불필요해졌다. 5V/5A 요구는 고정 스테이션 쪽에만 남는다.

**1차 벤치 테스트를 건너뛰고 2차(바닥 주행)로 바로 갈 수 있는지 — 검토 결과: 건너뛰지 않는다**

건너뛰자는 근거(I2C 프로토콜은 제작사 이미지로 확증됨, 자동 정지 구현돼 있음, 일정 압박)는
이해되지만, **셋 다 아직 실물에서 한 번도 확인된 적이 없다.**

| 미확인 항목 | 바닥에서 틀렸을 때 |
| --- | --- |
| 바퀴 회전 방향(좌우 배선) | `forward`가 제자리 회전이 된다 — 책상에서 떨어질 수 있다 |
| **2초 자동 정지의 실동작** | `_safe_stop()`이 I2C 예외를 `except: pass`로 **조용히 삼킨다.** 정지에 실패해도 **로그조차 없이 계속 달린다** |
| I2C 주소(`0x16` vs `0x2B`) | 틀리면 무반응. 무해하지만 바닥에서 알 이유가 없다 |

추가로 `_auto_stop_timer`는 **daemon 스레드**다. 주행 중 서비스를 `Ctrl+C`로 죽이면 타이머가
사라지고 코프로세서는 **마지막 명령을 계속 유지**한다 — 바퀴가 멈추지 않는다. 블럭 위에서는 이
동작을 안전하게 관찰할 수 있다.

- **비대칭이 결정적이다.** 블럭 테스트는 10~15분이고, 막는 사고는 **차체 또는 RPi4B 손실**이다.
  RPi4B는 예비가 없고 오늘 막 도착했으며, 남은 일정은 W4(~10/04)다.
- 다만 **별도 일정으로 분리할 필요는 없다.** 같은 세션의 앞 10분으로 붙이면 되고, 오히려 방향
  매핑을 미리 알고 들어가므로 2차 튜닝이 빨라진다. → §9.2에 근거와 함께 명시했다.

### 2026-09-22 (추가) · `picar` — picar 전원을 차체 배터리 단일 계통으로 변경 (오전 결정 번복)

**결정**: RPi4B는 **별도 어댑터를 쓰지 않는다.** 차체 배터리가 강압을 거쳐 **GPIO 헤더 5V로 Pi에
공급**한다. 모터와 Pi가 같은 배터리를 공유하는 단일 계통이다.

| 배터리 사양 | 값 |
| --- | --- |
| 구성 | 3S 리튬이온 — 공칭 **11.1V** / 만충 12.6V / **하한 9.0V**(3.0V/셀) |
| 용량 | **2200mAh · 24.42Wh** |

**① 용량은 제약이 아니다**

가용 19.5Wh(24.42의 80%), RPi4B 헤드리스 약 3W에 강압 효율 85% 적용:

| 조건 | 평균 | 구동 시간 |
| --- | --- | --- |
| Pi 단독 | 3.5W | 약 5.5시간 |
| + 모터 듀티 10% | 5.2W | **약 3.8시간** |
| + 모터 듀티 20% | 6.9W | 약 2.8시간 |

주행은 명령당 2초뿐이라 실제 듀티가 10%를 넘기 어렵다. **시연 시간 대비 충분하다.**

**② 🔴 진짜 제약은 과도 특성이다**

모터 기동/정지 순간의 전압 흔들림이 위험하다. **RPi4B는 4.63V 미만을 언더볼티지로 판정**하고,
그 상태에서 SD에 쓰고 있으면 카드가 깨진다. 확인할 것 3가지를 §7.1.2에 정리했다 —
차체 강압 회로의 5V 정격(부팅 돌입 전류), 벌크 커패시터(470~1000µF) 추가 여부, LVC 유무.

**③ 되살아난 리스크 — 모터 노이즈 ↔ Wi-Fi**

오전의 계통 분리로 "레일을 공유하지 않으니 경로 자체가 없다"고 해소 처리했던 항목이다.
**단일 계통에서는 다시 실측 대상**이며, picar가 Wi-Fi로 명령을 받으므로 끊기면 시연이 멈춘다.
→ `08_리스크레지스터`에 신규 등록하고, 구성도 §5의 체크도 되돌렸다.

**④ 🔴 배선 규칙이 반전됐다 — 가장 헷갈리기 쉬운 지점**

| | 오전(분리) | **현재(단일)** |
| --- | --- | --- |
| 헤더 5V | **차단할 것** | **급전 경로 — 연결 유지** |
| USB-C 어댑터 | Pi 급전용 | 🔴 **동시 연결 금지** |
| GND | 공통 유지 | 공통 유지 (동일) |

백피드 위험이 사라진 것이 아니라 **"차단하라"가 "둘 중 하나만 쓰라"로 바뀐 것**이다. 개발 중
어댑터를 쓰려면 배터리 스위치를 내리고 꽂는다.

### 2026-09-22 (추가) · `picar` — 적색 LED를 2핀으로 분리 (5mm 사양 확정에 따름)

**결정**: LED는 **5mm(정격 20mA)**, 저항은 개별 직렬로 통일(당초 330Ω → **같은 날 220Ω으로 변경**,
아래 후속 참고). 그에 맞춰 **적색 2개를 BCM13 하나의 병렬에서 BCM13 + BCM19 두 핀으로 분리**한다.

**왜 분리했나**

| 구성 | 330Ω 기준 핀 전류 | 판정 |
| --- | --- | --- |
| 적색 2개 → 1핀(병렬) | 약 **7.9mA** | ⚠️ 핀 기본 구동 한도 **8mA에 붙음** |
| 적색 2개 → **2핀** | 핀당 약 **3.9mA** | ✅ 핀당 8mA까지 여유 |

5mm LED 정격이 20mA라 330Ω(약 3.9mA)은 **정격의 20%** 수준이다. 실물에서 어두우면 저항을 낮춰야
하는데, **병렬 구성은 이미 한도에 붙어 있어 그 여지가 없었다**(220Ω이면 약 12mA로 초과).
GPIO 구동 강도 설정을 바꾸는 것은 뱅크 단위라 다른 핀에 영향이 가고, 트랜지스터 추가는 부품이
늘어난다. **핀을 나누는 것이 가장 간단하다** — BCM19는 Raspbot 점유가 아닌 여유 핀이다.

**스키마는 바뀌지 않는다.** 적색은 정지(양쪽 점등)·확인_완료(양쪽 점멸)에만 쓰이고 한쪽만 켜지는
경우가 없어 `red` 단일 채널 그대로다. 핀이 2개가 된 것은 **전류 문제일 뿐 제어 의미는 1채널**이다.

**코드 변경** (`services/picar/src/controller.py`)
- `PIN_MAP` 값을 **핀 튜플**로 바꿨다 — `led_red: (13, 19)`, 황색은 `(5,)`/`(6,)`. 핀이 1개인
  채널도 튜플로 통일해 분기를 단순하게 뒀다.
- 🔴 **`LED` 대신 `LEDBoard`를 쓴다.** `LED` 객체 2개를 따로 `blink()`시키면 **각자 스레드를 돌려
  위상이 어긋날 수 있다** — 적색 2개가 엇갈려 깜빡이면 "확인_완료" 표시가 망가진다. `LEDBoard`는
  한 스레드로 묶어 구동하므로 동조가 보장된다. 핀을 나누면서 새로 생긴 위험이라 코드로 막았다.
- 응답 필드가 `pin`(정수) → `pins`(리스트)로 바뀌었다. web은 이 필드를 쓰지 않아 영향 없음.
- 테스트 27개 통과(+1) — `test_red_channel_drives_two_dedicated_pins`로 **다시 1핀으로 합치는
  회귀를 막는다.**

**산출물 반영**: `11_하드웨어설계서.md` §5.3·§7·§9.2, `hardware_pinmap.md`(여유 핀 목록 포함),
`02_설계문서.md`, `services/picar/README.md`.

**참고 — 여유 핀이 하나 남았다**: 이제 완전히 자유로운 핀은 **BCM26** 하나뿐이다.

**후속 (같은 날) — 저항 330Ω → 220Ω**

실물에서 어두워 저항을 낮추기로 했다. **핀을 분리해 둔 덕에 가능한 선택**이었다 — 병렬 구성이면
220Ω에서 약 11.8mA로 핀 한도 8mA를 넘었을 것이다.

| 저항 | 적색 | 황색 | 판정 |
| --- | --- | --- | --- |
| 330Ω | 3.9mA | 3.6mA | 어둡다 (5mm 정격 20mA의 20%) |
| **220Ω** | **5.9mA** | **5.5mA** | ✅ 채택 — 핀 기본 한도 8mA 안 |
| 150Ω | 8.7mA | 8.0mA | ❌ 적색이 한도 초과 |

전체 4핀 합계 약 22.7mA로 보드 한계(50mA) 안이다. **150Ω 이하로는 내리지 않는다**는 기준을
문서에 박아 뒀다 — 더 밝게 하려면 저항이 아니라 트랜지스터 드라이버가 필요하다.

- ✅ **220Ω 4개 보유 확인** (2026-09-22). 부품 측 대기 항목 없음 — **배선·점등 검증만 남았다.**
- **GND 배치 확정**: 황색 2개는 물리 30번, 적색 2개는 물리 34번에 **쌍으로 묶는다.** 각 GND가
  자기 쌍의 한가운데(29·31 사이 / 33·35 사이)라 배선이 가장 짧고 그라운드 선이 4→2가닥이 된다.
  GND 핀은 보드 내부에서 모두 연결돼 있고 **8mA 한도는 출력 핀에만 적용**되므로 합산 약 12mA는
  무방하다. ⚠️ **GND 공유와 저항 공유는 다르다** — 저항은 LED마다 하나씩 유지 (§5.3).

| 6 | `vcgencmd get_throttled` (모터 20회 후) | ✅ **`0x0`** |
| 6 | 모터 구동 중 Wi-Fi 왕복 | ✅ **실패 0건** |

**① 전원 단일 계통 — 최대 불확실성이 해소됐다**

어제 전원을 배터리 단일 계통으로 바꾸면서 되살아났던 두 리스크가 **실측으로 닫혔다.**

- `get_throttled`가 `0x0`이고 **bit 16(발생 이력)까지 서지 않았다** — 순간 강하조차 없었다는 뜻이다.
  차체 강압 회로가 Pi와 모터를 여유 있게 감당한다.
- **벌크 커패시터 불필요**(§10 #17 종결), 강압 회로 정격 확인도 해소(#15).
- 모터 노이즈가 Wi-Fi에 영향을 주지 않았다 — `08_리스크레지스터` 해당 행을 🟡 → 🟢으로 내렸다.

> 🟡 **단서: 무부하 조건이었다.** 바퀴를 띄워 모터가 차체 무게를 밀지 않았다. 바닥에서는 기동
> 토크로 전류가 크게 늘고, 배터리가 12.6V → 9.0V로 갈수록 강압 여유가 준다 — **시연 후반부가
> 가장 불리하다.** §10 #18로 "바닥 주행 재확인"을 남겼고, 커패시터도 배제하지 않고 "플래그가
> 서면 재검토"로 열어 뒀다.

**② 자동 정지가 실제로 동작한다**

`_safe_stop()`이 I2C 예외를 `except: pass`로 삼키는 구조라, **정지에 실패해도 로그조차 안 남는다.**
이것이 1차 벤치를 건너뛰지 않기로 한 가장 큰 이유였는데, 실물에서 정상 동작을 확인했다.
바닥 주행의 선결 조건이 충족됐다.

**③ 디버깅에서 배운 것 — 기록해 둘 가치가 있다**

LED가 처음에 전혀 안 켜졌고, 원인은 **GND 오삽입**이었다. 좁혀 간 경로:

| 관찰 | 판단 |
| --- | --- |
| `POST /picar` 응답이 `ok`(≠`mocked`) | 소프트웨어·`MOCK_HARDWARE` 정상 |
| `pinctrl set 13 op dh`로도 안 켜짐 | **소프트웨어 문제 아님 — 물리 쪽** |
| `pinctrl get 13` = `hi` | SoC는 3.3V를 내고 있음 → 핀 이후 구간 문제 |
| **4개 전부** 실패 | 개별 불량이 아니라 **공통 원인** → GND 의심 |

- 🔑 **`pinctrl`로 서비스를 우회하면 SW/HW가 한 번에 갈린다.** 서비스를 끄고 핀만 직접 때려 보는
  것이 가장 빠른 분리 방법이다.
- 🔑 **"전부 실패 = 공통 원인"** — 개별 배선을 하나씩 뜯기 전에 GND·전원·핀 기준점부터 본다.
- ⚠️ **`pinctrl` 잔상 주의**: `dh`로 올려둔 핀은 서비스를 다시 띄우기 전까지 그대로 남는다.
  GND를 고친 직후 "LED가 안 꺼진다"고 판단했던 것이 이 때문이었다 — 코드 문제가 아니었다.
  (gpiozero 2.0.1 소스로 `LEDBoard.off()`가 `_stop_blink()`를 먼저 부르는 것까지 확인했다.)

### 2026-09-23 (추가) · `actuation` `web` — AI Hand RPi5 실물 검증: 손가락 간격 150ms 확정, 펌웨어 핸들러 블로킹 결함 발견

#### 회차별 결과

| 회차 | 펌웨어 | 방식 | `/command` (G1~G7) | `/result` | 070·리셋 |
| --- | --- | --- | --- | --- | --- |

- **손가락 간격 150ms 확정.** 서보 이동 시간(200ms)보다 짧아 인접 2개가 50ms씩 겹치지만(약 1.74A <

  → 회신을 먼저 보내도록 변경(ACK-first).
- 이전 회차에서 `/result correct` 때 봤던 **070은 이후 4회 모두 재현되지 않았다.** 원인 미확정.

#### 🔴 연속 모드가 드러낸 결함 — ACK-first만으로는 부족했다

자동 연속 모드에서 `result correct`(38ms) 직후의 `result incorrect`와 `progress 3/7`이 **매번 정확히
1424ms** 걸렸다. 원인이 두 겹이었다.

1. `showResult()`가 **수신 핸들러 안에서** `pause`하는 동안 다음 명령이 줄을 서서 기다렸다(사라지지는 않음).
2. `basic.showLeds()`는 두 번째 인자를 안 주면 **그림을 그린 뒤 400ms를 더 쉰다.** `pause(1000)` + 400 =
   1.4초 — LED가 문서상 1초가 아니라 **실제로는 1.4초** 켜져 있었다.

**실전 영향**: web이 판정 결과 직후 다음 손동작을 보내면 1.4 + 0.8 ≈ 2.2초로 `ACK_TIMEOUT_S`(2.0초)를
넘어 **손 동작이 timeout으로 기록된다.** 대화형은 사람이 쉬는 틈에 LED가 끝나 안 보였다.

→ 펌웨어를 `control.inBackground(() => showResult(..))` + `showLeds(.., 0)`으로 수정. 표시 중에 새
결과가 오면 앞 표시가 새 표시를 지우지 않도록 순번(`resultSeq`)도 넣었다. **재검증 대기.**

### 2026-09-28 · `picar` `web` — LED 자동 소등: 정지 계열 명령 뒤 LED 잔류 해결

**문제** — `picar_command` 스키마에는 LED를 켜는 값만 있고 끄는 시점이 없다. 정지·확인_완료·주의는 모터 자동 정지

**결정** — web이 끄는 명령을 보내는 대신 **picar가 스스로 끈다.** 자동 정지를 picar에 둔 이유와 같다 — 끄는 명령이 유실되면
LED가 남는다. 이렇게 하면 web은 고칠 것이 없다(조은수 할 일 ④ 종결).

**구현** (`services/picar/src/controller.py`)
- LED를 하나라도 켠 명령 뒤 `LED_HOLD_S`(기본 = `MOTION_DURATION_S` 2초, `PICAR_LED_HOLD_S`)에 3채널 전부 소등. 0 이하면 기능 끔
