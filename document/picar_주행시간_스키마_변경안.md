## 안건 1. picar가 언제 멈춰야 하는지 아무도 정해주지 않는다

### 문제

`picar_command.schema.json`에는 `motor.action`(전진/후진/좌/우/정지)과 `motor.speed`만 있고
**주행을 언제 끝낼지에 대한 필드가 없습니다.**

그래서 지금 계약대로라면 picar는 이렇게 동작합니다:

```
"서행" 판정 → web이 {action: "forward", speed: 40} 전송 → picar 전진 시작
                                                        → ...계속 전진...
                                                        → 다음 명령이 올 때까지 계속 전진
```

다음 명령은 **학습자가 다음 수신호를 맞출 때까지** 오지 않습니다. 그 사이 차는 계속 달립니다.
시연장에서 벽이나 사람 쪽으로 돌진합니다.

`services/web`의 상태머신도 정지 명령을 따로 보내지 않습니다 — 보낼 근거가 계약에 없으니까요.

### 현재 임시 조치 (2026-09-21 구현)

`services/picar/src/controller.py`가 주행 명령 후 **2초 뒤 자동 정지**시킵니다
(`MOTION_DURATION_S`, `PICAR_MOTION_DURATION_S` 환경변수로 조정 가능).

안전장치일 뿐이고, **2초라는 값에는 근거가 없습니다.** 게다가 picar 서비스가 "서행은 얼마나
달려야 하는가" 같은 교육 설계 판단을 떠안고 있는 것도 이상합니다 — 그건 상태머신(web)이나
기획의 몫입니다.

### 대안 비교

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A** | 스키마에 `duration_ms` 추가, 보내는 쪽(web)이 신호별로 지정 | 신호마다 다르게 줄 수 있음. 교육 설계 판단이 web에 남음. 계약이 자기설명적 | 스키마 변경 → 전원 리뷰 필요 |
| **B** | 스키마 그대로 두고 picar가 고정 시간으로 자동 정지 (현재 임시 조치) | 스키마 안 건드림 | 신호별 차등 불가. 교육 판단이 하드웨어 서비스에 박힘 |
| **C** | web이 주행 명령 후 N초 뒤 별도 `stop` 명령 전송 | 스키마 안 건드림. web이 타이밍 제어 | 🔴 **정지 명령이 유실되면 차가 영원히 달림.** picar 통신은 500ms 타임아웃 + 1회 재시도 후 실패를 그냥 넘기는 정책(§7)이라 유실이 정상 시나리오다 |

### 권고: A + B 병행 (fail-safe)

- `duration_ms`를 **선택 필드**로 추가하고, 보내는 쪽이 지정하면 그 값을 쓴다 (A)
- **생략되면 picar가 자체 기본값으로 자동 정지한다** (B를 폴백으로 유지)

이렇게 하면 구버전 메시지가 오거나 web이 필드를 빠뜨려도 **차가 무한히 달리는 일은 없습니다.**
C안은 "정지 명령 유실 = 폭주"라서 채택하지 않기를 권합니다.

### 제안 스키마 변경

```diff
 "motor": {
   "type": "object",
   "required": ["action", "speed"],
   "properties": {
     "action": { "type": "string", "enum": ["stop", "forward", "backward", "left", "right"] },
     "speed": { "type": "integer", "minimum": 0, "maximum": 100,
                "description": "%, slow 명령은 정상보다 낮은 고정값 — ⚠️ 실측 후 확정" },
+    "duration_ms": {
+      "type": "integer", "minimum": 0, "maximum": 5000,
+      "description": "주행 지속 시간(ms). 이 시간이 지나면 picar가 스스로 정지한다. 생략하면 picar의 기본값(PICAR_MOTION_DURATION_S, 현재 2000ms)이 적용된다 — 어떤 경우에도 무한 주행은 하지 않는다. action=stop이면 무시된다."
+    }
   }
 }
```

`required`에 넣지 않으므로 **기존 메시지와 호환**됩니다.

### 신호별 제안값 (잠정 — 실물 주행 후 조정)

| 신호 | action | speed | `duration_ms` 제안 | 근거 |
| --- | --- | --- | --- | --- |
| 정지 | stop | 0 | — | 정지엔 불필요 |
| 서행 | forward | 40 | **1500** | "천천히 가고 있다"가 보이려면 직진은 좀 길어야 함 |
| 좌회전_유도 | left | 60 | **800** | 제자리 회전이라 짧아도 방향 전환이 크게 보임 |
| 우회전_유도 | right | 60 | **800** | 위와 동일 |
| 확인_완료 | stop | 0 | — | LED만 사용 |
| 후진 | backward | 50 | **1200** | 직진 계열이라 서행보다 약간 짧게 |
| 주의 | stop | 0 | — | LED만 사용 |

전부 1.5초 이하로 잡았습니다 — 이유는 안건 2와 연결됩니다.

## 안건 2. (확인 요청) "물리 피드백 지연 P95 ≤ 2.0초" KPI가 지금 정의대로면 달성 불가능해 보입니다

> 이건 제가 KPI 정의를 잘못 읽은 것일 수 있어 **확인 요청**으로 올립니다. 제 해석이 맞다면
> 정의 문구를 고쳐야 하고, 틀렸다면 제가 이해를 고치면 됩니다.

### 현재 정의 (10_PRD_v2 §2.1)

> 물리 피드백 지연 (P95) ≤ 2.0초 — 손 정지 시점 → **AI Hand + picar + micro:bit 중 가장 늦게
> 완료되는 시점**까지

문제는 **"완료"** 입니다. 이걸 "동작이 끝난 시점"으로 읽으면, 실측 가능한 구간들만 더해도
이미 2초를 넘습니다:

| 구간 | 소요 | 출처 |
| --- | --- | --- |
| 손 정지 → 판정 확정 | ≤ 1.0초 | 판정 지연 KPI 목표값 (§2.1) |
| web 폴링 간격 | ~0.2초 | `state_machine.py`의 `POLL_INTERVAL_S = 0.2` |
| AI Hand 제스처 완료 | ~1.0초 | 펌웨어 `setHand()` — 손가락 5개 × 200ms 순차 이동 (동시 구동 금지 제약 때문에 줄일 수 없음) |
| micro:bit LED 표시 완료 | 2.0초 | `showResult()` — O/X를 2초간 표시 후 소등 |
| picar 주행 완료 | duration_ms | 안건 1 |
| **합계 (LED 기준)** | **약 4.2초** | |

즉 **picar 주행 시간을 0으로 놓아도** micro:bit LED 표시(2초)만으로 이미 KPI를 넘습니다.

### 짚어둘 점

- 손가락 200ms 순차 이동은 **줄일 수 없습니다.** micro:bit v2 공급 전류(~300mA) < 서보 1개 stall
  전류(700mA)라 동시 구동하면 전압 강하로 BLE가 끊깁니다 (03_인터페이스계약서 §5-3).
- LED 2초 표시도 줄이면 학습자가 정오답을 놓칩니다.

### 제안

"완료"를 **"피드백이 시작되어 학습자가 인지할 수 있게 된 시점"** 으로 바꾸면 현실적입니다:

> 물리 피드백 지연 (P95) ≤ 2.0초 — 손 정지 시점 → AI Hand·picar·micro:bit **각 장치가 반응을
> 시작한 시점 중 가장 늦은 것**까지 (동작이 끝날 때까지가 아님)

이 정의라면 판정(1.0) + 폴링(0.2) + BLE 전송(~0.3) ≈ 1.5초로 달성 가능성이 있습니다.
그리고 이 경우 **picar `duration_ms`는 KPI와 무관해지므로** 안건 1의 값들을 교육 효과 기준으로만
자유롭게 정하면 됩니다.

**결정해야 할 것**: 위 재정의를 채택할지, 아니면 현행 정의를 유지하고 목표치를 올릴지(예: 5초).
어느 쪽이든 06_테스트기록·07_평가리포트의 측정 방법이 여기에 맞춰져야 합니다.

## 안건 3. (부수) `확인_완료`의 LED 패턴을 현재 스키마로 표현할 수 없다

`수신호에 따른 picar 동작.md`는 확인_완료를 이렇게 정의합니다:

> 양쪽 빨간색 LED 노란색 LED를 **번갈아** 2회 점멸 후 LED 꺼버린다

그런데 스키마의 `led`는 LED별로 `off`/`on`/`blink` 하나씩만 지정할 수 있어서 **시퀀스(순서·횟수)를
표현할 수 없습니다.** 지금 web은 `red: blink, yellow_left: blink, yellow_right: blink`를 보내고
있어서 실제로는 "**번갈아**"가 아니라 "**동시 점멸**"이 됩니다.

| 안 | 내용 | 비용 |
| --- | --- | --- |
| **A** | 현행 유지 — "동시 점멸"로 사양을 낮추고 `수신호에 따른 picar 동작.md`를 수정 | 없음 |
| **B** | `led.pattern: "alternate"` 같은 열거값 추가, picar가 패턴을 해석 | 스키마 + picar 구현 소폭 |
| **C** | LED 시퀀스를 배열로 표현 (`[{red:"on",...,ms:300}, ...]`) | 스키마 구조 변경, 과설계 우려 |

**권고: A.** 확인_완료는 "교육 1회차 종료" 신호라 연출 디테일보다 동작 여부가 중요하고,
B/C는 지금 남은 일정(W4 ~10/04) 대비 비용이 큽니다. 다만 결정은 기획(이동혁)·web(조은수)의 몫입니다.
