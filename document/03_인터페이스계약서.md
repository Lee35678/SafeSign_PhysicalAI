## 1. 시스템 구성 요소

```
[Raspberry Pi 5 — 학습자 앞 고정 스테이션]
[Pi Camera Module 3] → [Perception: MediaPipe (LIVE_STREAM)] → [Cognition: 분류기] → [교육 상태머신] → [Actuation: AI Hand / micro:bit]
                                                ↕                                              │
                                          [수신호 DB]                                    Wi-Fi(HTTP)
                                                                                                │
                                                                                                ▼
                                                                          [Raspberry Pi 4B 8GB — picar 탑재]
                                                                                       [Actuation: picar]
```

RPi5(카메라·AI Hand·micro:bit, 고정)와 RPi4B 8GB(picar 탑재, 이동)는 물리적으로 분리된 두 보드이며
**Wi-Fi**로 통신한다 — picar가 움직이면 카메라도 함께 이동해버리는 문제를 피하기 위한 배치
(02_설계문서 §1-1, 2026-09-18).

## 2. 카메라 → Perception

> **확정**: **Raspberry Pi Camera Module 3**를 CSI로 RPi5에 직결한다 (15핀 카메라 케이블 →
> 22핀 변환 케이블 → RPi5 CAM/DISP 포트). 온보드 자체 분류 AI 카메라(WonderCam류)나 범용 USB 웹캠은
> 채택하지 않는다 — 리스크 레지스터의 "카메라가 랜드마크 좌표를 못 내줌" 항목은 이 결정으로 해결됨.
> 

| 항목 | 스펙 |
| --- | --- |
| 장치 | Raspberry Pi Camera Module 3 (CSI, 15핀→22핀 변환 케이블) |
| 입력 | 계약값 **1920×1080 @ 60fps (Binned Mode)** (2026-09-18). vision 서비스 기본값은 **1280×720 @ 30fps** — `CAPTURE_SIZE`/`CAPTURE_FPS`로 계약값 전환 (`services/vision/src/perception/capture.py`) |
| 출력 | 21 keypoints × (x, y, z) |
| MediaPipe 실행 모드 | `LIVE_STREAM` (05_모델카드 §3-2 — 실시간 성능 우선, `VIDEO` 동기 루프 대비 캡처-추론 분리) |

> **실무 참고**: 카메라 캡처 자체는 1080p@60fps로 동작하지만, RPi5에서 MediaPipe 추론을 매 프레임(60fps)
> 그대로 돌릴 필요는 없다 — `LIVE_STREAM` 콜백이 처리 가능한 속도로 프레임을 서브샘플링하거나, 추론
> 직전에 축소본을 만들어 넘기는 방식을 권장한다. 실제 추론 처리율은 실측 후 05_모델카드 §3-3에
> 반영하고, 판정 지연(P95 ≤ 1.0초) 미달 시 이 지점을 우선 점검한다.
> 

## 3. Perception → Cognition (랜드마크 스키마)

```json
{
  "timestamp": 12345,
  "captured_at_ms": 1789000000000,
  "hand_detected": true,
  "handedness": "Right",
  "landmarks": [
    {"id": 0, "x": 0.0, "y": 0.0, "z": 0.0},
    "... (21개)"
  ]
}
```

필수: `timestamp`, `hand_detected`, `landmarks` / 선택: `captured_at_ms`, `handedness` (`landmark_frame.schema.json`)

- `timestamp`(필수, 정수): ms 단위 **단조 증가** 카운터 — MediaPipe `LIVE_STREAM`이 요구하는 프레임 타임스탬프 (05_모델카드 §3-2)
- `captured_at_ms`(선택, 정수): 벽시계 기준 캡처 시각(ms). **판정 지연 측정용** — `timestamp`는 단조 증가 카운터라 지연 계산에 쓸 수 없다
- `hand_detected`(필수, boolean)
- `handedness`(선택): `"Right" | "Left"`, 기본 `"Right"`. 정규화 단계에서 **왼손을 오른손 기준으로 미러링**하는 데 필요 (05_모델카드 §3-5 4번)
- `landmarks`(필수, 0~21개): 각 항목 `id`(0~20)·`x`·`y`·`z` 필수. `hand_world_landmarks`(실세계 미터 단위 3D). `hand_detected=false`면 빈 배열

> ⚠️ `captured_at_ms`·`handedness`는 2026-09-18에 추가됐다. 문서상 정규화 절차(§3-5 4번)가 좌우 손
> 판별을 요구하는데 기존 스키마에 그 정보가 없었고, 지연 KPI도 벽시계 기준 시각이 없으면 측정할 수
> 없어서 보완한 것이다.

## 4. Cognition → 교육 상태머신 (판정 결과 스키마)

```json
{
  "predicted_class": "string (수신호 이름 또는 'negative')",
  "confidence": 0.0,
  "match_score": 0,
  "is_reject": false,
  "latency_ms": 0,
  "reason": "below_tau",
  "consecutive": 2,
  "class_probabilities": {
    "정지": 0.0, "서행": 0.0, "좌회전_유도": 0.0, "우회전_유도": 0.0,
    "확인_완료": 0.0, "후진": 0.0, "주의": 0.0
  }
}
```

필수: `predicted_class`, `confidence`, `match_score`, `is_reject`, `latency_ms` / 선택: `reason`, `consecutive`, `class_probabilities` (`judgment_result.schema.json`)

> ✅ **`class_probabilities` — 2026-09-30 추가, 구현된 선택 필드** (2026-10-04 "제안" 표기 정리). vision(`classify.predict`)·web(`_target_score`)
> 구현과 스키마 파일 반영이 끝났다. **학습자 화면의 "일치율"은 이 값 중 목표 수신호의 확률 × 100**이다([05 §10-8](05_모델카드.md)).
> 바꾼 이유: `match_score`(예측 클래스 템플릿과의 코사인)는 7종을 가르는 값이 아니어서(주의↔우회전 대표 손끼리 0.958) 오답인데 85~99%,
> 정답인데 50%대가 나왔다. `match_score`는 하위 호환·참고용으로 남기고, 시행 로그 CSV에는 원값(`match_score`)과 화면 값(`target_score`)을
> 둘 다 남긴다. 이 필드의 팀 확인 항목은 15 TODO에 아직 남아 있다.

- `predicted_class`(필수, 문자열): 수신호 이름(7종, §5-1 enum과 같은 표기) 또는 `"negative"`
- `confidence`(필수, 0~1 실수)
- `match_score`(필수, 0~100 정수): ~~일치율(유사도) 점수 (계획서 KPI 항목). 예측 클래스의 템플릿과의 cosine similarity를 매핑~~
  (→ 2026-09-30 정정: **학습자 화면의 일치율이 아니다** — 화면 일치율은 아래 `class_probabilities`의 목표 수신호 값 × 100(web
  `state_machine._target_score`, [05 §10-8](05_모델카드.md)). `match_score`는 하위 호환·시행 로그 원값으로 남는 참고값이다:
  예측 클래스 템플릿(템플릿 DB, 없으면 모델 번들 centroid)과의 cosine similarity를 **클래스별 구간**(그 클래스 학습 표본의
  P1~P95, 없으면 공통 P5~P95)으로 0~100에 선형 매핑, 템플릿이 없으면 0 — `templates.match_score`).
  예측 클래스 기준이라 오답일 때도 높게 나올 수 있어 화면 일치율로 쓰지 않는다.
  ⚠️ 스키마 파일의 `match_score` 설명은 아직 옛 문구("일치율(유사도) … cosine similarity를 매핑한 값")다 — 뜻은 이 문서를 따른다
- `class_probabilities`(선택, 객체): 분류기가 본 7종별 확률 — 판정(`confidence`·τ)에 쓰는 바로 그 값(2026-09-30, `classify.predict`)
  - **키**: 수신호 이름 7종(§5-1 `target_signal` enum과 같은 표기). `negative`는 없다(학습 클래스가 아님, 02 §4)
  - **값**: 0~1 실수, 소수 4자리 반올림. 분류기(SVM + Platt 보정, [05 §6](05_모델카드.md))의 `predict_proba` 그대로라 **7개 합은 약 1**
    (반올림 오차만큼 어긋날 수 있다). `confidence`는 이 중 가장 큰 값이다
  - **있는 경우**: 분류기가 돌고 소속 게이트를 통과했을 때 — 정상 판정, `below_tau`, `awaiting_consecutive_frames`
  - **없는 경우**: 분류기 전에 멈춘 `no_hand`·`normalize_failed`·`model_not_loaded`·`inference_error`, 그리고 **게이트 차단 `out_of_distribution`**
    ("다른 수신호" 안내와 높은 확률이 함께 보이지 않게 일부러 뺀다). 없으면 web은 `match_score`로 대신한다(`_target_score`)
  - 스키마 파일은 값 범위(0~1 숫자)만 검사하고 키 이름·개수는 강제하지 않는다(`additionalProperties`)
- `latency_ms`(필수, 0 이상 정수): 캡처 → 판정 확정까지(ms)
- `is_reject`(필수, boolean): 미판정 여부 (미판정률 계산에 사용). τ 미달뿐 아니라 손 미검출·N프레임 미충족도 포함
- `reason`(선택, is_reject=true일 때): `no_hand` · `normalize_failed` · `model_not_loaded` ·
  `inference_error` · `below_tau` · **`out_of_distribution`** · `awaiting_consecutive_frames`
  - `awaiting_consecutive_frames`: N프레임을 채우는 중인 과도 상태 — 오답이 아니며 web은 오버레이 없이 대기
  - **`out_of_distribution`** (2026-09-22 추가): 손은 잡혔지만 **7종 어디에도 속하지 않는 손모양**.
    1단계 소속 게이트가 차단한 경우다. `below_tau`("맞는 것 같은데 확신이 부족")와 구분된다 —
    이쪽은 "아예 우리가 아는 수신호가 아니다"라는 뜻이라, 화면 문구를 다르게 주는 편이 좋다
    (예: below_tau → "조금 더 정확히 해주세요" / out_of_distribution → "다른 수신호를 하고 계세요").
    웹 상태머신 입장에서는 둘 다 SC-03b(재시도 유도)로 묶어도 동작에는 문제가 없다.
    근거·동작점은 05_모델카드 §3-7.
  → 웹 상태머신이 **SC-04(카메라 인식 실패: `no_hand`/`normalize_failed`)** 와
  **SC-03b(재시도 유도: `below_tau` 등)** 를 구분하는 근거. 2026-09-18 추가.
- `consecutive`(선택): 현재 연속 동일 판정 프레임 수 — N프레임 안정화(05_모델카드 §3-6) 진행도
- 판정 지연(P95 ≤ 1.0초) 측정 기준점: `captured_at_ms` → 이 스키마 확정 시점. 연속 판정을 확정한 **마지막 프레임 1장** 기준이라
  N프레임을 채우는 시간·web 폴링 대기는 빠진다 — 09-30 회의에서 현행 유지 + 한계 명시로 결정, 스키마 필드는 추가하지 않음([16 §5.6](16_통합테스트_KPI_CI.md) #1)

### 5-1. AI Hand 제어 명령 (초안)

```json
{
  "command": "demo | correct_pose",
  "target_signal": "정지 | 서행 | 좌회전_유도 | 우회전_유도 | 확인_완료 | 후진 | 주의",
  "servo_angles": {
    "thumb": 170, "index": 170, "middle": 170, "ring": 170, "pinky": 170,
    "wrist_rotation": 90
  }
}
```

필수: `command`, `target_signal`, `servo_angles`(6개 키 전부) — `aihand_command.schema.json`

- `target_signal` enum은 위 7개(밑줄 표기)이며 §5-2·§4 `predicted_class`와 같은 문자열이다.
- `servo_angles`: 손가락 5개 **10~170 정수**, `wrist_rotation` 0~180(기본 90). **필수 필드로 유지하지만
  actuation은 쓰지 않는다** — `target_signal`만 보고 `G{n}`(§5-3)을 보내며, 실제 각도는 펌웨어가 정한다
  (손가락별 가동범위 [11 §4.3](11_하드웨어설계서.md)). web은 스키마를 맞추려 자리표시값을 보낸다.

> **초기 기본값 (2026-09-18, 실물 캘리브레이션 전 잠정)**: 서보는 0~180° 범위지만, 양 끝단(0°/180°)에
> 반복적으로 붙이면 기어/서보혼에 기계적 스트레스가 누적되므로 여유를 두고 **펴짐(EXTENDED)=170°,
> 굽힘(CURLED)=10°**의 이진값만 사용한다. 손목은 이번 7종 판별에 사용하지 않으므로(02_설계문서 §4
> 참고사항 4) 항상 **중립 90°**로 고정한다. AiHand 실물 수령 후 이 값들은 실제로 각 손가락이 눈으로 봐도
> "펴짐/굽힘"으로 보이는지 확인해 조정하세요(구조는 유지, 각도 수치만 보정).

| --- | --- | --- | --- | --- | --- | --- |
| 정지 | 170 | 170 | 170 | 170 | 170 | 90 |
| 서행 | 10 | 170 | 170 | 10 | 10 | 90 |
| 좌회전_유도 | 170 | 170 | 10 | 10 | 10 | 90 |

### 5-2. picar 제어 명령 — RPi5 ↔ RPi4B Wi-Fi 통신 (확정, 2026-09-18)

> 02_설계문서 §4 "수신호 확정안(통합 7종 + picar 동작)" 표를 그대로 구현에 반영. `command`는 표의 picar 동작 열과 1:1 대응.
>
> ⚠️ **정정**: 이전 버전은 "RPi5가 picar를 GPIO로 직접 구동"이라고 기술했으나, picar가 움직이면 카메라도
> 함께 이동해버리는 문제 때문에 picar 컴퓨트 보드를 **Raspberry Pi 4B 8GB로 분리**했다(02_설계문서
> §1-1). 아래 스키마는 이제 **네트워크 메시지**이며, RPi5의 교육 상태머신이 RPi4B의 HTTP 엔드포인트로
> 전송한다.

**검토한 대안**: MQTT(pub/sub, 재연결 로직 내장) vs HTTP REST(기존 FastAPI 마이크로서비스 구조 재사용).
**기준**: 1:1 통신(브로커가 중개할 다수 구독자가 없음)이라 pub/sub 이점이 작고, 브로커(mosquitto 등)를
새로 설치/운영하는 부담을 피하고 싶었다. **선택**: **HTTP REST(POST)**, 이미 만들어둔 FastAPI 서비스
구조를 그대로 재사용.

#### picar 내부 — 모터 I2C 프로토콜 (2026-09-21 확보)

RPi4B가 `picar_command`를 받은 뒤 실제로 모터를 돌리는 방법이다. 서비스 간 계약은 아니지만,
**`motor.action`/`motor.speed`가 하드웨어에서 어떻게 해석되는지**를 남겨 둔다.

모터는 RPi4B GPIO 직결이 아니라 **I2C 코프로세서(bus 1, `0x16`)** 경유다. LED만 GPIO 직결이다
(적색 BCM13·BCM19 / 황색 좌 BCM5 / 황색 우 BCM6, 보드 내장 BCM21·BCM20은 미사용).
- `services/picar`가 `motor.speed`(%)를 코프로세서 `0~255`로 변환한다. 좌/우 회전은 제자리 회전(한쪽 전진 + 반대쪽 후진).
- 레지스터·바이트 포맷·주소 확인 절차는 [11 §5.2](11_하드웨어설계서.md), 핀맵은 [11 부록 A](11_하드웨어설계서.md).

✅ **주행 종료는 picar가 정한다 (2026-09-27 결정).** 스키마에는 주행 지속 시간 필드가 없고, 추가하지 않기로
했다(`duration_ms` 미채택 — `document/proposals/picar_주행시간_스키마_변경안.md` 안건 1). `services/picar`가
주행 명령 후 `PICAR_MOTION_DURATION_S`(기본 2초) 뒤 자동 정지한다. 이 값이 없으면 다음 명령이 올 때까지
차가 계속 달리므로 **picar 쪽 자동 정지를 끄지 말 것.**

```json
{
  "command": "stop | slow | turn_left | turn_right | reverse | caution | complete",
  "target_signal": "정지 | 서행 | 좌회전_유도 | 우회전_유도 | 확인_완료 | 후진 | 주의",
  "motor": {
    "action": "stop | forward | backward | left | right",
    "speed": 0
  },
  "led": {
    "red": "off | on | blink",
    "yellow_left": "off | on | blink",
    "yellow_right": "off | on | blink"
  }
}
```

| 항목 | 값 |
| --- | --- |
| 전송 방식 | HTTP POST, RPi5 AP ↔ RPi4B 1:1 Wi-Fi 직결 |
| 엔드포인트 | 실물: `POST http://192.168.50.10:8000/picar` (web `PICAR_URL`). docker-compose 개발 PC에서는 호스트 포트 `8003`(컨테이너 내부 8000) |
| Body | 위 JSON (picar_command.schema.json) |
| 요청 타임아웃 | **500ms** — 물리 피드백 지연 예산(P95 ≤ 2.0초) 안에서 Wi-Fi 왕복 실패를 빠르게 감지하기 위함 |
| 재시도 | 1회만 재시도 후 포기 (ACK 왕복을 여러 번 반복하지 않음 — micro:bit와 동일하게 "실패하면 다음
  이벤트에서 다시 시도"하는 self-healing 방침, §5-3 참고) |
| 실패 시 | picar 없이 AI Hand + micro:bit로 진행 (§7 폴백) |

필수: `command`, `target_signal`, `motor`(`action`, `speed`), `led`(`red`, `yellow_left`, `yellow_right`) 전부 — `picar_command.schema.json`

- `motor.speed`: **0~50 정수(%)**. 확정값 서행 20 / 좌·우회전·후진 40 / 정지류 0 (2026-09-23 바닥 주행,
  [13 §4.5](13_picar_하드웨어_검증리포트.md)). 상한 50은 picar의 `PICAR_MAX_SPEED` 기본값과 같다 — 한쪽을 바꾸면 함께 바꾼다.
- `command`와 `motor`/`led` 조합은 02_설계문서 §4 표 참고 (예: `stop` → `motor.action=stop`, `led.red=on`)
- 스키마상 `motor`·`led`는 필수지만, picar는 둘이 객체가 아니면(`null` 등) **없는 것으로** 받아 안전한 쪽으로 처리한다 —
  LED 3채널 `off`, 모터 `stop`(2026-10-03 `899f6ba`).
- IP는 고정 IP로 확정: RPi5 `192.168.50.1` / RPi4B `192.168.50.10` ([07_네트워크설정법](07_네트워크설정법.md), [11 §6.1](11_하드웨어설계서.md))

**응답 (참고, 스키마 없음)** — `services/picar/src/controller.py` `execute()`

| 필드 | 값 | 의미 |
| --- | --- | --- |
| `status` | `ok` \| `partial` | 모터가 성공(`ok`/`mocked`)이면 `ok`, 아니면 `partial`. **LED 실패는 반영되지 않는다** — `led.*`를 따로 볼 것 |
| `motor.status` / `motor.reason` | `ok`·`mocked`·`error` / `i2c_failed`·`invalid_speed`·`unknown_motor_action` | 모터 결과 |
| `motor.speed_capped_from` | 정수(있을 때만) | 요청 속도가 상한을 넘어 잘렸을 때 원래 요청값 |
| `motor.auto_stop_s` | 초(주행 시) | 주행 명령 후 자동 정지까지 시간(기본 2.0, `PICAR_MOTION_DURATION_S`) |
| `led.<채널>.status` / `.reason` | `ok`·`mocked`·`error`·`unsupported` / `gpio_failed`·`unknown_led_state` | LED 결과 — 실패해도 모터는 실행됨 |
| `led_hold_s` | 초 \| `null` | LED를 하나라도 켠 명령이면 이 시간 뒤 picar가 **3채널을 전부 끈다**(기본 2.0, `PICAR_LED_HOLD_S`, 2026-09-28). 전부 `off`였거나 기능을 끄면 `null`. web은 LED를 끄는 명령을 따로 보내지 않는다 |

> web은 본문 `status`까지 보고 성공/실패를 가른다 — 판정 기준은 **§5-5**(2026-09-28), web 구현 `c8f1fd3`(이동혁, 2026-09-28).

### 5-3. micro:bit BLE 프로토콜 (2026-09-21 갱신 — 시리얼에서 BLE로 전환)

> ⚠️ **정정**: 이 문서가 2026-09-18에 확정했던 방식은 **USB 시리얼(115200 baud, 8N1)** 이었다. 그런데
> 실제 구현에 착수한 뒤 이 방식이 성립하지 않는다는 것이 실측으로 드러나, **BLE로 전환**했다.

**전환 이유**

micro:bit v2의 하드웨어 UART 1개를 StartbitV2 서보 초기화(`startbit_Init()`)가 서보 채널(P12/P8)로
가져가 **서보를 구동하는 순간 USB 시리얼이 죽는다**. I2C·여유 GPIO 시리얼도 검토한 뒤 **BLE(Nordic UART
Service)**를 채택했다. 상세 근거는 [11 §4.5](11_하드웨어설계서.md)·`services/actuation/doc/aihand_gesture_checklist_final.md` 세션 1~2.

**연결 방식**

- 통신 방식: **BLE**, Nordic UART Service(NUS) 프로파일. 단, 이 micro:bit 펌웨어(MakeCode Bluetooth
  확장)는 표준 NUS와 달리 RX/TX 캐릭터리스틱 UUID가 **반대로 배정**되어 있다 — 표준상 TX인
  `6e400003`이 실제로는 **쓰기용(PC/RPi → micro:bit)**, 표준상 RX인 `6e400002`가 실제로는
  **알림용(micro:bit → PC/RPi)**이다. 실측으로 확인된 값이며(세션 4), 표준 NUS 예제 코드의 UUID를
  그대로 가져다 쓰면 통신이 되지 않는다.
- 메시지는 텍스트, `\n`(LF)로 종료. 콜론 구분자는 쓰지 않는다 — 운영 펌웨어는 micro:bit의 협소한
  RAM에서 파싱 비용(힙 할당)을 줄이기 위해 `G1`~`G7`처럼 최소 글자 수만 사용한다(세션 8).

**RPi → micro:bit** (제스처 실행 지시)

```
G1\n ~ G7\n    예) G3\n   (수신호 7종에 대응하는 제스처 번호)
```

- `target_signal`(수신호 이름) ↔ `G{n}` 매핑: `services/actuation/src/aihand/controller.py`의
  `GESTURE_MAP` 참고. 매핑 순서는 02_설계문서 §4 표와 동일하다(정지 G1 · 서행 G2 · 좌회전_유도 G3 ·
  우회전_유도 G4 · 확인_완료 G5 · 후진 G6 · 주의 G7). 우회전_유도(G4)는 펌웨어대로 "엄지+소지"이며
  02_설계문서 §4도 같게 정정돼 있다.

**RPi → micro:bit** (판정 결과 / 진행 표시)

```
correct\n              판정 결과 LED에 O 표시(1초) 후 소등 (부저 없음 — 아래 참고)
incorrect\n            판정 결과 LED에 X 표시(1초) 후 소등 (부저 없음 — 아래 참고)
P<current><total>\n    예) P37\n   (3/7번째 — 둘 다 한 자리 숫자, 7종 고정이라 콜론 없이 붙여 씀)
```

- `correct`/`incorrect`는 기존 시리얼 설계의 `RESULT:<OK|NG>:<match_score>`를 대체한다. **다만
  match_score는 전달하지 않는다** — 펌웨어가 LED로는 정오답 여부만 표시하고 점수는 쓰지 않기 때문.
  match_score는 web 화면 쪽에서 별도로 표시한다. (→ 2026-10-04 보충: web이 actuation `/result`에 싣는 `match_score`는
  화면 일치율 — 목표 수신호 확률 × 100, §4 — 이다. actuation은 이 값을 펌웨어로 보내지 않는다.)
- **`correct`/`incorrect`는 회신(`OK:CORRECT`/`OK:INCORRECT`)을 LED 표시보다 먼저 보낸다**(2026-09-23).
  종전에는 LED 표시가 끝난 뒤 회신해 RPi의 응답 대기(2.0초)를 넘겨 매번 timeout이었다. LED 표시는
  펌웨어가 백그라운드로 돌리므로 **표시 중에도 다음 명령을 바로 받는다** — 호출 측은 LED 1초를 기다릴
  필요 없이 곧바로 다음 `G{n}`을 보내도 된다(실측 회신 26~42ms, `11_하드웨어설계서.md` §4.5.
  ~~백그라운드화는 재검증 대기~~ → 2026-09-25 재검증 통과 — `correct` 직후 명령 1424ms → 36~39ms, 11 §4.5).
- `P<current><total>`은 기존 시리얼 설계의 `PROGRESS:<current>:<total>`을 대체한다. **LED 표시는
  하지 않는다**(2026-09-21 결정, 진행 표시는 web 화면 담당) — micro:bit는 수신 확인(`OKP<current><total>`)만
  회신한다.
- 🔴 **소리 피드백은 사용하지 않는다 — 하드웨어 제약으로 확정 (2026-09-22).** BLE SoftDevice와
  `music`이 같은 타이머/PWM을 공유해 `music.*` 호출 시 패닉 070이 나고 BLE가 끊긴다(우회 불가).
  `bluetooth.startUartService()` 이후 `music.*` 호출 금지, 판정 피드백은 **LED O/X만** 사용한다.
  재현·검증 경위는 [11 §4.7](11_하드웨어설계서.md).

**micro:bit → RPi** (완료 응답)

```
OK<n>\n              예) OK3\n           (G{n} 제스처 실행 완료 — 손 동작이 끝난 **뒤** 회신, 실측 약 0.80초)
OK:CORRECT\n / OK:INCORRECT\n           (correct/incorrect 처리 완료)
OKP<current><total>\n예) OKP37\n         (P<current><total> 처리 완료)
```

**micro:bit → RPi** (버튼 입력 — 요청 없이 올라옴, 2026-09-28)

```
BTN:A\n              버튼 A를 누를 때마다 1회 (web 확인 버튼 대용)
```

- 기존 시리얼 설계의 `BTN:A|B|AB` 중 **A만** 쓴다. B는 TEST_MODE 전용(`READY` 재표시)이라 올리지 않는다.
- 펌웨어는 버튼을 눌러도 **LED를 쓰지 않는다** — 긴 표시가 O/X 1초 표시와 화면을 두고 부딪힌다. 눌렸다는
  피드백은 web 화면 전환이 대신한다.
- 🔴 **회신과 섞으면 안 된다.** RPi의 회신 대기는 한 줄짜리 칸 하나라, 명령 회신을 기다리는 중에 `BTN:A`를 회신으로
  받으면 AI Hand가 아직 움직이는데 `/command`가 `ok`로 돌아가고 버튼 입력은 사라진다. `ble_bridge._on_notify`는 알림을
  **줄 단위로 나눠** `BTN:`으로 시작하는 줄은 회신에서 빼고 누른 횟수(`seq`)만 올린다. 알림 한 번에 두 줄이 붙어
  와도(`OK3\nBTN:A\n`) 각각 처리한다. 모든 줄이 알림 한 번(20바이트)보다 짧아 알림 사이에 걸쳐 잘리는 경우는 없다.

**손가락 서보 동시 구동 제한 (BLE 연결 안정성)**

- 손가락 서보를 동시에 기동하면 같은 레일의 micro:bit가 브라운아웃되어 BLE가 끊긴다. 그래서 펌웨어는
  손가락을 **150ms 간격으로 하나씩 출발**시킨다(인접 2개까지만 겹침, 제스처 약 0.80초 — 2026-09-23 확정,
  종전 200ms 완전 순차). 간격 변경은 전류 재계산·연속 검증 없이 하지 않는다. 전류 계산은 [11 §4.4](11_하드웨어설계서.md).

**에러 처리 정책 (물리 피드백 지연 P95 ≤ 2.0초 KPI를 고려한 설계 — 시리얼 방식과 동일 기조 유지)**

- RPi는 `G{n}` 전송 후 `OK{n}` 응답을 최대 2초 대기하지만(`ACK_TIMEOUT_S` — `G{n}`은 손 동작 후
  회신이라 실측 0.80초가 이 대기 안에 들어가야 한다), 왕복 재확인(ACK) 프로토콜을 반복하지는
  않는다 — 응답이 오지 않으면 타임아웃으로 처리하고 다음 이벤트에서 다시 시도한다(self-healing,
  `services/actuation/src/microbit/ble_bridge.py`).
- **회신은 보낸 명령의 기대 ACK만 인정한다**(2026-10-03 `d81948b`): `G{n}` → `OK{n}`, `correct` → `OK:CORRECT`,
  `incorrect` → `OK:INCORRECT`, `P{c}{t}` → `OKP{c}{t}`. 맞지 않는 줄은 버리고 `ACK_TIMEOUT_S` 안에서 계속 기다린다 —
  시간 초과로 버려진 앞 명령의 늦은 회신(예: `OK3`)이 다음 명령의 ACK로 잡히지 않게. 버린 줄은 actuation 응답의
  **선택 필드 `ignored`**(문자열 배열, 버린 줄이 있을 때만)에 남는다. `BTN:` 줄은 여기에 들어가지 않는다(위 버튼 입력).
- BLE 쓰기 실패(연결 끊김 등) 시: RPi가 재연결을 1회 시도한 후 다시 전송한다. 재시도 후에도 실패하면
  에러 상태를 반환하고 다음 이벤트에서 자연 복구된다. 재연결 전에 이전 연결은 끊고 새로 잡는다(2026-10-03 `d81948b`).
- 이 설계는 §5-2(picar)의 "타임아웃 + 1회 재시도, 실패해도 학습 흐름 계속" 방침과 동일한 기조를
  따른다.

이 설계는 별도 회의 없이 "피지컬 AI 제품에서 중요한 것은 왕복 확인이 아니라 다음 이벤트에서 항상
최신 상태가 다시 도착하는 것"이라는 원칙으로 정했다. micro:bit 담당자는 이후 실제 동작이 이 문서와
다르면(예: UUID가 바뀌었다는 등) 이 절을 갱신하세요.

### 5-5. 장치 응답 판정 기준 — web `_post_with_retry` (2026-09-28)

actuation·picar는 장치가 실패해도 **HTTP 200**에 본문 `status`로 결과를 알린다. web은 예전에 HTTP 200이면 전부
성공으로 셌으므로(14_web_구현보고서 §7), 아래 기준으로 **본문까지 판정**한다. 구현은 web 할 일 ③(이동혁, **2026-09-28 완료** `c8f1fd3`), 기준은
장치 담당(송승호)이 코드(`services/actuation/src/microbit/ble_bridge.py`, `services/picar/src/controller.py`)에서 정리했다.

**원칙**
1. **본문 `status`가 실패여도 재시도하지 않는다.** 명령이 이미 장치에 닿았을 수 있어, 다시 보내면 AI Hand가 두 번
   움직이거나 picar가 두 번 주행한다. 실패는 `last_dispatch`와 시행 로그 CSV에 **기록만** 한다. BLE 재연결·재전송은
   actuation이 이미 1회 해 두었다(§5-3).
2. **HTTP 층 실패는 종류를 나눈다.** 연결 실패(요청이 가지 않음)와 4xx/5xx(서버가 처리하지 못함)는 지금처럼 1회
   재시도한다. **읽기 타임아웃은 요청이 이미 갔을 수 있으므로 `/command`·`/picar`는 재시도하지 않는다** — 아래 ⚠️.
3. `mocked`는 성공으로 처리하되 **표시**한다. 실물 시험 중에 나오면 `MOCK_HARDWARE` 설정 누락이다.

**actuation — `/command` · `/result` · `/progress`** (응답 본문 `status`, 실패 시 `reason`)

| `status` | `reason` | 뜻 | web 판정 |
| --- | --- | --- | --- |
| `ok` | — | micro:bit가 회신함. `/command`는 **손 동작이 끝난 뒤**(실측 0.79~0.83초), `/result`는 회신 뒤 LED O/X 1초 표시 | ✅ 성공 |
| `timeout` | — | 전송은 했지만 `ACK_TIMEOUT_S`(2.0초) 안에 회신이 없음. **명령은 실행됐을 수 있다** | ❌ 실패 (재시도 안 함) |
| `error` | `microbit_unreachable` | BLE 연결 불가 (재연결 시도 후에도) | ❌ 실패 |
| `error` | `write_failed` | 전송 실패 (재연결 후 1회 재전송까지 실패) | ❌ 실패 |
| `error` | `unknown_target_signal` | web이 7종 밖의 `target_signal`을 보냄 — **web 버그** | ❌ 실패 |
| `mocked` | — | `MOCK_HARDWARE=true` | ✅ 성공 + 모의 표시 |
| `error` | `invalid_progress` | (`/progress`만) `current`·`total`이 0~9 정수가 아님 — BLE로 보내지 않음, **web 버그** (2026-10-03) | ❌ 실패 |

**요청 본문 검사 (2026-10-03 `899f6ba`)** — `/result` `{"is_correct": bool, "match_score": int}`: `is_correct`가 JSON `true`일 때만
`correct`를 보내고, 그 밖(누락·문자열 `"false"` 등)은 `incorrect`다. `/progress` `{"current": int, "total": int}`: 프로토콜이
`P<한 자리><한 자리>`(§5-3)라 둘 다 0~9 정수만 받는다. 회신 대조로 버린 줄이 있으면 응답에 `ignored`가 붙는다(§5-3).

**picar — `/picar`** (§5-2 응답 표 참고)

| 조건 | 뜻 | web 판정 |
| --- | --- | --- |
| `status: ok`, `motor.status: ok` | 모터 정상 | ✅ 성공 |
| `status: partial` | **모터 실패**(`motor.reason`: `i2c_failed` 등). LED는 처리됐을 수 있음 | ❌ 실패 (재시도 안 함 — 주행 재시도 여부는 picar 쪽에서 결정, [13 §5 #7](13_picar_하드웨어_검증리포트.md)) |
| `status: ok`인데 `led.<채널>.status: error` | LED만 실패(`gpio_failed` 등) — 최상위 `status`에 반영되지 않는다 | ✅ 성공(모터 기준) + **LED 실패 기록** |
| `motor.status: mocked` | 모의 모드 | ✅ 성공 + 모의 표시 |

**HTTP 층**

| 실패 | 요청이 장치에 갔나 | web 처리 |
| --- | --- | --- |
| 연결 실패 (`ConnectError` 등) | 안 갔음 | 1회 재시도 |
| 4xx / 5xx | 서버가 처리 못 함 | 1회 재시도 |
| **읽기 타임아웃** (`ReadTimeout`) | **갔을 수 있음** | `/command`·`/picar`: **재시도 안 함**, 실패로 기록. `/result`·`/progress`: 1회 재시도 허용(표시가 반복될 뿐) |

> ⚠️ **`/command` 이중 전송 위험 (2026-09-28 발견)** — web의 `/command` 타임아웃은 **1.5초**(C′안)인데 actuation은
> micro:bit 회신을 **2.0초**까지 기다린다. 그래서 회신이 1.5초를 넘기면 web은 actuation의 `timeout` 응답을 받기 전에
> 끊고 **재시도**하고, actuation은 두 번째 `G{n}`을 줄 세워 보내 **AI Hand가 같은 동작을 두 번** 한다. 정상 회신
> (약 0.8초)에서는 드러나지 않고 BLE가 느려질 때만 나타난다. → 위 표대로 **읽기 타임아웃 재시도를 막는 것**이 필수다
> (web `_post_with_retry(..., retry_read_timeout=False)`로 반영, 2026-09-28 `c8f1fd3`).
> (대안: actuation `ACK_TIMEOUT_S`를 1.5초 미만으로 낮춰 web이 본문 `timeout`을 받게 하는 방법도 있지만, 실측 0.83초 대비
> 여유가 줄어 이번에는 쓰지 않는다.)

**기록할 것** — `last_dispatch`와 시행 로그 CSV(web 할 일 ②-a, `services/web/logs/web_trials_*.csv`)에 장치별로 `ok`(위 판정), 본문 `status`·`reason`, 모의 여부,
picar LED 실패 여부, 응답 시간(ms)을 남긴다.

| **인터넷 단절** (Supabase에 닿지 않음) | 회원 API가 `reason: offline`을 돌려준다(Supabase 요청 타임아웃 5초 `SUPABASE_TIMEOUT_S`). 결과 저장은 `queued` | 로그인·가입에 "인터넷에 연결되지 않아 회원 확인을 할 수 없습니다. 게스트로 학습할 수 있어요." 결과 화면에 "인터넷 연결을 기다리는 중"(대기 n건) | **계속(게스트).** 판정·장치 제어는 교육장 안에서만 오가므로 인터넷과 무관하다. 회원 결과는 대기열에 쌓인다 | **자동** — 30초마다 다시 보낸다(`RESULTS_RETRY_INTERVAL_S`). 즉시 보내기는 `POST /api/auth/results/retry`(§8) | 구현. ⚠️ 인터넷만 없을 때 로그인·가입 응답이 10~20초 걸림(08, 대응 중). Supabase 무료 프로젝트는 7일 요청이 없으면 일시 정지 — 시연 전 확인(08) |

- 위 표의 감지·화면·흐름은 **코드(`state_machine.py`·`main.js`·`ble_bridge.py`·picar `app.py`) 기준**으로 정리했다. 실물에서 확인된 것은
  각 출처 문서에 적힌 것뿐이다 — 예: SC-04 재시도(2026-09-29, 09), 카메라 고장 두 경우(가짜 카메라 재현, 16 §2.4), picar Ctrl+C 시 정지(2026-10-04, 06 §1-3·08).
- 운영자가 서비스를 끌 때는 `bash scripts/rpi/stop_all.sh` — picar 정지 명령을 먼저 보낸 뒤 web → vision → actuation → picar 순서로 Ctrl+C
  (`kill -9`는 쓰지 않는다, [17](17_실물실행_스크립트_사용법.md)).

## 8. web 브라우저용 API — 영상 중계 · 회원 (2026-10-04 정리)

교육장 PC 브라우저 ↔ web(RPi5 `:8000`) 사이 계약이다. 학습 흐름 API(`/api/state`·`/api/start`·`/api/confirm` 등)는
[14 §4.1](14_web_구현보고서.md), DB 저장은 [18](18_DB설계서.md)에 있다. 여기서는 다른 서비스·DB와 맞닿는 것만 적는다.

**영상 중계** — `services/web/backend/camera.py`

| 엔드포인트 | 응답 | 비고 |
| --- | --- | --- |
| `GET /api/camera/stream` | vision `GET /stream`(§4-1)의 MJPEG를 그대로 중계 | 브라우저는 vision 주소(`VISION_URL`, RPi5 기준)에 닿지 않아 같은 출처로 중계한다. vision 연결 실패·200 아님이면 503 `{"status": "error", "reason": "vision_unreachable" \| "vision_http_<코드>"}`. 연결 타임아웃 3초, 읽기 타임아웃 없음 |

**회원 API** — `services/web/backend/members.py` 라우터, 접두 `/api/auth`

| 메서드 · 경로 | 본문 | 요점 |
| --- | --- | --- |
| `POST /signup` | `email`, `password`, `name`, `org`(선택) | 가입 후 이 스테이션의 현재 학습자로 로그인. 비밀번호 규칙 18 §6-2 |
| `POST /login` | `email`, `password` | 실패 5회/10분이면 잠금(이메일·접속 주소 각각) |
| `POST /find-id` | `name`, `member_code` | 둘 다 맞으면 가린 이메일 `email_masked`. 10회/10분 제한 |
| `POST /password/request` | `email` | 6자리 인증 코드 메일(로컬 모드는 서버 로그). 가입 여부와 관계없이 같은 안내. 3회/10분 제한 |
| `POST /password/reset` | `email`, `code`, `new_password` | 코드 틀림 5회/10분 잠금. 성공해도 로그인시키지 않음 |
| `POST /guest` | — | 게스트 학습자(회원 DB에 올리지 않음) |
| `POST /logout` | — | 현재 학습자 해제 |
| `GET /me` | — | `{"member": …, "store": {"backend", "pending", "last_save"}}` |
| `POST /results/retry` | — | 대기열 즉시 재전송(평소엔 30초마다 자동) |

- 응답은 HTTP 200에 `{"status": "ok" \| "error", "reason", "message"}`. 성공하면 `member`가 붙는다.
- `member`는 `member_code`(화면 표기 "사원 코드")·`name`·`org`·`guest`만 담는다 — **이메일은 넣지 않는다**(2026-10-01 `faa3fa9`.
  `/api/state`도 같은 형식).
- 회사 사이트(`services/portal`)는 같은 `members.py` 함수를 쓰지만 API는 따로다 — [19 §3](19_회사웹사이트.md).
