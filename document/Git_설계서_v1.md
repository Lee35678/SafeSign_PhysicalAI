## 1. 개요

본 문서는 SafeSign_PhysicalAI 프로젝트의 Git 저장소 운영 전략을 정의한다. 팀원 간 협업 시
브랜치 생성·병합·배포 규칙을 명확히 하여 코드 충돌과 배포 사고를 최소화하는 것을 목적으로 한다.

전통적인 Git Flow(main / develop / feature / release / hotfix)는 브랜치 종류가 많아 소규모·
비전공 인력이 혼합된 팀에는 운영 부담이 크다. 이에 본 프로젝트는 release, hotfix 브랜치를
제외하고 **main / dev / feature 3단계 구조**로 단순화하여 설계하였다.

| 고려사항 | Git Flow(표준) | 본 프로젝트 설계 |
| --- | --- | --- |
| 브랜치 종류 수 | 5종 (main, develop, feature, release, hotfix) | 3종 (main, dev, feature) |
| 배포 전 별도 검증 브랜치 | release 브랜치 운영 | dev에서 충분히 검증 후 main으로 직접 반영 |
| 운영 중 긴급 수정 | hotfix 브랜치 별도 운영 | feature 브랜치 워크플로우를 그대로 적용 |
| 적용 난이도 | 높음 | 낮음 (비전공 인력 포함 팀에 적합) |

---

## 2. 브랜치 구조 정의

| 브랜치 | 유형 | 역할 | 생명주기 |
| --- | --- | --- | --- |
| main | 영구 브랜치 | 검증이 완료된 최종/배포 코드를 보관 | 프로젝트 종료 시까지 유지 |
| dev | 영구 브랜치 | 각 담당 영역의 작업을 통합·검증하는 브랜치 | 프로젝트 종료 시까지 유지 |
| feature/* | 임시 브랜치 | 담당 영역별 개별 작업 단위 | 작업 완료 후 dev 병합 시 삭제 |

feature 브랜치는 `feature/담당영역` 형식으로 명명하며, 본 프로젝트에서는 아래 5개 담당
영역으로 고정 운영한다.

| 브랜치명 | 담당 영역 |
| --- | --- |
| feature/actuation | 구동(액추에이터) 제어 |
| feature/data | 데이터 수집/처리 |
| feature/picar | PiCar 로봇/하드웨어 연동 |
| feature/vision | 비전(영상 인식) 처리 |
| feature/web | 웹(대시보드/서비스) |

---

## 3. 브랜치 흐름

```
main ──────────────────────────────────────────────► main (배포)
  │                                                     ▲
  └──► dev ───────────────────────────────────────────┘
        │▲    │▲    │▲    │▲    │▲
        ││    ││    ││    ││    ││
        ▼│    ▼│    ▼│    ▼│    ▼│
   feature/  feature/  feature/  feature/  feature/
   actuation data      picar     vision    web
```

- 각 feature/* 브랜치는 dev에서 분기되어 작업 후 다시 dev로 병합(merge)된다.
- dev가 충분히 안정화되면 dev → main으로 병합하여 배포한다.

---

## 4. 워크플로우 정의

**(1) 일반 작업 흐름 (feature → dev)**

| 순서 | 단계 | 수행 주체 |
| --- | --- | --- |
| 1 | dev 브랜치 최신화 (pull) | 작업자 |
| 2 | 담당 feature/* 브랜치로 전환(또는 생성) | 작업자 |
| 3 | 작업 수행 및 커밋 | 작업자 |
| 4 | 원격 저장소에 push | 작업자 |
| 5 | Pull Request 생성 (base: dev) | 작업자 |
| 6 | 코드 리뷰 및 승인 | 리뷰어 |
| 7 | dev로 병합 | 리뷰어/작업자 |
| 8 | feature 브랜치 삭제(정리) | 작업자 |

**(2) 배포 흐름 (dev → main)**

| 순서 | 단계 | 수행 주체 |
| --- | --- | --- |
| 1 | dev 브랜치 안정성 확인(통합 테스트) | 팀 전체 |
| 2 | Pull Request 생성 (base: main, compare: dev) | 담당자/팀 리더 |
| 3 | 최종 승인 | 팀 리더(지정 승인자) |
| 4 | main으로 병합 | 승인자 |

배포는 매 작업 단위가 아니라, 정해진 마일스톤/일정 시점에 일괄적으로 수행하는 것을 원칙으로
한다.

---

## 5. 브랜치 보호 정책

| 브랜치 | 정책 |
| --- | --- |
| main | 직접 push 금지, PR을 통한 병합만 허용, 최소 1인 이상 승인 필수 |
| dev | 직접 push 금지 원칙(불가피한 경우 팀 합의), PR을 통한 병합 권장 |
| feature/* | 담당자 자율 운영, 단 PR 대상(base)은 항상 dev로 설정 |

> GitHub 기준 설정 위치: Settings → Branches → Branch protection rules 에서 main, dev 각각에
> "Require a pull request before merging", "Require approvals(1)" 옵션을 활성화한다.

## 6. 커밋 메시지 규칙

```
[담당영역] 작업 내용 요약

예시)
[vision] 차선 인식 알고리즘 초기 구현
[data] 센서 로그 수집 모듈 추가
[web] 대시보드 실시간 그래프 연동
```

담당영역 태그는 5개 feature 브랜치명과 동일하게 `actuation / data / picar / vision / web`
중 하나를 사용하며, 여러 영역에 걸친 작업(예: 문서, 설정 파일)은 `[common]`을 사용한다.

## 7. .gitignore 정책

프로젝트 특성상 대용량 데이터·모델·환경 파일이 실수로 커밋되어 저장소가 비대해지거나
민감 정보가 노출되는 것을 방지하기 위해 아래 패턴을 저장소 최상위 `.gitignore`에 기본
포함한다.

```gitignore
# 데이터 (04_데이터셋명세서_v2 관련 원본 이미지/영상)
data/raw/
data/tmp/
*.mp4
*.avi

# 학습된 모델 가중치 (05_모델카드_v3 관련)
*.pt
*.pkl
*.h5
models/checkpoints/

# 환경/설정 (API 키, 시리얼 포트 등 인터페이스 계약서 관련 민감 값)
.env
config/local.*

# 캐시·빌드 산출물
__pycache__/
*.pyc
node_modules/
dist/
build/

# OS/에디터
.DS_Store
.vscode/
.idea/
```

- 각 feature 담당자는 위 목록에 자신의 영역에서 추가로 제외할 파일(예: vision 담당의
프레임 캐시 폴더)이 있는지 확인하고, PR로 `.gitignore`에 추가한다.
- 이미 커밋된 대용량/민감 파일이 발견되면 즉시 팀 리더에게 보고하고, 이력 삭제(`git filter-repo`
등)가 필요한지 판단한다.

## 8. 대용량 파일 처리 방침

- 원칙적으로 **원본 학습 데이터(이미지/영상)는 Git 저장소에 포함하지 않는다.** 별도 클라우드
저장소(예: Google Drive, 팀 공유 스토리지)에 두고, 코드에는 데이터 경로/다운로드 스크립트만
포함한다.
- 소규모 샘플 데이터(테스트용 몇 장의 이미지 등, 수 MB 이하)는 `data/samples/` 폴더에 한해
커밋을 허용한다.
- Git LFS(Large File Storage) 도입 여부는 현재 데이터 규모상 필수는 아니라고 판단하되, W3
데이터 수집 완료 후 저장소 용량이 100MB를 초과하면 도입을 재검토한다. (판단 주체: data
담당자 + 팀 리더)

## 9. 파일/디렉토리 소유권 규칙 (충돌 예방)

5개 feature 브랜치가 병렬로 작업하는 만큼, 서로 다른 담당자가 같은 파일을 동시에 수정하여
발생하는 병합 충돌을 예방하기 위해 아래와 같이 디렉토리 경계를 둔다.

| 디렉토리(예시) | 주 담당 |
| --- | --- |
| `/actuation/` | feature/actuation |
| `/data/` | feature/data |
| `/picar/` | feature/picar |
| `/vision/` | feature/vision |
| `/web/` | feature/web |
| `/common/` (공용 유틸, 03_인터페이스계약서_v2 관련 스키마 등) | 전체 협의 후 수정, 수정 전 팀 채팅으로 공유 |
| `README.md`, `.gitignore` | 전체 협의, 임의 단독 수정 지양 |

- `/common/`, 최상위 설정 파일 등 공용 파일을 수정해야 하는 경우, PR 생성 전 팀 채팅(또는
회의)에서 사전 공유하여 동시 수정으로 인한 충돌을 줄인다.
- 인터페이스 계약(예: micro:bit ↔ RPi 시리얼 스키마, 03_인터페이스계약서_v2 관련)이 바뀌는
경우, 영향을 받는 모든 feature 담당자에게 사전 공지 후 수정한다.

## 10. 롤백 및 되돌리기 절차

- main 병합 후 문제가 발견된 경우, **`git reset`이 아닌 `git revert`를 원칙으로 한다**
(이미 공유된 브랜치의 이력을 강제로 바꾸지 않기 위함).
- 절차: ① 문제 발견자가 팀 리더에게 즉시 보고 → ② 팀 리더(또는 지정 승인자)가 되돌릴
커밋 범위를 확정 → ③ revert 커밋 생성 후 PR로 main에 반영 → ④ dev도 동일하게 동기화
(dev가 뒤처지지 않도록 revert 내용을 dev에도 반영).
- 시연 직전(W5) 등 긴급 상황에서는 팀 리더 승인 하에 리뷰 절차를 신속화하되, 반드시 revert
커밋 자체는 남긴다(이력 삭제 금지).

## 11. README 관리 규칙

- 저장소 최상위 `README.md`는 브랜치 구조, 담당자, 실행 방법(picar/micro:bit 연동 포함)을
설명하는 최소 문서로 유지한다.
- 브랜치 구조(§2)나 담당 영역이 바뀌는 경우, 해당 PR에 README 갱신을 포함한다.
- 변경 시 최상단에 "최근 변경일 + 변경 사유 한 줄"을 남겨, 02_설계문서_v2 등 기존 문서의
관리 방식과 통일한다.

## 12. 예외 상황 처리

- **병합 충돌**: 병합을 시도한 작업자가 우선 해결을 시도하며, 판단이 어려운 경우 관련
담당자와 협의하여 최종 내용을 결정한다. §9의 소유권 규칙을 우선 참고하여 원 소유자와
상의한다.
- **운영 중 긴급 수정**: 별도의 hotfix 브랜치를 운영하지 않으며, 해당 담당 영역의
feature/* 브랜치 워크플로우를 그대로 따르되 리뷰·승인 절차를 신속화하여 처리한다.
- **대용량/민감 파일 실수 커밋**: §7~§8 기준으로 즉시 조치하고, 필요 시 이력 삭제를
팀 리더와 협의 후 진행한다.
