# picar 하드웨어 검증 리포트 (v1 — 작성 중)

**팀명**: 심기일전 · **작성자**: 송승호 (하드웨어·로봇동작 R)
**최초 작성**: 2026-09-23 · **대상**: `services/picar` + Raspbot 차체 + RPi4B

> **이 문서의 범위**: picar **하드웨어 경로**(I2C 모터 · GPIO LED · 전원 · 무선)가 설계대로
> 동작하는지에 대한 실측 기록이다. 수신호 **분류 정확도·혼동행렬**은 `06_테스트·평가리포트_v3`,
> 설계 근거와 배선 사양은 `11_하드웨어설계서_v1`이 각각 다룬다 — 중복해서 적지 않는다.
>
> 📝 **표기**: 이 문서 안의 `§n`은 이 문서의 절이다. 다른 문서를 가리킬 때는 **"설계서 §n"**
> (= `11_하드웨어설계서_v1`)처럼 문서명을 앞에 적는다.
>
> 📌 **판정 경로(vision)와 무관하다.** picar는 판정 결과를 받아 물리로 표현하는 출력 장치이므로,
> 여기서의 실패는 KPI 중 **물리 피드백 지연**과 시연 안정성에만 영향을 준다.

## 1. 검증 대상 구성 (as-built)

실제로 조립·검증한 구성이다. 설계 의도는 `11_하드웨어설계서_v1` §5·§7 참고.

| 항목 | 값 |
| --- | --- |
| 컴퓨트 | Raspberry Pi 4B 8GB · Raspberry Pi OS **Bookworm** (제작사 이미지 미사용 — 설계서 §5.5.7) |
| 모터 | Raspbot MCU 코프로세서 **I2C `0x16`** 경유 (reg `0x01` 구동 / `0x02` 정지) |
| 외부 LED | 5mm 4개 — 적색 **BCM13·19**, 황색 좌 **BCM5** / 우 **BCM6**, 각 **220Ω** 개별 저항 |
| LED 구동 | `gpiozero.LEDBoard` (적색 2핀을 한 스레드로 묶어 점멸 동조 보장) |
| 전원 | **차체 배터리 단일 계통** — 3S 11.1V / 2200mAh / 24.42Wh → 차체 강압 → **헤더 5V로 Pi 급전** |
| 무선 | Wi-Fi (개발 중 공유기 경유. 시연 시 RPi5 AP 직결 — 설계서 §6.1) |
| 자동 정지 | `PICAR_MOTION_DURATION_S` = **2.0초** (잠정값, 미확정 — 설계서 §10 #3) |

> ⚠️ **전원은 2026-09-22에 한 번 뒤집힌 결정**이다. 오전에는 "모터=배터리 / Pi=별도 어댑터"로
> 분리하기로 했다가, 주행 시연에 테더링이 불가하다는 이유로 **단일 계통**으로 확정했다.
> 그 결과 "모터 노이즈가 Wi-Fi에 영향을 주는가"가 다시 실측 대상이 됐다(§3·§4.2).

## 2. 측정 지표

| 지표 | 도구 | 판정 기준 |
| --- | --- | --- |
| **I2C 도달성** | `GET /health` → `hardware.i2c.reachable` | `true` |
| **전원 안정성** | `vcgencmd get_throttled` (Pi 로컬) | **`0x0`** |
| **무선 안정성** | `scripts/load_test.py` 요청 실패율 | 0% |
| **무선 신호 세기** | `iw dev wlan0 link` → `signal` (dBm) | **≥ -67 dBm** 유지 |
| **왕복 지연** | 같은 스크립트, 성공 요청 기준 P95 | **≤ 500ms** (`03_인터페이스계약서_v2` §5-2 예산) |
| **자동 정지** | 육안 + `/health` → `hardware.motion_active` | 2초 내 정지, `false` |

### `get_throttled` 비트 해석

| 비트 | 값 | 의미 |
| --- | --- | --- |
| 0 | `0x1` | **현재** 언더볼티지 (5V 레일 < 4.63V) |
| 1 | `0x2` | 현재 주파수 제한 |
| 2 | `0x4` | 현재 스로틀링 |
| 16 | `0x10000` | **부팅 이후 언더볼티지 발생 이력** (sticky) |
| 18 | `0x40000` | 부팅 이후 스로틀링 발생 이력 |

> 🔴 **bit 16은 부팅 이후 계속 누적된다.** 회차마다 깨끗한 값을 얻으려면 **테스트 전 재부팅**하고,
> 시작 시점에 `0x0`임을 확인한 뒤 진행할 것. 그러지 않으면 이전 회차의 플래그와 구분할 수 없다.

### 3.2 해석

- **차체 강압 회로가 Pi와 모터를 동시에 감당한다.** 벌크 커패시터 불필요 (설계서 §10 #17 종결).
- **모터 노이즈가 무선 링크에 영향을 주지 않았다.** 전원 계통을 공유해도 관측되는 간섭이 없다.
- **자동 정지가 실제로 동작한다.** `_safe_stop()`이 I2C 예외를 `except: pass`로 삼키는 구조라
  실패해도 로그가 남지 않는다 — 이 확인이 바닥 주행의 선결 조건이었다.

### 3.3 🟡 이 결과의 한계

**무부하 조건이다.** 바퀴가 떠 있어 모터가 차체 무게를 밀지 않았다. 바닥에서는

1. **기동 토크**로 전류가 크게 늘고 (정지 → 출발 순간이 최악),
2. 배터리가 **12.6V → 9.0V**로 갈수록 강압 입력 여유가 줄어든다 — **시연 후반부가 가장 불리**하다.

→ §4의 부하 테스트로 재확인한다.

#### 결과 해석

✅ **전원은 부하 조건에서도 문제없다.** 누적 약 **10분**, `speed 70` 포함 10회 전부
`get_throttled = 0x0`이었다. 무부하 결과(§3)가 부하에서도 유지됐으므로 **벌크 커패시터는
불필요**하고, 설계서 §10 #18을 닫을 수 있다.

✅ **무선도 안정적이다.** 총 653회 요청에 **실패 0건**, 지연 P95는 회차와 무관하게 **43~49ms**로
일정했다. 계약 예산 500ms의 **10분의 1**이다. 신호도 측정 구간에서 -27 ~ -54 dBm으로 양호했다.

🔴 **#10에서 정지 실패 — 이번 테스트의 가장 중요한 발견이다.**

`speed 50`으로 올린 **#10에서만** "끝날 때 정지 안 됨"이 관측됐다. 원인은 코드에 있었다.

```python
if kind == "stop":
    _cancel_auto_stop()   # ← 안전망을 먼저 걷고
    _write_stop()         # ← 그 다음에 정지를 쓴다
```

**`_write_stop()`이 실패하면 자동 정지 타이머는 이미 취소된 뒤**라, 차를 멈출 수단이 하나도
남지 않는다. 전원(`0x0`)은 정상이었으므로 **전원이 아니라 I2C 경로 문제**이며, `speed 50`에서만
난 것은 모터 전류가 클수록 I2C에 노이즈가 실리기 때문으로 보인다.

> ⚠️ **이 실패를 `load_test.py`가 놓쳤다** — 실패/전송이 `0/105`로 기록돼 있다. 스크립트가
> HTTP 200만 보고 응답 **본문**을 읽지 않았기 때문이다. picar는 I2C가 실패해도
> `{"status":"partial","motor":{"reason":"i2c_failed"}}` 를 **200으로** 돌려준다.
> **web의 `_post_with_retry`에서 지적했던 것과 같은 결함을 내 스크립트가 갖고 있었다.**

**조치 (2026-09-23 적용)**

| # | 조치 | 위치 |
| --- | --- | --- |
| 1 | **정지 쓰기 성공 후에 타이머를 걷도록 순서 반전** — 실패 시 안전망이 남아 늦어도 2초 안에 멈춘다 | `controller._apply_motor` |
| 2 | **정지 쓰기 재시도**(기본 3회, `PICAR_STOP_RETRY`) — I2C 노이즈 한 번에 차를 놓치지 않기 위함 | `controller._write_stop_retrying` |

| 4 | **`load_test.py`가 응답 본문의 `motor.status`까지 확인** | `scripts/load_test.py` |

### 4.2 무선 신호 동시 관측

실패가 났을 때 **모터 노이즈인지 신호 부족인지**를 가르려면 신호 세기 기록이 필요하다.
Pi에서 아래를 같이 띄워 둔다.

```bash
while true; do
  L=$(iw dev wlan0 link)
  S=$(echo "$L" | grep -oP 'signal:\s*\K-?\d+')
  B=$(echo "$L" | grep -oP 'tx bitrate:\s*\K[\d.]+')
  echo "$(date +%T)  signal=${S:-끊김} dBm  bitrate=${B:-N/A} Mb/s"
  sleep 1
done | tee -a ~/wifi.log
```

| 실패 시점의 신호 | 진단 | 대응 |
| --- | --- | --- |
| **-50 dBm 내외(양호)** | **모터 노이즈** | 전원 쪽 — 벌크 커패시터·배선 재검토 |
| **-70 dBm 이하(약함)** | 단순 신호 부족 | AP 위치·채널·주행 범위 |

> 🔑 **패턴에 따라 해석이 달라진다.**
>
> | 패턴 | 차 위치 | 해석 |
> | --- | --- | --- |
> | `spin` | **고정** — 안테나 방향만 회전 | **모터 노이즈를 깨끗하게 분리**한다 |
> | `circle` | 이동 — 거리·방향 동시 변화 | 노이즈와 거리 효과가 **섞인다** |
>
> `spin`에서 실패가 없고 `circle`에서만 난다면 노이즈가 아니라 **주행 범위가 AP 커버리지를
> 벗어난 것**일 가능성이 크다. 시연장 배치(설계서 §6.1 AP 위치)에 반영할 정보다.

### 4.3 중단 기준

| 증상 | 의미 | 조치 |
| --- | --- | --- |
| `get_throttled` ≠ `0x0` | 언더볼티지 | 중단 → 벌크 커패시터(470~1000µF) 검토 |
| **Pi 재부팅** | 심한 전압 강하 | 즉시 배터리 차단 |
| 요청 실패 다발 | 무선 끊김 | 실패 시각 + **그 시점 신호 세기** 기록 후 중단 (§4.2) |
| 신호 **-70 dBm 이하** 지속 | 커버리지 밖 | 주행 범위 축소 또는 AP 재배치 |
| 모터 발열·이상음 | 기계적 문제 | 즉시 중단 |

### 4.4 ⬜ 배터리 전압 측정 수단 미확보

현재 팩 단자에 접근할 수단이 없어 전압을 기록하지 못한다. 대안:

1. **BMS(보호회로) 유무 확인** — 있으면 과방전은 팩이 자체 차단한다 (설계서 §10 #16 해소)
2. **밸런스 커넥터(JST-XH)가 있으면 3S 배터리 체커** 부착 — 가장 확실
3. 그 전까지는 **누적 구동 시간 + `get_throttled`** 로 대체. 배터리가 내려가면 강압 입력 여유가
   줄어 결국 언더볼티지 플래그가 뜨므로, **`0x0`이 깨지는 시점을 방전 한계 접근으로 간주**한다
   (늦은 신호이지만 팩을 크게 상하게 할 정도는 아니다)

| 서행 | `slow` | `forward` | **20** | 황색 양쪽 `blink` |
| 좌회전_유도 | `turn_left` | `left` | **40** | 좌측 황색 `blink` |
| 우회전_유도 | `turn_right` | `right` | **40** | 우측 황색 `blink` |
| 확인_완료 | `complete` | `stop` | 0 | 적·황 번갈아 2회(스키마로 표현 불가 — 미결 #4) |
| 후진 | `reverse` | `backward` | **40** | — |
| 주의 | `caution` | `stop` | 0 | 황색 양쪽 `blink` |

- **`speed`는 50을 넘기지 않는다.** 2026-09-24부터 **picar 서비스가 `PICAR_MAX_SPEED`(기본 50)로
  잘라서 실행**하고 응답에 `speed_capped_from`을 붙인다 — 안전망일 뿐이니 web은 처음부터 위 값을 보낼 것.
  (당시 `origin/feature/web`은 서행 40 / 좌우 60 / 후진 50을 보내고 있었다.)
- 주행은 2초 뒤 자동 정지한다(잠정, `proposals/picar_주행시간_스키마_변경안.md` 결정 1).
- 응답은 HTTP 200이어도 본문 `status`가 `partial`일 수 있다(I2C 실패) — **본문을 읽을 것**
  (`proposals/web_picar_통신_신뢰성_개선안.md` 변경 1).
- `picar_command.schema.json`의 `speed` 설명은 아직 *"⚠️ 실측 후 확정"* 이다. 값이 정해졌으므로
  갱신할 때가 됐지만 `shared/schemas/` 변경이라 **전원 리뷰 대상**이다 — 회의 안건으로 올린다.

## 6. 디버깅에서 얻은 절차 (재사용)

LED가 전혀 켜지지 않았을 때 원인을 좁힌 경로다. 같은 증상에서 그대로 쓸 수 있다.

| 관찰 | 판단 |
| --- | --- |
| `POST /picar` 응답이 `ok` (≠ `mocked`) | 소프트웨어·`MOCK_HARDWARE` 정상 |
| `pinctrl set 13 op dh`로도 안 켜짐 | **소프트웨어 문제 아님 — 물리 쪽** |
| `pinctrl get 13` = `hi` | SoC는 3.3V를 내고 있음 → **핀 이후 구간** 문제 |
| **4개 전부** 실패 | 개별 불량이 아니라 **공통 원인** → GND·전원·핀 기준점 |

- 🔑 **`pinctrl`로 서비스를 우회하면 SW/HW가 한 번에 갈린다.**
- 🔑 **"전부 실패 = 공통 원인"** — 개별 배선을 뜯기 전에 공통 요소부터 본다.
- ⚠️ **`pinctrl` 잔상**: `dh`로 올린 핀은 서비스를 다시 띄우기 전까지 그대로 남는다. GND를 고친
  직후 "LED가 안 꺼진다"고 판단했던 것이 이 때문이었고, **코드 문제가 아니었다**
  (gpiozero 2.0.1 `LEDBoard.off()`가 `_stop_blink()`를 먼저 호출하는 것까지 확인).

## 7. 결론 및 미결 항목

### 7.1 현재까지의 결론

**picar 하드웨어 경로는 부하 조건에서도 설계대로 동작한다.**

- **전원 단일 계통은 안전하다.** 누적 약 10분·`speed 70` 포함 10회 전부 `get_throttled = 0x0`.
  무부하(§3)와 부하(§4) 모두 통과했으므로 **벌크 커패시터는 불필요**하다.
- **무선도 안정적이다.** 653회 요청 실패 0건, 지연 P95 43~49ms — **계약 예산 500ms의 1/10**이다.
- **속도 실측값이 확정됐다**(§4.5). 서행 20 / 좌우회전·후진 40 / 상한 50.

> 🔴 **다만 부하 테스트가 소프트웨어 결함 하나를 드러냈다.** 정지 쓰기가 실패하면 자동 정지
> 타이머까지 이미 취소된 상태라 **차를 멈출 수단이 없어지는** 구조였다(§4.1 #10). 조치는
> 완료했으나 **`speed 50` 재시행으로 확인해야 한다.** 부하 테스트를 건너뛰었다면 시연 중에
> 발견했을 결함이다.
